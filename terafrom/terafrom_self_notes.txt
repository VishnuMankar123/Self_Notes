

# ✅ **Terraform – Definition (English-wali Hindi)**

**Terraform ek Infrastructure as Code (IaC) tool hai** jo aapko cloud resources **code likh-kar** create, update, aur delete karne deta hai.

Matlab:
Jaisa aap Java ya Python ka code likhte ho, waise hi aap Terraform ka code likhkar:

* AWS EC2 bana sakte ho
* VPC create kar sakte ho
* Google Cloud resources manage kar sakte ho
* Azure networking setup kar sakte ho
* On-prem VMware infra manage kar sakte ho

**Terraform ka kaam hai entire infrastructure ko automate karna — bina manual console configuration ke.**

### **Simple words mein:**

Terraform = Cloud ka *remote control*
Jo bolta hai: “EC2 bana do”, “S3 delete kar do”, “VPC update kar do” — aur cloud wahi karega exactly jaisa code mein likha hai.

---

# ✅ **Why Terraform? (English-wali Hindi)**

* Manual kaam nahi → sab code se hota hai
* Infrastructure repeatable hota hai
* Version control (Git) use kar sakte ho
* Multi-cloud support (AWS + Azure + GCP sab ek code se)
* Team collaboration easy hoti hai

---

# 🕘 **History of Terraform (English-wali Hindi)**

### **2014**

* HashiCorp ne Terraform ko **open-source** project ke रूप में release kiya.
* Goal: Distributed systems aur cloud infrastructure ko automate karna.

### **2015–2017**

* Terraform ne AWS, Azure, GCP jaise major clouds ke providers add kiye.
* Ye time pe Terraform fastest-growing DevOps tool ban gaya.

### **2018**

* Terraform registry launch hua jahan community modules upload kar sakti thi.
  (Jaise: ready-made VPC module, EC2 module, ALB module)

### **2019**

* Terraform 0.12 release — Sabse big update.
* Isme better syntax, for loops, count enhancements aaye.

### **2020**

* Terraform Cloud launch hua — collaborative workflows ke liye.
* Remote state + policy checks + cost estimation features aaye.

### **2021**

* Terraform 1.0 release.
* Stability guarantee di gayi → backward compatibility strong hui.

### **2022–2024**

* Enterprise features improve huye.
* Module ecosystem huge ban gaya.
* Multi-cloud orchestration ka trend boom hua.

# ✅ **Infrastructure as Code (IaC) – Why It Matters (English-wali Hindi)**

**Infrastructure as Code (IaC)** ka simple matlab:
**Cloud infrastructure ko manually click–click karke banane ke bajaye, code likhkar create karna.**

Jaise aap AWS Console me jaake manually EC2 banate ho →
IaC me aap sirf code likho, aur woh automatically EC2, VPC, Load balancer sab bana deta hai.

---

# ⭐ **Why IaC Matters? (IaC important kyun hai?)**

## **1️⃣ Speed & Automation (kaam bohot fast hota hai)**

Manual setup me:

* VPC create karo
* Subnets banao
* Route tables attach karo
* NIC configure karo

Sab **time-consuming** aur boring.

IaC me:

```terraform
terraform apply
```

Aur poora infrastructure **2–3 minutes me ready**.

---

## **2️⃣ Consistency (har baar same result milega)**

Manual setup me human errors hoti hain
→ kabhi subnet wrong ban gaya
→ kabhi security group galat set ho gaya

IaC me code fix hota hai → output **100% consistent**.

---

## **3️⃣ Version Control (Git se pura infra manage hota hai)**

Jaise code Git me store hota hai,
waise IaC me **infrastructure bhi Git me save hota hai**.

Benefits:

* kisne kya change kiya track hota hai
* purane version par rollback possible
* team collaboration easy

---

## **4️⃣ Reusability (same infra bar-bar use kar sakte ho)**

Ek baar agar aapne:

* VPC module banaya
* EC2 module banaya

Toh same module **dusre projects me copy-paste** kar sakte ho.

Production-grade companies me ye bohot useful hota hai.

---

## **5️⃣ Multi-Environment Support (DEV / QA / PROD easily manage)**

Aap same code se multiple environment bana sakte ho:

* **dev.tfvars**
* **qa.tfvars**
* **prod.tfvars**

Aur bas run karo:

```sh
terraform apply -var-file=prod.tfvars
```

Instant PROD infra ready.

---

## **6️⃣ Cost Control (galti se resources on rakhe to pata lagta hai)**

IaC code aapko clearly dikhata hai:

* kitne EC2
* kitne LB
* kitne RDS
* kitne subnets

Mistakes kam hoti hain → billing surprises reduce.

---

## **7️⃣ Disaster Recovery (infra quickly restore ho jata hai)**

Agar pura cloud delete ho jaye…
IaC se aap just command chalao:

```sh
terraform apply
```

Pureka infrastructure **as it is** recreate ho jayega.

---

## **8️⃣ Standardization (company ke rules follow karwana easy)**

IaC ensures:

* Naming conventions
* Security policies
* Network rules

Sab automatically follow hote hain →
team me koi bhi person mistake nahi karega.

# ✅ **Terraform HCL — Kya Hai? (English-wali Hindi)**

**HCL ka full form hai → HashiCorp Configuration Language.**
Ye Terraform ka **official language** hai jisme aap apna infrastructure ka code likhte ho.

**Simple words mein:**
HCL = Terraform ka *coding style* / *syntax*
jisme aap likhte ho:

* EC2 kaise banana hai
* VPC ka size kya hona chahiye
* Security group me kaunsi rules honge
* Environment variables kya honge

---

# ⭐ **HCL — Kyon use hota hai?**

HCL ka purpose hai:

✔ Human ke liye easy
✔ Machine ke liye readable
✔ Cloud infrastructure ko describe karna

Ye normal programming language nahi hai,
sirf **infrastructure describe** karne ke kaam aati hai.

---

# ⭐ **HCL ke Features (Simple English-Hindi)**

### **1️⃣ Declarative Syntax**

Aap sirf “kya chahiye” batate ho —
HOW ka part Terraform handle karta hai.

Example:
"Aur EC2 instance chahiye" → Terraform khud bana dega.

---

### **2️⃣ JSON se easy**

Terraform JSON भी support karta hai,
par HCL zyada **clean, readable aur short** hota hai.

---

### **3️⃣ Variables Support**

Aap values ko variable bana sakte ho.

```hcl
variable "instance_type" {
  default = "t2.micro"
}
```

---

### **4️⃣ Reusable Modules**

HCL se aap modules create kar sakte ho
jo multiple projects me reuse hote hain.

---

### **5️⃣ Functions Support**

Aap HCL me functions use kar sakte ho:

* `lower()`
* `upper()`
* `length()`
* `format()`
* `file()`

---

### **6️⃣ Strong Typing**

Variables me type define kar sakte ho:

```hcl
type = string
type = number
type = list(string)
```

---

# ⭐ **HCL ka Basic Example**

Ye ek simple EC2 ka HCL code:

```hcl
resource "aws_instance" "my_server" {
  ami           = "ami-0abcd1234"
  instance_type = "t2.micro"

  tags = {
    Name = "MyServer"
  }
}
```

**Terraform 2 type ke attributes deta hai:**

## ✔ **Explicit Attributes (Jise aap set karte ho)**

Example:

```
instance_type = "t2.micro"
```

Ye aap manually set kar rahe ho.

## ✔ **Computed Attributes (Jo Terraform generate karta hai)**

Example:

```hcl
output "server_ip" {
  value = aws_instance.myserver.public_ip
}
```

Yaha `public_ip` ek attribute hai jo **Terraform generate karta hai**
jab EC2 instance ban jaye.

### Common computed attributes:

* `id`
* `arn`
* `public_ip`
* `private_dns`
* `vpc_id`

Attributes ka use:

* outputs me
* dousre resources me dependency banate time

```hcl
resource "aws_instance" "web" {   # BLOCK

}

output "server_ip" {
  value = aws_instance.web.public_ip        # ATTRIBUTE
}
```

# 🎯 **Terraform HCL Syntax Rules (Easy English-Hindi)**

Terraform code **HCL (HashiCorp Configuration Language)** me likha jata hai.
Isme kuch basic rules hai jinko follow karna **must** hota hai.

Neeche saare rules simple explanations + examples ke saath milega 👇

---

# ⭐ Rule 1: **Everything in Terraform is a Block**

Har Terraform code **blocks** me likha jata hai.

### Example:

```hcl
resource "aws_instance" "myserver" {
}
```

Block =

* keyword → `resource`
* type → `"aws_instance"`
* name → `"myserver"`
* body → `{ }` ke andar code

---

# ⭐ Rule 2: **Blocks always use { } (curly brackets)**

HCL me har block ke andar details **curly braces** me hote hain.

### Example:

```hcl
provider "aws" {
  region = "ap-south-1"
}
```

---

# ⭐ Rule 3: **Arguments use key = value format**

Block ke andar jo settings hoti hain unhe **arguments** bolte hain.

Syntax:

```
key = value
```

### Example:

```hcl
instance_type = "t2.micro"
ami           = "ami-12345"
```

---

# ⭐ Rule 4: **Strings must be inside double quotes (" ")**

HCL me strings hamesha `" "` ke andar hoti hain.

Correct ✔

```hcl
ami = "ami-12345"
```

Wrong ❌

```hcl
ami = ami-12345
```

---

# ⭐ Rule 5: **Indentation matters for readability (but not required)**

Terraform indentation ignore karta hai, but **proper formatting recommended**.

Example (good formatting):

```hcl
resource "aws_instance" "server" {
  ami           = "ami-12345"
  instance_type = "t2.micro"
}
```

---

# ⭐ Rule 6: **Attributes are referenced as: resource_type.resource_name.attribute**

Syntax:

```
aws_instance.myserver.public_ip
```

### Example:

```hcl
output "ip" {
  value = aws_instance.myserver.public_ip
}
```

---

# ⭐ Rule 7: **Lists use [ ] brackets**

Example:

```hcl
security_groups = ["sg-123", "sg-456"]
```

---

# ⭐ Rule 8: **Maps use { key = value }**

Example:

```hcl
tags = {
  Name = "MyServer"
  Env  = "dev"
}
```

---

# ⭐ Rule 9: **Variables follow a specific syntax**

### Example:

```hcl
variable "instance_type" {
  type    = string
  default = "t2.micro"
}
```

---

# ⭐ Rule 10: **Comments syntax**

Terraform me comments 3 tarah ke hote hain:

### Single-line comment:

```hcl
# This is a comment
```

### Another single-line:

```hcl
// Another comment
```

### Multi-line comment:

```hcl
/*
 This is multi-line comment
*/
```

---

# ⭐ Rule 11: **Interpolation uses ${ } inside older syntax**

Old syntax:

```hcl
"${aws_instance.server.public_ip}"
```

New syntax (recommended):

```hcl
aws_instance.server.public_ip
```

---

# ⭐ Rule 12: **Functions follow function_name(argument)**

Example:

```hcl
lower("HELLO")   # output: hello
length(var.names)
format("ID-%s", "123")
```

---

# ⭐ Rule 13: **Terraform files end with .tf or .tfvars**

* Main files → `main.tf`, `variables.tf`, `outputs.tf`
* Variables file → `dev.tfvars`, `prod.tfvars`

---

# ⭐ Rule 14: **Terraform treats all .tf files as a single configuration**

Multiple `.tf` files = Terraform automatically merge karta hai.

Example:

* `main.tf`
* `variables.tf`
* `outputs.tf`

Terraform sabko ek hi file jaisa treat karta hai.

---

# ⭐ Rule 15: **Resource type & name must be unique**

Example:

```hcl
resource "aws_instance" "myserver" { }
```

* `"aws_instance"` → resource type
* `"myserver"` → logical name (unique hona chahiye)

---

# ⭐ SUPER EASY SUMMARY (2 Lines)

### ✔ **Block** → `{ }` wali structure

### ✔ **Argument** → key = value

### ✔ **Attribute** → resource_type.resource_name.property

# 🎯 **Part 1 — Terraform Expressions (Easy English-Hindi)**

**Expression = koi bhi value calculate karne ka formula ya logic.**

Terraform me expressions ka use hota hai:

* values combine karne me
* conditions apply karne me
* resource attributes refer karne me
* lists/maps handle karne me

---

# ⭐ 1️⃣ **Literal Expressions (Direct values)**

Direct values ko literal expressions bolte hain.

### Example:

```hcl
"hello"     # string
123         # number
true        # boolean
["a", "b"]  # list
```

---

# ⭐ 2️⃣ **Reference Expressions**

Kisi resource, variable, data source ka value use karna.

Syntax:

```
resource_type.resource_name.attribute
```

### Example:

```hcl
aws_instance.web.public_ip
var.instance_type
```

---

# ⭐ 3️⃣ **Interpolation (Old style)**

Old syntax:

```hcl
"${var.name}"
```

New syntax (recommended):

```hcl
var.name
```

---

# ⭐ 4️⃣ **Conditional Expressions (ternary operator)**

Simple if-else rule:

Syntax:

```
condition ? true_value : false_value
```

### Example:

```hcl
instance_type = var.env == "prod" ? "t3.large" : "t2.micro"
```

Meaning:

* agar environment = prod → t3.large
* otherwise → t2.micro

---

# ⭐ 5️⃣ **For Expressions (loops)**

List ya map ko convert karne ke liye.

### Example (list transformation):

```hcl
[for name in var.names : upper(name)]
```

If var.names = ["vishnu", "manku"]
Output → ["VISHNU", "MANKU"]

---

# ⭐ 6️⃣ **Splat (*) Expressions**

Multiple resource attributes collect karna.

Example:

```
aws_instance.web[*].public_ip
```

---

# 🎯 Quick Summary of Expressions:

| Expression  | Purpose                           |
| ----------- | --------------------------------- |
| Literal     | direct values                     |
| Reference   | resource/variable value use karna |
| Conditional | if-else logic                     |
| For         | loops                             |
| Splat       | list of attributes                |

# 🎯 **String Interpolation Kya Hota Hai?**

**String Interpolation = String ke andar dynamic value insert karna.**

Matlab:

* Ek fixed text hai
* Ek variable ya resource ka value hai
* Dono ko combine karke final string ban jati hai

Jaise normal English me:

```
"Hello " + name + "!"
```

Terraform me ye kaam **interpolation syntax** se hota hai.

---

# ⭐ Terraform Interpolation Syntax (OLD Style)

Old syntax:

```
"${ expression }"
```

### Example:

```hcl
"${var.environment}-server"
```

Agar environment = "dev"
Output = **dev-server**

⚠ NOTE: Old syntax ab avoid karte hain, but interviews me pucha jata hai.

---

# ⭐ Terraform Interpolation (NEW Style — Recommended)

NEW syntax me **direct expression** likh sakte ho.

### Example:

```hcl
"${var.name}"   # old
var.name        # new (recommended)
```

### Example:

```hcl
"${aws_instance.web.public_ip}"   # old
aws_instance.web.public_ip        # new
```

---

# ⭐ Simple Interpolation Example

### Example block:

```hcl
variable "env" {
  default = "prod"
}

output "server_name" {
  value = "${var.env}-app"
}
```

Output:

```
prod-app
```

---

# ⭐ **Interpolation inside Strings**

Ye sabse zyada use hota hai:

### Example:

```hcl
output "name" {
  value = "server-${var.env}-${var.team}"
}
```

Agar:

* env = dev
* team = backend

Output:

```
server-dev-backend
```

---

# ⭐ **Interpolation with Resource Attributes**

### Example:

```hcl
output "server_ip" {
  value = "Public IP: ${aws_instance.myserver.public_ip}"
}
```

Output:

```
Public IP: 13.233.42.10
```

# ⭐ **Interpolation with Functions**

### Example:

```hcl
output "msg" {
  value = "User: ${upper(var.username)}"
}
```

If username = "vishnu"
Output:

```
User: VISHNU
```

# ⭐ **Interpolation with Condition (ternary) Inside String**

```hcl
output "instance_name" {
  value = "server-${var.env == "prod" ? "high" : "low"}"

```

If env = prod → `server-high`
Else → `server-low`

# ⭐ **Interpolation with Lists/Maps**

### List example:


### Map example:

# 🚀 **Terraform Workflow: Write → Plan → Apply**

Ye 3-step lifecycle hamesha Terraform me follow hota hai.

Dekho easy version:

```
1️⃣ Write  → Code likho
2️⃣ Plan   → Terraform kya karega, wo dikhta hai
3️⃣ Apply  → Changes actual cloud me create/update/destroy hote hain
```

Chaliye detail me samajhte hain 👇

---

# 🟩 **1️⃣ WRITE — Terraform Code Likhna**

Is step me aap `.tf` files me apna infrastructure define karte ho.

Yaha aap likhte ho:

* provider
* resources
* variables
* outputs
* modules

### Example:

```hcl
provider "aws" {
  region = "ap-south-1"
}

resource "aws_instance" "server" {
  ami           = "ami-0abcd123"
  instance_type = "t2.micro"
}
```

👉 Is step me Terraform kuch **execute nahi** karta.
Sirf code likhte ho.

---

# 🟦 **2️⃣ PLAN — Terraform kya karega, wo pehle bata deta hai**

Command:

```
terraform plan
```

PLAN me Terraform batata hai:

* Kaunse resources **create** honge
* Kaunse **update** honge
* Kaunse **destroy** honge
* Kya-kya changes apply honge

PLAN = **Dry run** (No changes happen)

PLAN output me symbols dikhenge:

| Symbol | Meaning      |
| ------ | ------------ |
| `+`    | Create hoga  |
| `-`    | Destroy hoga |
| `~`    | Update hoga  |
| `-/+`  | Replace hoga |

### Example Output:

```
  # aws_instance.server will be created
  + ami = "ami-0abcd123"
  + instance_type = "t2.micro"
  + id = (known after apply)
```

👉 Yaha cloud me abhi kuch bhi create nahi hota.
Sirf preview milta hai.

**Terraform double-check karne ka mauka deta hai.**

---

# 🟧 **3️⃣ APPLY — Actual Infrastructure create/update/destroy hota hai**

Command:

```
terraform apply
```

Terraform phir poochta hai:

```
Are you sure you want to apply these changes? (yes/no)
```

Jab aap `yes` likhte ho:

* AWS resources create honge
* Network, servers, databases deploy honge
* Output print hoga

Ye REAL execution hota hai.

### Example Output:

```
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Outputs:
server_ip = "13.232.45.98"
```

---

# 🧠 **Why Write → Plan → Apply workflow important hai?**

Because:

* **Human error avoid** hoti hai
* Before changes → aap PLAN dekh kar confirm kar sakte ho
* Safe, predictable infra changes hoti hain
* Teams me collaboration easy hota hai
* Large-scale infra environments break nahi hote

---

# 🔥 **REAL-LIFE Example Explained (English-Hindi)**

### Step 1: WRITE

You write EC2 instance ka code.

### Step 2: PLAN

Terraform batata hai:

* “Ek EC2 create hoga”
* “Instance type t2.micro hoga”
* “AMI ye hoga”

Ab aap dekh sakte ho → sahi hai ya nahi.
Agar galti hai → code edit kar lo.

### Step 3: APPLY

Terraform AWS ko request bhejta hai aur instance **actual me create** ho jata hai.

# 🟥 **1️⃣ terraform taint — Force Recreate Resource**

### ❓ Meaning:

Agar kisi resource me problem hai, misconfiguration hai, ya manually cloud me change ho gaya,
to **Terraform ko bolo ki is resource ko next apply me destroy + recreate kar dena.**

### 🔧 Syntax:

```
terraform taint <resource-address>
```

### 🔥 Example:

```
terraform taint aws_instance.web
```

### Result:

Next apply me:

* Purana instance delete
* Naya instance create

### Use Cases:

* EC2 corrupt ho gaya
* Disk attach nahi ho rahi
* Server configuration messed up
* QA team ko fresh infra chahiye

# 🟦 **2️⃣ terraform import — Bring Existing Resources Into Terraform**

### ❓ Meaning:

Agar aapke cloud me **pehle se resources exist** karte hain
(jise manually banaya gaya hai),
Terraform unhe **import** karke manage kar sakta hai.

Import = resource ko Terraform ke state me add karna.

### 🔧 Syntax:

```
terraform import <resource-address> <cloud-resource-id>
```

### 🔥 Example (EC2 instance import):

```
terraform import aws_instance.web i-0abc123def456
```

### Result:

* EC2 terraform state me aa jayega
* But **.tf file manually likhni padti hai** (major interview point!)

### Use Cases:

* Manual infrastructure ko Terraform me shift karna
* Disaster recovery
* Cloud resources ko Terraform control me lana

| **import**     | Existing resource ko Terraform ke control me laana | “Ye already bana hua hai — use Terraform me daal do” |
| **graph**      | Dependency diagram                                 | “Kaun resource kisi pe depend hai?”                  |
| **state list** | Show resources in state                            | “State me kya kya stored hai?”                       |
| **state rm**   | Remove from state                                  | “State se hata do, cloud se nahi”                    |
| **state mv**   | Rename/Move state resource                         | “Resource ko state me shift karo”                    |
| **state show** | Resource state details                             | “Resource ki info dikhao”                            |

# ✅ **03:23:00 – Dynamic Blocks (for_each, count)**

---

# 🔵 **4️⃣ count — Repeat resource N times**

### Example:

```hcl
variable "servers" {
  default = ["web", "app", "db"]
}

resource "aws_instance" "server" {
  count         = length(var.servers)
  ami           = "ami-12345"
  instance_type = "t2.micro"

  tags = {
    Name = var.servers[count.index]
  }
}
```

Results:

# 🔵 **5️⃣ for_each — Create resource for each map/set**

### Example:

```hcl
variable "servers" {
  default = {
    web = "t2.micro"
    app = "t2.small"
    db  = "t3.medium"
  }
}

resource "aws_instance" "server" {
  for_each      = var.servers
  ami           = "ami-12345"
  instance_type = each.value

  tags = {
    Name = each.key
  }
}
```

for_each = dynamic + readable
count = simple list repetition

---

## 🟠 Types of Provisioners

| Type        | Use                     |
| ----------- | ----------------------- |
| local-exec  | Local machine command   |
| remote-exec | Server ke andar command |
| file        | File copy               |

---

## 🟠 Example 1: local-exec

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0f5ee92e2d63afc18"
  instance_type = "t2.micro"

  provisioner "local-exec" {
    command = "echo EC2 created > result.txt"
  }
}
```

👉 EC2 create ke baad **local machine** pe command chalegi

---

## 🟠 Example 2: remote-exec (REAL USE)

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0f5ee92e2d63afc18"
  instance_type = "t2.micro"
  key_name      = "my-key"

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("my-key.pem")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo yum install -y nginx",
      "sudo systemctl start nginx"
    ]
  }
}
```

## ❌ PROBLEMS WITH PROVISIONERS

| Issue           | Problem            |
| --------------- | ------------------ |
| Not idempotent  | Repeat run me fail |
| SSH dependency  | Network issue      |
| Partial failure | State inconsistent |
| Hard to debug   | Logs weak          |

---

# 🔴 USER DATA vs PROVISIONERS (CLEAR)

| Feature      | User Data  | Provisioner           |
| ------------ | ---------- | --------------------- |
| Runs         | First boot | After resource create |
| Recommended  | ✅ YES      | ❌ NO                  |
| Cloud-native | ✅          | ❌                     |
| Reliable     | ✅          | ❌                     |
| Idempotent   | ✅          | ❌                     |

> **Server ke andar ka kaam = User Data**
> **Terraform ke bahar ka kaam = Provisioner**

✔ User Data → Bootstrap server
✔ Ansible → Advanced config
✔ No provisioners in production

# ✅ SOLUTION: TERRAFORM WORKSPACES

## 🧠 Workspace kya hota hai?

👉 Workspace = **same Terraform code + different state**

Terraform internally karta hai:

```
terraform.tfstate.d/
├── dev/terraform.tfstate
├── staging/terraform.tfstate
└── prod/terraform.tfstate
```

👉 Code same
👉 State alag
👉 Environment isolated

---

## 🔥 One-line definition (Interview Ready)

> **Terraform workspace allows managing multiple environments using the same configuration by maintaining separate state files.**

---

# 🧩 REAL USE CASE EXAMPLE

## 🎯 Goal:

Same EC2 resource:

* Dev → t2.micro
* Staging → t2.small
* Prod → t3.medium

---

# 🟢 STEP 1: Base Terraform Code

### main.tf

```hcl
provider "aws" {
  region = "ap-south-1"
}

locals {
  instance_type = {
    dev     = "t2.micro"
    staging = "t2.small"
    prod    = "t3.medium"
  }
}

resource "aws_instance" "app" {
  ami           = "ami-0f5ee92e2d63afc18"
  instance_type = local.instance_type[terraform.workspace]

  tags = {
    Name        = "app-${terraform.workspace}"
    Environment = terraform.workspace
  }
}
```

---

## 🔍 KEY LINE:

```hcl
terraform.workspace
```

👉 Automatically batata hai:

```
dev / staging / prod
```

---

# 🟢 STEP 2: Workspace Commands

### Check current workspace

```bash
terraform workspace show
```

Output:

```
default
```

---

### Create workspaces

```bash
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod
```

---

### List workspaces

```bash
terraform workspace list
```

Output:

```
* default
  dev
  staging
  prod
```

---

### Switch workspace

```bash
terraform workspace select dev
```

---

# 🟢 STEP 3: Apply per Environment

### Dev

```bash
terraform workspace select dev
terraform apply
```

👉 Creates:

```
EC2 → t2.micro
Name → app-dev
```

---

### Staging

```bash
terraform workspace select staging
terraform apply
```

👉 Creates:

```
EC2 → t2.small
Name → app-staging
```

---

### Prod

```bash
terraform workspace select prod
terraform apply
```

👉 Creates:

```
EC2 → t3.medium
Name → app-prod
```

# 🧠 VISUAL UNDERSTANDING

| Workspace | State File                  | EC2 Type  |
| --------- | --------------------------- | --------- |
| dev       | terraform.tfstate.d/dev     | t2.micro  |
| staging   | terraform.tfstate.d/staging | t2.small  |
| prod      | terraform.tfstate.d/prod    | t3.medium |

```text
module "ec2"
```

---

# 🏗️ STEP 1: MODULE BANANA (Slow & Simple)

## 📁 Folder structure (IMPORTANT)

```text
project/
│
├── main.tf          ← main/root file (yahin se call hota hai)
│
└── modules/
    └── ec2/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

Socho:

* `modules/ec2` = **EC2 banane ki factory**

---

## 🔹 modules/ec2/variables.tf

👉 Module ko kya-kya input chahiye?

```hcl
variable "ami" {}
variable "instance_type" {}
variable "name" {}
```

Matlab:

> “Jo bhi mujhe use karega, wo mujhe ye values dega”

---

## 🔹 modules/ec2/main.tf

👉 Actual EC2 creation logic

```hcl
resource "aws_instance" "this" {
  ami           = var.ami
  instance_type = var.instance_type

  tags = {
    Name = var.name
  }
}
```

👉 **Yahin EC2 ban raha hai**

---

## 🔹 modules/ec2/outputs.tf

👉 Module se kya return karna hai

```hcl
output "public_ip" {
  value = aws_instance.this.public_ip
}
```

Jaise function return karta hai.
