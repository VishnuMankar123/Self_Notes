# 🎯 Interview Questions (Part 1)

### Q1. What is Helm?

**Answer:** Helm is the package manager for Kubernetes. It helps install, upgrade, uninstall, and manage Kubernetes applications.

---

### Q2. Why do we need Helm?

**Answer:** Helm removes the need to manually manage multiple Kubernetes YAML files and automates installation, upgrades, and configuration.

---

### Q3. Is Helm similar to APT?

**Answer:** Yes. Just as APT manages packages in Ubuntu, Helm manages application packages in Kubernetes.

---

### Q4. Can we install applications without Helm?

**Answer:** Yes, using `kubectl apply`, but it becomes difficult to manage many YAML files, dependencies, and versions in real projects.

---

### Q5. Name four things Helm can do.

**Answer:** Install, Upgrade, Uninstall, and Package Kubernetes applications.

---

### ⭐ Part 1 Revision (5-Minute Recap)

* **Helm = Package Manager for Kubernetes**
* **APT : Ubuntu :: Helm : Kubernetes**
* Helm helps **Install**, **Upgrade**, **Uninstall**, and **Package** applications.
* It reduces manual YAML management.
* It automatically handles deployment order and dependencies.
* In real companies, Helm is commonly used to deploy tools like **Prometheus**, **Grafana**, **Argo CD**, and internal microservices.

# 🎯 Interview Questions (Part 2A)

### Q1. Where do we install Helm?

**Answer:** Helm v3 is installed only on the client machine (local laptop/server). Nothing is installed inside the Kubernetes cluster.

---

### Q2. What was Tiller?

**Answer:** Tiller was the server-side component used in Helm v2 to communicate with the Kubernetes cluster.

---

### Q3. Why was Tiller removed?

**Answer:** Because it introduced security and maintenance issues. Helm v3 communicates directly with the Kubernetes API.

---

### Q4. How does Helm connect to Kubernetes?

**Answer:** Helm uses the same **kubeconfig** file and **current context** that `kubectl` uses.

---

### Q5. Which file does Helm use to identify the target cluster?

**Answer:** The **kubeconfig** file.

---

### Q6. How does Helm know which cluster to deploy to?

**Answer:** It reads the **current context** from the kubeconfig file.

---

## ⭐ 5-Minute Revision

* **Helm v3** is installed only on the **local machine**.
* **Helm v2** required **Tiller** inside the cluster.
* **Tiller** was removed in Helm v3 for better security and simplicity.
* Helm uses the **same kubeconfig** as `kubectl`.
* The **current context** decides which Kubernetes cluster Helm will operate on.
* Helm is **not a replacement for kubectl**; it builds on top of the Kubernetes API to manage complete applications.

* **Helm v3** runs on the client machine and uses the same **kubeconfig** as `kubectl`.
* Always verify Helm installation with **`helm version`**.

# ⭐ 5-Minute Revision

* **Repository** stores multiple **Charts**.
* A **Chart** is a package containing Kubernetes manifests like Deployment, Service, ConfigMap, Secret, etc.
* A **Release** is a deployed instance of a Chart.
* One Chart can have multiple Releases (e.g., `prod-nginx`, `qa-nginx`, `dev-nginx`).
* In `helm install my-nginx bitnami/nginx`:

  * `my-nginx` = **Release**
  * `bitnami` = **Repository**
  * `nginx` = **Chart**

# ⭐ 5-Minute Revision

* Use `helm create <chart-name>` to generate a new Helm Chart.
* `Chart.yaml` contains chart metadata such as name, version, and appVersion.
* `templates/` stores Kubernetes manifests like Deployment and Service.
* `values.yaml` provides configurable values that templates use.
* `charts/` is used for dependent Helm Charts.
* A single template can be reused across Dev, QA, and Production by changing only `values.yaml`.

* **values.yaml** → Configuration values (replicas, image, ports, resources, etc.).
* **templates/** → Kubernetes YAML templates (Deployment, Service, ConfigMap, Secret, Ingress).
* **charts/** → Dependency charts (optional).

# ⭐ 5-Minute Revision

* Create one Helm Chart per microservice (e.g., Payment, Shipping).
* `helm create` generates the initial chart structure.
* Put Kubernetes manifests in `templates/`.
* Replace hardcoded values with `{{ .Values... }}` placeholders.
* Store environment-specific settings in `values.yaml`.
* `Chart.yaml` contains chart metadata like `appVersion`.
* The same template can deploy to Dev, QA, and Production by changing only `values.yaml`.

* Use `helm repo index .` to generate `index.yaml`.
* `index.yaml` helps Helm discover available Charts in a repository.

## 👨‍🎓 Student

> **Helm is the package manager for Kubernetes. It helps us package, install, upgrade, rollback, and uninstall Kubernetes applications. A Helm Repository stores multiple Charts, and a Chart is a packaged Kubernetes application containing manifests like Deployment, Service, ConfigMap, and Secret. When we install a Chart, it becomes a Release. Helm uses templates and values.yaml to make deployments configurable across Dev, QA, and Production environments. We can package Charts using `helm package`, publish them to repositories like Nexus or Artifactory, and deploy them using commands such as `helm repo add`, `helm search`, and `helm install`. This simplifies Kubernetes application deployment and version management.**
