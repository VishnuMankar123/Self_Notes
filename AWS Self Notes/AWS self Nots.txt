---

### 🧠 What it means

**Client-Server Architecture** is a model where two parts work together:

* **Client** → asks for something
* **Server** → gives the answer

---

### 🖥️ Real-life example

Think of it like a **restaurant** 🍽️

| Role             | In Real Life             | In Computing                           |
| ---------------- | ------------------------ | -------------------------------------- |
| Customer         | You place an order       | **Client** (e.g., your browser or app) |
| Waiter + Kitchen | Prepares and serves food | **Server** (handles and sends data)    |

---

### ⚙️ How it works (steps)

1. **Client sends a request** → “I want this data/page.”
2. **Server receives it** → Checks what’s needed.
3. **Server processes** → Runs code, queries database.
4. **Server sends a response** → Sends result back.
5. **Client displays** → Shows result to the user.

---

### 💡 Example

You open a website like `www.google.com`

1. Your browser (client) → sends request to Google’s server.
2. Google’s server → processes and sends search page back.
3. Browser → shows it on your screen.

---

### 🔗 Common examples

* **Web apps**: Browser (client) ↔ Web server
* **Mobile apps**: App (client) ↔ API server
* **Games**: Player app (client) ↔ Game server

---

### 🧩 Types

1. **Two-tier architecture** → Client ↔ Server
2. **Three-tier architecture** → Client ↔ Application Server ↔ Database Server

---

### ✅ Advantages

* Centralized data & control
* Easy to maintain & secure
* Multiple clients can connect

### ❌ Disadvantages

* If the server fails, everyone is affected
* Network dependency

# One-Tier (Single-Tier) Architecture

**Kya hai:**
Sab kuch ek hi system/instance mein hota hai — presentation, business logic, aur data sab ek jagah pe.

**Kaise work karta hai:**

* Application aur data dono ek hi machine ya process mein run karte hain.
* No network communication between layers because layers aren’t separated.

**Example:**

* A simple desktop app (e.g., a standalone calculator, a single-user MS Access file with forms and tables).
* A local-only utility where user interface and data store are in the same program.

**Diagram (simple):**

```
[Client + App + Database]  —> (Single machine/process)
```

**Pros:**

* Very simple to build and deploy
* Low latency (no network calls)
* Good for single-user or prototype apps

**Cons:**

* Not scalable — can’t handle many users
* Hard to maintain as app grows
* Less secure and less modular

## 🧩 **Types of Client–Server Architecture**

### 🥇 1. **Two-Tier Architecture**

➡️ **Client ↔ Server**

**How it works:**

* Client directly talks to the server.
* Server handles both **business logic** and **database**.

**Example:**
A desktop app (like an old banking software) directly connecting to the database server.

**Diagram:**

```
Client  ⇄  Server (App + Database)
```

**Pros:** Simple, fast for small systems
**Cons:** Not scalable, difficult to maintain for large apps

---

### 🥈 2. **Three-Tier Architecture**

➡️ **Client ↔ Application Server ↔ Database Server**

**How it works:**

* Client sends request to **Application Server**
* Application Server processes logic, fetches data from **Database Server**
* Sends result back to client

**Example:**
Modern web applications —
Browser → (Client)
Spring Boot or Node.js → (App Server)
MySQL / Oracle → (DB Server)

**Diagram:**

```
Client ⇄ Application Server ⇄ Database Server
```

**Pros:**
✅ Scalable
✅ Secure (database not directly exposed)
✅ Easy to maintain

**Cons:**
⚠️ Slightly complex setup

---

### 🥉 3. **N-Tier Architecture (Multi-Tier)**

➡️ **Client ↔ Web Server ↔ App Server ↔ DB Server ↔ Other Services**

**How it works:**

* Used in **large enterprise systems**.
* Multiple layers handle different responsibilities (like API layer, business logic, database, caching, etc.).

**Example:**
E-commerce site like Amazon —
Client → Web Server → App Server → Database + Payment + Logging

**Diagram:**

```
Client ⇄ Web Server ⇄ App Server ⇄ Database ⇄ Other Services
```

**Pros:**
✅ Very scalable
✅ Secure & modular
✅ Easy to add or change parts

**Cons:**
⚠️ High cost and complexity

## 🧠 **Loopback Address (127.0.0.1)** — Simple Explanation

### 🔹 Definition:

**Loopback address** ek **special IP address** hota hai jo **apne hi computer ko refer karta hai**.
Matlab:

> Jab aap apne computer se apne computer ko hi request bhejte ho.

---

### 🔹 Default Loopback Address:

```
127.0.0.1
```

and hostname:

```
localhost
```

Dono ka meaning same hai.

---

### 💡 Example:

Agar aap browser me likho:

```
http://127.0.0.1:8080
```

ya

```
http://localhost:8080
```

👉 Toh aapka browser **aapke hi system par chal rahe server** (like Tomcat, Spring Boot, etc.) se connect karega.

---

### 🔹 Use:

1. **Testing purpose** –
   Local web servers (Tomcat, XAMPP, Node.js) ko test karne ke liye.

2. **Network configuration check** –
   Ping command se check karte hain ki TCP/IP stack sahi chal raha hai ya nahi.

   ```
   ping 127.0.0.1
   ```

   Agar reply aata hai → network stack working fine.

3. **Local communication** –
   Apps ek hi computer ke andar data exchange karne ke liye loopback ka use karti hain.

---

### 🔹 Important Points:

* Yeh packets **kabhi network par nahi jaate** — sirf system ke andar circulate hote hain.
* Range: `127.0.0.0 – 127.255.255.255` (sab loopback ke liye reserve hai).
* Commonly used: `127.0.0.1`

---

Jaise tum khud se baat karte ho ("main khudse practice kar raha hoon") —
waise hi **loopback** me computer apne aap se baat karta hai 🖥️➡️🖥️

## 🔹 **Concept 1 – DNS क्या करता है**

**Teacher:**
DNS का काम है → “Domain Name” को “IP Address” में बदलना।

**Example:**

```
www.google.com  ➜  142.250.190.78
```

इंसानों को नाम याद रखना आसान है, लेकिन कंप्यूटर सिर्फ IP address समझते हैं।
DNS दोनों के बीच translator का काम करता है।

---

## 🔹 **Concept 2 – जब आप Browser में कोई Website खोलते हैं तो क्या होता है**

**Teacher:**
चलो step by step समझते हैं कि जब आप browser में `www.google.com` लिखते हैं तो background में क्या-क्या होता है 👇

---

### 🟩 Step 1: Browser Cache Check

* Browser सबसे पहले अपने **local cache** में चेक करता है कि क्या उस domain का IP पहले से मौजूद है।
* अगर मिला → वही IP use कर लेता है।
* अगर नहीं मिला → अगला step।

---

### 🟨 Step 2: OS Cache Check

* Browser फिर **Operating System (DNS Cache Table)** में check करता है।
* अगर नहीं मिला → आगे बढ़ता है।

---

### 🟦 Step 3: Router/Local DNS Check

* अब request जाती है आपके **Router** या **Local DNS Server** तक।
* अगर वहाँ भी नहीं मिला → request भेजी जाती है आपके ISP के DNS Resolver को।

---

### 🟧 Step 4: Recursive DNS Resolver (ISP DNS)

* यह आपका **Internet Service Provider (Jio, Airtel आदि)** का DNS होता है।
* इसे कहते हैं **Recursive Resolver**, क्योंकि यह बाकी servers से recursively जवाब ढूंढता है।

---

### 🟥 Step 5: Root DNS Server

* अगर ISP के पास IP नहीं है, तो यह **Root DNS Server** से पूछता है।
* Root server actual IP नहीं बताता — वह बताता है कि उस domain का TLD server कौन-सा है।
* Root servers दुनिया में केवल **13 logical sets (A–M)** हैं।

---

### 🟪 Step 6: TLD (Top Level Domain) Server

* Root server `.com`, `.org`, `.in` जैसे extensions के लिए TLD server का path देता है।
* अब resolver उस **TLD server** से पूछता है कि यह domain कहाँ hosted है।

**Example:**
`.com` server कहेगा → “google.com का authoritative server है ns1.google.com।”

---

### 🟫 Step 7: Authoritative Name Server

* अब resolver उस authoritative server से पूछता है — “google.com का actual IP बताओ।”
* Authoritative server actual IP देता है जैसे `142.250.190.78`।
* यही final जवाब होता है।

---

### ⬛ Step 8: Response to Browser

* यह IP अब resolver → system → browser को वापस भेजी जाती है।
* Browser इस IP को cache कर लेता है (next time fast access के लिए)।
* फिर browser TCP/IP connection बनाता है और web page लोड हो जाता है ✅

---

## 🔹 **Concept 5 – DNS Load Balancer कैसे काम करता है**

**Teacher:**
जब किसी domain के पीछे कई servers होते हैं (high traffic sites),
तो DNS एक ही domain के लिए **multiple IP addresses** देता है।
इससे load अलग-अलग servers पर divide हो जाता है।

---

### ⚙️ Common DNS Load Balancing Algorithms

| Algorithm     | Description                                             |
| ------------- | ------------------------------------------------------- |
| Round Robin   | हर request को अलग server पर भेजता है (sequence में)     |
| Geo-based     | User के location के पास वाले server पर भेजता है         |
| Latency-based | जो server सबसे fast response दे रहा हो, उसी पर भेजता है |
| Weighted      | Priority के हिसाब से servers को traffic देता है         |

---

### 🧩 **Example: Round Robin Load Balancing**

| Client | DNS Response (IP) | Server Selected   |
| ------ | ----------------- | ----------------- |
| User A | 10.0.0.1          | Server 1          |
| User B | 10.0.0.2          | Server 2          |
| User C | 10.0.0.3          | Server 3          |
| User D | 10.0.0.1          | Server 1 (repeat) |

👉 इससे load बराबर बंट जाता है और कोई server overload नहीं होता।

## **1️⃣ TCP (Transmission Control Protocol)**

**Key Features:**

1. **Reliable delivery:**

   * TCP ensure karta hai ki **sab packets sahi order me aur loss ke bina** receiver tak pahunch jaaye.
   * Agar koi packet lost ho jaye, to TCP automatically **resend** karta hai.

2. **Connection-oriented:**

   * Sender aur receiver ke beech **connection establish** hota hai pehle (3-way handshake).
   * Jaise phone call start karte ho, dono ready hain baat karne ke liye.

3. **Error checking & flow control:**

   * Agar data me error ho → TCP detect karke **request karta hai resend**
   * Flow control se sender ka data receiver ko overwhelm nahi karta.

**Analogy:**

* TCP = **Registered Post / Courier Service**

  * Letter guaranteed deliver hoga, agar lost ho to resend hoga, aur sab letters order me pahunchenge.

**Use Cases:**

* Web browsing → **HTTP/HTTPS**
* Email → **SMTP, IMAP, POP3**
* File transfer → **FTP**

---

## **2️⃣ UDP (User Datagram Protocol)**

**Key Features:**

1. **Faster delivery:**

   * UDP **connection nahi banata**, simply packet bhej deta hai.
   * Error checking aur resend ka kaam nahi karta → speed fast.

2. **Connectionless:**

   * Sender aur receiver ke beech pehle se connection establish nahi hota.
   * Jaise aap ek postcard bhejte ho, direct receiver ko.

3. **Less reliable:**

   * Agar packet lost ho gaya → **koi automatic resend nahi**.
   * Order guarantee bhi nahi hai.

**Analogy:**

* UDP = **Postcard / WhatsApp message**

  * Jaldi bheja jaata hai, lekin agar lost ho gaya, firse bhejna **aapko khud karna padega**.

**Use Cases:**

* Video/Audio streaming → **YouTube, Netflix**
* Online gaming → **fast updates, minor packet loss acceptable**
* DNS queries → **fast request-response**

---

**Summary Table:**

| Feature        | TCP                 | UDP                    |
| -------------- | ------------------- | ---------------------- |
| Delivery       | Reliable            | Unreliable             |
| Connection     | Connection-oriented | Connectionless         |
| Speed          | Slower              | Faster                 |
| Error Handling | Yes, resend         | No                     |
| Use Case       | Web, Email, FTP     | Streaming, Gaming, DNS |

---

## **1️⃣ TCP (Transmission Control Protocol)**

* **Type:** Transport Layer Protocol
* **Function:**

  * Data ko **reliable aur ordered** delivery ensure karta hai.
  * Error checking aur retransmission ka kaam karta hai.
* **Connection:** Connection-oriented (pehle handshake hota hai)
* **Example Use:** HTTP, FTP, Email
* **Analogy:** Courier service – sab parcels order me aur safe deliver hote hain.

---

## **2️⃣ IP (Internet Protocol)**

* **Type:** Internet Layer Protocol
* **Function:**

  * Data packets ko **logical addressing (IP address)** aur **routing** provide karta hai.
  * Decide karta hai ki packet **kaunse path se destination tak jaayega**.
* **Connection:** Connectionless (bina handshake ke packet bhejta hai)
* **Example Use:** IP packet delivery across networks
* **Analogy:** Road network / GPS – packet ko destination tak pahunchata hai, lekin delivery ki guarantee nahi deta.

---

## **Key Differences (Simple Table)**

| Feature    | TCP                            | IP                             |
| ---------- | ------------------------------ | ------------------------------ |
| Layer      | Transport                      | Internet                       |
| Delivery   | Reliable, ordered              | Unreliable, no order guarantee |
| Connection | Connection-oriented            | Connectionless                 |
| Function   | Data delivery & error checking | Packet addressing & routing    |
| Analogy    | Courier service                | Road / GPS system              |

---

💡 **Important:**

* TCP aur IP aksar **TCP/IP** ke form me saath me use hote hain.
* IP packet ko **destination tak pahunchata hai**, TCP ensure karta hai ki **data sahi aur complete mile**.

### 💻 **3. Parts of a URL**

Parts breakdown:
1️⃣ **Protocol** → https
2️⃣ **Host name / Domain name** → [www.neraclasses](http://www.neraclasses)
3️⃣ **Top-level domain (TLD)** → .in
4️⃣ **Port number** → :443 (optional if using default port)
5️⃣ **Path** → /page1
6️⃣ **Query separator** → ?
7️⃣ **Query string** → course=network
8️⃣ **Fragment** → #section2

**👨‍🎓 Student Notes:**
🧾 URL = Protocol + Domain + TLD + Port + Path + Query + Fragment
⚙️ Default Ports:

* HTTP → 80
* HTTPS → 443

📌 Port number optional for default ports.

### 🔐 **4. Protocols – HTTP vs HTTPS**

**👨‍🏫 Teacher:**

* **HTTP (HyperText Transfer Protocol)**

  * Port 80
  * Plain text communication
  * Not encrypted → vulnerable to hackers
* **HTTPS (HTTP Secure)**

  * Port 443
  * Uses SSL/TLS encryption
  * Secure communication between client ↔ server

**👨‍🎓 Student Notes:**

| Protocol | Port | Security     | Encryption |
| -------- | ---- | ------------ | ---------- |
| HTTP     | 80   | ❌ Not secure | No         |
| HTTPS    | 443  | ✅ Secure     | SSL/TLS    |

🔒 HTTPS = Secure, encrypted communication between browser & website.

### 🌍 **5. Internet Protocol (IP)**

**👨‍🏫 Teacher:**

* IP = Method to send data from one computer to another over the Internet.
* Uses **IP address** to locate destination machine.
* Similar to home address or phone number concept.
* Data is converted into **binary (electronic signals)** before transmission.
* Used with communication models like TCP/IP.

**👨‍🎓 Student Notes:**
🧠 IP (Internet Protocol):

* Transfers data packets between devices.
* Needs receiver’s IP address.
* Converts data → binary → sends over network.

### 🧱 **6. TCP/IP Model – Layers**

**👨‍🏫 Teacher:**
TCP/IP model adopted in **1983** (ARPANET standard).
It has **4 layers**:
1️⃣ **Application Layer** – User interaction (HTTP, FTP, SMTP).
2️⃣ **Transport Layer** – Data delivery control (TCP, UDP).
3️⃣ **Internet Layer** – Logical addressing & routing (IP, ICMP).
4️⃣ **Network Access Layer** – Physical network (Ethernet, Wi-Fi).

Data Flow (Sender → Receiver):

* Sender: App → Transport → Internet → Network
* Receiver: Network → Internet → Transport → App

**👨‍🎓 Student Notes:**
📘 **TCP/IP Model Layers**

| Layer          | Function                     | Example Protocols |
| -------------- | ---------------------------- | ----------------- |
| Application    | User-level communication     | HTTP, SMTP, FTP   |
| Transport      | Reliable/unreliable delivery | TCP, UDP          |
| Internet       | Routing, addressing          | IP, ICMP          |
| Network Access | Physical transmission        | Ethernet, Wi-Fi   |

📡 Sender → (App→Trans→Net→Phys)
Receiver → (Phys→Net→Trans→App)

### 🔁 **7. TCP vs UDP**

**👨‍🏫 Teacher:**

* **TCP (Transmission Control Protocol)** – Reliable, connection-oriented.
* **UDP (User Datagram Protocol)** – Faster, connectionless, less reliable.

**👨‍🎓 Student Notes:**

| Feature     | TCP        | UDP               |
| ----------- | ---------- | ----------------- |
| Connection  | Oriented   | Connectionless    |
| Reliability | Reliable   | Unreliable        |
| Speed       | Slower     | Faster            |
| Use Case    | Web, Email | Streaming, Gaming |

## **1️⃣ Application Layer**

**Function:**

* Ye layer **user aur application programs** ke beech communication ka kaam karti hai.
* Ye data ko aise format me prepare karti hai jo **network par bhejne ke liye ready** ho.
* Directly **end-user interact** karte hain (browser, email client).

**Example Protocols & Use:**

| Protocol       | Purpose                                                                     |
| -------------- | --------------------------------------------------------------------------- |
| **HTTP/HTTPS** | Web browsing; HTTPS encrypted version of HTTP                               |
| **FTP**        | File transfer between client and server                                     |
| **SMTP**       | Sending emails                                                              |
| **POP3/IMAP**  | Receiving emails                                                            |
| **DNS**        | Domain name resolution (e.g., [www.google.com](http://www.google.com) → IP) |

**Analogy:** Ye layer **office receptionist** jaisi hai jo request samajhkar proper department ko forward karta hai.

---

## **2️⃣ Transport Layer**

**Function:**

* Ye layer **data ko segments me todta hai** aur reliable delivery ensure karta hai.
* **Error checking, flow control, congestion control** ka kaam bhi karta hai.
* Sender aur receiver ke beech **end-to-end communication** maintain karta hai.

**Example Protocols & Use:**

| Protocol                                | Features                                                                          |
| --------------------------------------- | --------------------------------------------------------------------------------- |
| **TCP (Transmission Control Protocol)** | Reliable, connection-oriented, ensures all packets arrive in order                |
| **UDP (User Datagram Protocol)**        | Unreliable, connectionless, faster, used for streaming, DNS queries, online games |

**Analogy:** Ye layer **post office** jaisi hai jo letters ko sahi address pe deliver karne ki responsibility leta hai, aur agar letter lost ho jaye to resend karta hai (TCP).

---

## **3️⃣ Internet Layer**

**Function:**

* Ye layer **logical addressing** aur **routing** ka kaam karti hai.
* Ye decide karti hai **data ka kaunsa path lena hai sender → receiver tak**.
* Packet ko **source IP se destination IP** tak bhejna iska kaam hai.

**Example Protocols & Use:**

| Protocol                                     | Features                                    |
| -------------------------------------------- | ------------------------------------------- |
| **IP (Internet Protocol)**                   | Addressing & routing; IPv4 or IPv6          |
| **ICMP (Internet Control Message Protocol)** | Error reporting, e.g., ping command         |
| **ARP (Address Resolution Protocol)**        | Maps IP addresses to physical MAC addresses |

**Analogy:** Ye layer **GPS navigator** jaisi hai jo decide karti hai kaunsa route follow karna hai destination tak pahunchne ke liye.

---

## **4️⃣ Network Access Layer** (Link Layer / Physical Layer)

**Function:**

* Ye layer **physical transmission** ka kaam karti hai: cables, switches, Wi-Fi signals.
* Data ko **frames** me convert karke **actual network hardware** se bhejti hai.

**Example Protocols & Use:**

| Protocol/Technology               | Purpose                             |
| --------------------------------- | ----------------------------------- |
| **Ethernet**                      | Wired LAN connection                |
| **Wi-Fi (IEEE 802.11)**           | Wireless LAN connection             |
| **PPP (Point-to-Point Protocol)** | Direct connection over serial links |
| **Frame Relay, ATM**              | WAN transmission protocols          |

**Analogy:** Ye layer **delivery truck / courier service** jaisi hai jo actual physical delivery karta hai.

---

## **📡 Data Flow Example**

**Sender:**
Application → Transport → Internet → Network Access → Physical Media → Receiver

**Receiver:**
Physical Media → Network Access → Internet → Transport → Application

**Example:**

* Aap browser me `www.google.com` type karte ho.

1. **Application Layer:** Browser request prepare karta hai → HTTP GET request
2. **Transport Layer:** TCP segment me divide karke error checking lagata hai
3. **Internet Layer:** Packet ko IP address ke through route karta hai
4. **Network Layer:** Ethernet/Wi-Fi se actual physical network par send karta hai

Receiver ke side me ye process reverse hota hai → finally aapko Google page milta hai.

## 🧠 OSI Model — Short Notes (From Nehra Classes Lecture)

### 📌 Full Form:

**OSI → Open System Interconnection Model**
→ Framework for communication between two devices over a network.

---

### 🏗️ Layers in OSI Model (Total 7)

+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| Layer No. | Layer Name          | Type                          | Main Function                                                                               |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 7         | Application Layer   | Software                      | User interface to access network (e.g., browsers like Chrome, Firefox). Uses HTTP, HTTPS,   |
|           |                     |                               | FTP, SMTP protocols.                                                                        |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 6         | Presentation Layer  | Software                      | Performs data translation, compression, and encryption/decryption. Converts human-readable  |
|           |                     |                               | data into binary form.                                                                      |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 5         | Session Layer       | Software                      | Manages sessions — create, maintain, and terminate communication. Adds checkpoints for      |
|           |                     |                               | error recovery.                                                                             |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 4         | Transport Layer     | Middle Layer (Heart of OSI)   | Ensures reliable data delivery using TCP (connection-oriented) or UDP (connectionless).     |
|           |                     |                               | Divides data into segments, handles flow control & error correction.                        |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 3         | Network Layer       | Hardware                      | Responsible for routing packets using IP addresses. Chooses the best path to send data.     |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 2         | Data Link Layer     | Hardware                      | Manages error detection and correction during physical transmission. Uses MAC addresses.    |
|           |                     |                               | Divides data into frames.                                                                   |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+
| 1         | Physical Layer      | Hardware                      | Transfers raw bits over the physical medium (cables, signals, voltages). Deals with actual  |
|           |                     |                               | hardware.                                                                                   |
+-----------+---------------------+-------------------------------+---------------------------------------------------------------------------------------------+


### ⚙️ Classification of Layers:

* **Software Layers:** Application (7), Presentation (6), Session (5)
* **Hardware Layers:** Network (3), Data Link (2), Physical (1)
* **Bridge Layer:** Transport (4)

---

### 🕓 History:

* Introduced: **1983**
* Adopted by **ISO (International Standards Organization)** in **1984**

---

### 📍 Key Points:

* OSI model is **advanced and detailed** compared to TCP/IP model.
* Helps standardize data communication globally.
* Provides **uniformity** and **error-free data transfer**.
* **Transport Layer** is called the **heart** of OSI model.
* Works from **Application → Physical** (Sender side) and reverse on **Receiver side**.

➡️ Local file storage

➡️ Company website (small-scale)

**Server Room Features:**

* छोटा area (जैसे एक कमरा)
* Limited servers & cooling
* Single organization के लिए
* Maintenance manually होती है

## 🏗️ **Cloud Computing कैसे काम करता है**

### 🔹 Step-by-Step Process:

1. **User Request करता है**

   * तुम किसी cloud service provider (जैसे AWS, Azure, Google Cloud) को request भेजते हो।
2. **Service Provider allocate करता है resources**

   * Cloud में virtual servers (VMs), storage, database allocate हो जाते हैं।
3. **Internet के ज़रिए access करते हो**

   * तुम किसी भी device से (mobile, laptop, browser) access कर सकते हो।
4. **Pay-as-you-go model**

   * जितना use किया, उतना pay किया — no maintenance, no hardware tension।

### **Cloud Service Models - Q&A Notes**

**Teacher:** Cloud computing me cloud service models kya hote hain?
**Student:** Cloud service models basically teen categories me hote hain:

1. **IaaS (Infrastructure as a Service)**
2. **PaaS (Platform as a Service)**
3. **SaaS (Software as a Service)**

---

**Teacher:** IaaS kya hota hai?
**Student:** IaaS me cloud provider aapko **hardware resources** provide karta hai jaise ki:

* CPU
* RAM
* Storage
* Networking devices
* Virtualization tools

Aap in resources ko use karke **apni virtual machine (VM)** deploy kar sakte ho. Yahan **operating system aur applications ko manage karna aapki responsibility hoti hai**.

**Example:** AWS me **EC2 (Elastic Compute Cloud)** service IaaS ka example hai.

---

**Teacher:** PaaS kya hota hai? IaaS se difference kya hai?
**Student:** PaaS me aapko **hardware + operating system** dono provide kiye jaate hain cloud provider se.

* Infrastructure to cloud provider ka hai
* Operating system bhi cloud provider ka hai
* Aapko sirf apni **applications aur data** manage karna hota hai

**Difference:** IaaS me aap apna khud ka OS choose karke manage kar sakte ho, PaaS me OS cloud provider ka hi hota hai aur aapko manage karne ki zarurat nahi.

**Example:** AWS me **Elastic Beanstalk** PaaS ka example hai, jahan aap apni application deploy kar sakte ho without worrying about OS.

---

**Teacher:** SaaS kya hota hai?
**Student:** SaaS me **hardware, OS, platform, applications sab cloud provider manage karta hai**.

* Aapko sirf application use karna hota hai
* Aapko kuch bhi manage nahi karna

**Examples:**

* CRM software
* ERP systems
* Email marketing software
* Accounting software

---

**Teacher:** On-premises infrastructure kya hota hai?
**Student:** On-premises me:

* Hardware, OS, middleware, data, applications sab **aapki company manage karti hai**
* Aapko apne server, storage, network sab khud setup aur maintain karna padta hai
* Cost aur operational efforts zyada hote hain

**Example:** Agar aap business ke liye ek ERP application run karna chahte ho, to aapko apna **data center setup** karna padega.

**Teacher:** On-premises vs cloud?
**Student:** Cloud adopt karne ka main reason hai:

* **Cost saving** (pay-as-you-go model)
* **No team required for managing infrastructure**
* **Flexibility**

**Example:** Car analogy:

* On-premises = Apni car kharidna, petrol, maintenance, driver sab aap manage karte ho
* Cloud = Taxi hire karna, sirf distance ka paisa dena, sab responsibility taxi company ki

---

**Teacher:** Shared responsibility model kya hai?
**Student:**

* Cloud me kuch resources **cloud provider manage karta hai**, kuch **customer manage karta hai**
* IaaS: Provider = networking, storage, servers, virtualization
  Customer = OS, middleware, applications, data
* PaaS: Provider = hardware + OS + runtime
  Customer = applications + data
* SaaS: Provider = sab manage karega
  Customer = sirf use karega

---

**Teacher:** AWS me IaaS ka example kya hai?
**Student:** **EC2 (Elastic Compute Cloud)**

* Virtual machines ko **instances** kehte hain
* AWS Management Console se instances launch aur manage kar sakte ho
* OS aur application aap manage karte ho

**Teacher:** PaaS ka AWS example?
**Student:** **Elastic Beanstalk**

* Application deploy karna easy
* OS aur platform ko cloud provider manage karta hai

**Teacher:** SaaS ka AWS example?
**Student:** ERP systems, CRM software jo AWS provide karta hai, jise aap **directly use kar sakte ho**

---

**Teacher:** Cloud ke advantages kya hain?
**Student:**

* **Cost-effective**
* **Flexible aur scalable**
* **No need for separate teams**
* **Quick deployment**

**Teacher:** Cloud ke layers ka virtualization diagram samjhao?
**Student:**

1. Hardware → Cloud provider manage karta hai
2. Firmware/Hypervisor → Virtual hardware create karta hai
3. Virtual machines → Customer deploy karta hai apna OS + apps
4. Applications aur data → Customer manage karta hai (IaaS/PaaS)
5. SaaS me sab provider manage karega

---

**Teacher:** AWS console me kaun kaun si services important hain?
**Student:**

* **EC2** → Virtual machines
* **S3** → Storage
* **VPC** → Networking
* **Elastic Beanstalk** → Platform for apps
* Aur bhi bahut saari services, jo practical me use hoti hain

### **AWS EC2 & Cloud Scaling Q&A Notes**

**Teacher:** Namaste! Aaj hum baat karenge **Elasticity** aur **Scalability** ke baare me. Pehle batao, Elasticity kya hoti hai?
**Student:** Elasticity ka matlab hai system ya infrastructure ki **ability** ki woh apne resources ko **auto-adjust kar sake demand ke hisaab se**. Jaise traffic badhe, toh resources automatically increase ho jayein aur traffic kam ho toh decrease ho jaye.

**Teacher:** AWS me Elasticity ka use kaise hota hai?
**Student:** AWS me Elasticity ka matlab hai ki **servers ka number demand ke hisaab se increase ya decrease hota hai**, **server capacity ko nahi badhate**. Yeh mostly **short-term** ke liye hota hai.

**Teacher:** Example do Elasticity ka.
**Student:** Maan lo humari application pe initially **1 server** hai, traffic bahut kam hai. Ab holiday me traffic increase ho jaye, toh **AWS automatically ek ya do aur servers add kar dega** (scale-out) aur traffic kam hone pe servers remove kar dega (scale-in).

**Teacher:** Scale-out aur scale-in kya hota hai?
**Student:**

* **Scale-out:** Jab workload ya traffic badhta hai, toh **additional servers add karna** → zyada users ko handle kar sake.
* **Scale-in:** Jab workload ya traffic kam hota hai, toh **servers ko remove karna** → unnecessary cost save hoti hai.
* Ye dono **auto-scaling** ke through hote hain aur **shutdown/reboot ki zarurat nahi hoti**.

**Teacher:** Auto-scaling kya hai?
**Student:** Auto-scaling ek AWS feature hai jo:

1. **Monitor karta hai traffic aur resources usage**
2. **Decides karta hai kitne servers chahiye**
3. **Automatically add ya remove karta hai servers**
   Isse humari app ki **performance stable** rehti hai aur **cost bhi low** rehti hai.

**Teacher:** Ab batao **Scalability** kya hoti hai?
**Student:** Scalability ka matlab hai **system resources ko increase ya decrease karna** jaise **CPU, RAM, Storage** ko scale up ya down karna.

* Yeh **long-term solution** hota hai
* Example: Database server pe 32GB RAM aur 12 vCPU hai, traffic badh gaya → hum **server ki RAM 64GB aur CPU 16 kar dete** hain.

**Teacher:** Elasticity aur Scalability me difference kya hai?
**Student:**

| Feature     | Elasticity                            | Scalability                                    |
| ----------- | ------------------------------------- | ---------------------------------------------- |
| Purpose     | Short-term demand adjust              | Long-term performance adjust                   |
| Adjust      | Number of servers                     | Server capacity (CPU/RAM/Storage)              |
| Example     | Extra server add during traffic spike | Database server RAM increase for growing users |
| AWS Feature | Auto-scaling                          | Vertical scaling                               |

**Teacher:** Horizontal aur Vertical Scaling me kya difference hai?
**Student:**

* **Horizontal Scaling (Scale-out/In):** **Number of servers change** hota hai, same capacity ke servers add/remove hote hain.

  * Example: 1 server → 3 servers during traffic spike
* **Vertical Scaling (Scale-up/Down):** **Server ki capacity change** hoti hai, CPU/RAM/Storage badhaya ya kam kiya jata hai.

  * Example: 32GB RAM → 64GB RAM

**Teacher:** Elasticity me Horizontal ya Vertical scaling hoti hai?
**Student:** Elasticity me **horizontal scaling** hoti hai, kyunki **number of servers auto-adjust hota hai**.

**Teacher:** Scalability me Horizontal ya Vertical scaling hoti hai?
**Student:** Scalability me **vertical scaling** hoti hai, kyunki **server capacity increase ya decrease hoti hai**.

**Teacher:** Ek simple scenario do Elasticity ka.
**Student:**

* Maan lo website pe initially **2 servers** hai
* Holiday ke din traffic badh gaya → Auto-scaling se **2 extra servers add**
* Traffic kam hua → **Extra 2 servers remove**
* User ko service interruption nahi hua

**Teacher:** Ek simple scenario do Scalability ka.
**Student:**

* Database server pe 32GB RAM hai, queries slow ho rahi hain
* Server ko **power-off karke RAM 64GB aur CPU 16** kar diya
* Server restart → application fast ho gayi
* Yaha **server count same raha, capacity badhi**

**Teacher:** Key terms yaad rakhne layak kya hain?
**Student:**

* **Elasticity** = Auto-adjust number of servers (short-term)
* **Scalability** = Increase/decrease server capacity (long-term)
* **Auto-scaling** = Elasticity achieve karne ka AWS feature
* **Scale-out** = Add servers
* **Scale-in** = Remove servers
* **Vertical Scaling** = Increase server capacity (CPU/RAM/Storage)
* **Horizontal Scaling** = Add/remove servers

---

✅ **Summary Tip:**

* Elasticity → Short-term → Horizontal → Number of servers
* Scalability → Long-term → Vertical → Server capacity
* Auto-scaling → AWS ka magic tool jo elasticity provide karta hai

## 👨‍🏫 **Teacher Explanation: Regions in Cloud Computing**

### 🔹 What is a Region?

* Cloud providers (AWS, Azure, GCP) duniya ke alag–alag areas me **data centers ke groups** banate hain.
* Har group ko **Region** kaha jata hai.
* Ek Region me kai **Availability Zones (AZs)** hote hain.

---

### 🔹 Distance Between Regions

* Regions **alag–alag cities ya countries** me hote hain.
* Distance region ke location pe depend karta hai, lekin average:

  * **Minimum:** ~500 km (same country ke regions)
  * **Maximum:** 10,000+ km (different continents ke regions)

| Example          | Region 1            | Region 2                    | Distance (Approx.) |
| ---------------- | ------------------- | --------------------------- | ------------------ |
| AWS ap-south-1   | Mumbai              | ap-southeast-1 (Singapore)  | ~3,900 km          |
| AWS us-east-1    | Virginia (USA)      | us-west-1 (California, USA) | ~3,700 km          |
| AWS eu-central-1 | Frankfurt (Germany) | ap-southeast-2 (Sydney)     | ~16,000 km         |

---

### 🔹 Why Regions Are Far Apart?

1. **Disaster recovery** – Agar ek region me flood, fire, ya power issue ho to doosra safe rahe.
2. **Latency optimization** – User ke nearest region se fast response milta hai.
3. **Data compliance** – Countries ke data laws ke hisaab se data local rehna chahiye (e.g., India data India me).

---

## 👨‍🎓 **Student Notes:**

📘 **Cloud Region**

* Data centers ka geographical group.
* Har region independent hota hai (apna power, cooling, network).
* Multiple **zones** hote hain ek region ke andar.

📏 **Distance:**

* 500 km – 10,000 km tak ho sakta hai (country aur continent pe depend karta hai).

📦 **Examples:**

* `ap-south-1` → Mumbai
* `ap-southeast-1` → Singapore
* `us-east-1` → Virginia

📡 **Purpose:**

* Disaster recovery
* Latency reduce karna
* Legal compliance maintain karna

## 📘 **Concept 1 – Data Center क्या होता है**

### 🧑‍🏫 Explanation:

Data Center एक **physical building** होता है जिसमें हज़ारों servers, routers, cooling systems, और power backup systems होते हैं।
यहीं पर Cloud के सारे data और applications store किए जाते हैं।

**Example:**
अगर आप Amazon EC2 instance बनाते हो, तो असल में वो किसी AWS Data Center में run होता है।

### 💡 Key Points:

* Data Center = Physical infrastructure (hardware, cooling, electricity)
* इसमें कई racks और servers होते हैं
* 24×7 बिजली, cooling, और internet backup होता है
* AWS के हर Data Center में **redundancy** (backup power + internet) मौजूद होती है

---

## 📘 **Concept 2 – Availability Zone (AZ) क्या होती है**

### 🧑‍🏫 Explanation:

Availability Zone एक **Region के अंदर मौजूद independent location** होती है जिसमें **एक या एक से ज़्यादा Data Centers** होते हैं।

हर AZ को इस तरह design किया गया है कि अगर एक Zone fail हो जाए (जैसे बिजली कट जाए या network down हो जाए)
तो दूसरा Zone automatically काम करे।

### 💡 Example:

AWS Mumbai Region (`ap-south-1`) में 3 Availability Zones हैं:

* `ap-south-1a`
* `ap-south-1b`
* `ap-south-1c`

अगर `1a` down हो जाए, तो traffic `1b` या `1c` पर redirect हो जाता है।

---

## 📘 **Concept 3 – Region क्या होता है**

### 🧑‍🏫 Explanation:

**Region** एक **geographical area** होता है जिसमें कई Availability Zones (AZs) होती हैं।
हर Region का अपना infrastructure, data laws, और pricing होता है।

### 💡 Example:

| Region Name              | Code         | Availability Zones |
| ------------------------ | ------------ | ------------------ |
| US East (N. Virginia)    | `us-east-1`  | 6 AZs              |
| Asia Pacific (Mumbai)    | `ap-south-1` | 3 AZs              |
| Asia Pacific (Hyderabad) | `ap-south-2` | 3 AZs              |

---

## 📘 **Concept 4 – Relationship Between Region, AZ, and Data Center**

### 🧑‍🏫 Hierarchy Diagram:

```
AWS Cloud
 ├── Region (e.g., ap-south-1 → Mumbai)
 │     ├── Availability Zone (ap-south-1a, 1b, 1c)
 │     │     ├── Data Center(s)
 │     │     │     ├── Physical Servers
```

👉 मतलब:

* Region = Group of AZs
* AZ = Group of Data Centers
* Data Center = Group of Servers

* Route 53, EC2, and S3 resources are Region-based.

### AWS Services Introduction | Q&A Notes

**Teacher:** AWS की सर्विसेस को हम कैसे categorize कर सकते हैं?
**Student:** AWS की सर्विसेस को तीन कैटेगरी में बांटा गया है:

1. **Zonal Services (जोनल सर्विसेस)** – केवल एक **Availability Zone (AZ)** में उपलब्ध होती हैं। उदाहरण: **Subnet**।
2. **Regional Services (रीजनल सर्विसेस)** – एक रीजन के कई AZs में उपलब्ध होती हैं। उदाहरण: **EC2, ELB, VPC, Elastic Beanstalk**।
3. **Global Services (ग्लोबल सर्विसेस)** – कई रीजन में उपलब्ध होती हैं। उदाहरण: **IAM, Route 53, CloudFront**।

---

**Teacher:** Zonal, Regional और Global services में फर्क क्या है?
**Student:**

* **Zonal:** केवल एक AZ में उपयोग हो सकती हैं।
* **Regional:** पूरे रीजन में, यानी एक से ज्यादा AZs में उपयोग हो सकती हैं।
* **Global:** एक से ज्यादा रीजन में उपलब्ध होती हैं।

---

**Teacher:** EC2 क्या है और इसका उपयोग कैसे करते हैं?
**Student:**

* **EC2 (Elastic Compute Cloud)** एक **रीजनल सर्विस** है।
* इसमें **Virtual Machine (VM) = Instance** बनाते हैं।
* आप रीजन और AZ चुनकर **instances launch** कर सकते हैं।
* EC2 में आपको **OS configuration, software installation, firewall setup** आदि खुद करना होता है।

---

**Teacher:** ELB क्या है?
**Student:**

* **ELB (Elastic Load Balancer)** एक **रीजनल सर्विस** है।
* Incoming traffic को **multiple EC2 instances** में distribute करता है।
* **Elastic** इसलिए क्योंकि इसमें **auto-scaling** का support होता है।
* Scale Out → Instances बढ़ाना, Scale In → Instances कम करना।

---

**Teacher:** Elastic Beanstalk क्या है और कैसे काम करता है?
**Student:**

* **Elastic Beanstalk (PaaS)** आपको **applications deploy करने की सुविधा** देता है।
* Infrastructure का **operational burden** AWS खुद manage करता है।
* आप सिर्फ **code upload** करते हैं, Beanstalk automatically servers, databases, load balancers और scaling setup करता है।
* यह भी **रीजनल सर्विस** है।

---

**Teacher:** EC2 और Elastic Beanstalk में फर्क क्या है?
**Student:**

| Feature             | EC2                                             | Elastic Beanstalk                        |
| ------------------- | ----------------------------------------------- | ---------------------------------------- |
| Control over server | High, आप खुद configure करते हैं                 | Low, AWS manage करता है                  |
| Setup complexity    | High, OS और environment configure करना पड़ता है | Low, बस code upload करना होता है         |
| Scaling             | Manual setup or ELB needed                      | Auto-scaling built-in                    |
| Target user         | DevOps/Server knowledge required                | Developers जो code deploy करना चाहते हैं |

---

**Teacher:** Lightsail क्या है?
**Student:**

* **Lightsail** एक simple **VPS** service है।
* Pre-installed tools और applications (WordPress, cPanel, Joomla आदि) के साथ आती है।
* **Easy to use**, लेकिन **auto-scaling नहीं है**।
* यह भी **रीजनल सर्विस** है।

---

**Teacher:** AWS Lambda क्या है?
**Student:**

* **Lambda** एक **serverless computing platform** है।
* आप **code run कर सकते हैं बिना server manage किए**।
* **Events** (जैसे S3 upload, scheduled task) के response में code execute होता है।
* Lambda भी **रीजनल सर्विस** है।
* उदाहरण:

  * S3 में picture upload → Lambda automatically resize कर दे।
  * EC2 instance stop होने पर → Lambda auto-restart कर दे।

---

**Teacher:** Lambda और EventBridge कैसे काम करते हैं?
**Student:**

* **EventBridge** events capture करता है।
* Lambda उन events के response में code execute करता है।
* Supports **event-driven automation** और **scheduled tasks**।

---

**Teacher:** AWS की सर्विसेस summary?
**Student:**

1. **EC2** → Virtual Machines, रीजनल।
2. **ELB** → Load balancing, रीजनल।
3. **Elastic Beanstalk** → Application deployment, PaaS, रीजनल।
4. **Lightsail** → Easy VPS, रीजनल, pre-installed apps।
5. **Lambda** → Serverless functions, रीजनल, event-driven।

## ⚙️ **Amazon EBS (Elastic Block Store) — Kya Hai?**

**Amazon EBS** ek **block storage service** hai jo **EC2 instances** ke liye use hoti hai.
Iska matlab — ye **virtual hard disk** jaisa kaam karti hai jo aapke **EC2 (virtual machine)** ke sath attach hoti hai.

---

### 🧠 **Simple Definition:**

> **EBS** ek **persistent block storage** hai jo **Amazon EC2** instances ko data store karne ke liye disk ke roop me milta hai.

---

## 💡 **Example Samajhiye:**

Agar aapne **EC2 instance** launch kiya (jaise ek Linux server),
to us server ko apne files, database, application data store karne ke liye **hard disk** chahiye hoti hai.
Wahi **EBS volume** hota hai.

📘 Example:

* EC2 Instance = Computer (CPU + RAM)
* EBS Volume = Hard Disk (Storage)

---

## 🔹 **EBS Ki Key Features:**

| Feature               | Description                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------- |
| **Block Storage**     | Data blocks ke form me store hota hai (like local disk).                                    |
| **Persistent**        | Instance band hone ke baad bhi data delete nahi hota (jab tak aap manually na delete karo). |
| **Attach/Detach**     | Aap volume ko kisi bhi EC2 instance ke sath attach ya detach kar sakte ho.                  |
| **Scalable**          | Size badha ya ghata sakte ho bina data lose kiye.                                           |
| **Backup (Snapshot)** | Aapka data ka backup Amazon S3 me snapshot ke roop me store hota hai.                       |
| **Encrypted Storage** | Data-at-rest aur data-in-transit dono encrypted hota hai.                                   |

---

## 🧩 **EBS Volume Types:**

| Type                               | Description                 | Use Case                      |
| ---------------------------------- | --------------------------- | ----------------------------- |
| **gp3 (General Purpose SSD)**      | Balanced performance & cost | Boot volumes, small databases |
| **io2 (Provisioned IOPS SSD)**     | High performance (IOPS)     | Databases like Oracle, MySQL  |
| **st1 (Throughput Optimized HDD)** | Sequential data ke liye     | Big data, log processing      |
| **sc1 (Cold HDD)**                 | Low-cost, infrequent access | Archive data, backup          |

---

## 🪣 **EBS vs S3 (Difference Table):**

| Feature          | **EBS**                   | **S3**                       |
| ---------------- | ------------------------- | ---------------------------- |
| **Storage Type** | Block Storage             | Object Storage               |
| **Attach To**    | EC2 Instance              | Internet accessible          |
| **Persistence**  | Tied to specific instance | Independent                  |
| **Performance**  | High I/O speed            | Slower (API-based access)    |
| **Use Case**     | OS, database, app files   | Backups, media, static files |

---

## 📘 **EBS Snapshot:**

* EBS volumes ka backup **Snapshot** ke form me **S3** me store hota hai.
* Snapshot se aap **naya volume restore** kar sakte ho.

📙 Command Example:

```bash
aws ec2 create-snapshot --volume-id vol-0abcd1234efgh5678 --description "My backup"
```

---

## 🎯 **EBS Ka Use Kis Liye Karte Hain:**

| Use Case                                            | Description                              |
| --------------------------------------------------- | ---------------------------------------- |
| **EC2 instance ka OS aur data store karne ke liye** | Boot volume ke roop me                   |
| **Database storage**                                | MySQL, PostgreSQL, Oracle, MongoDB, etc. |
| **File system storage**                             | Application data, logs                   |
| **Backup & Restore**                                | Snapshots ke zariye                      |
| **High-performance workloads**                      | Low-latency I/O tasks ke liye            |

---

## 🧠 **In Short:**

> **Amazon EBS** ek **virtual hard disk** hai jo **EC2 instances** ke liye high-performance, persistent, aur secure block storage provide karti hai.

## 🎯 **Session 13 – AWS Storage Services (EFS, Snow Family, S3 Glacier)**

### 🔹 भाग 1 – EFS (Elastic File System)

**Q1. AWS EFS क्या है?**
EFS यानी **Elastic File System** — AWS की एक **serverless, scalable, managed file storage service** है।
यह एक ही डेटा को **multiple EC2 instances** पर एक साथ शेयर करने की सुविधा देता है।

**Q2. EBS की limitation क्या थी?**
EBS को एक समय में केवल एक EC2 instance से attach किया जा सकता है।
भले ही “multi-attach” फीचर है, पर वह भी अधिकतम 16 instances तक सीमित है और block-level पर काम करता है।

**Q3. EFS क्यों जरूरी है?**
क्योंकि यह **file-level storage** देता है और एक ही समय पर **हजारों EC2 instances** को access करने की अनुमति देता है।

**Q4. EFS की खासियतें क्या हैं?**

* Serverless (कोई manual provisioning नहीं)
* Auto scaling – डेटा के अनुसार size बढ़ता/घटता है
* Encrypted & Secure
* Concurrent file access
* AWS Managed Service
* Multi-AZ (Regional Service)
* NFS v4 protocol पर काम करता है

**Q5. EFS किस use-case में helpful है?**
जब एक ही डेटा को **कई सर्वर या एप्लिकेशन** को एक साथ access करना हो — जैसे shared configuration files या web content।

**Q6. EFS regional क्यों कहलाता है?**
क्योंकि यह **multi-AZ** में data store करता है और पूरे region में accessible होता है, जबकि EBS केवल एक AZ तक सीमित है।

---

### 🔹 भाग 2 – AWS Snow Family

**Q7. AWS Snow Family क्या है?**
यह **physical storage devices** का collection है जिसका उपयोग **large-scale data transfer** (on-premises ↔ cloud) के लिए किया जाता है।
जब internet bandwidth कम हो या cost ज़्यादा हो तो Snow devices से data physically move किया जाता है।

**Q8. Snow Family में कौन-कौन सी services आती हैं?**

1. **AWS Snowcone** – छोटी device (~8 TB), portable, edge computing के लिए।
2. **AWS Snowball Edge** – medium-size device (40–80 TB), large data transfer के लिए।
3. **AWS Snowmobile** – बहुत बड़ी truck-size device (100 PB तक), पूरे data center migration के लिए।

**Q9. Snow devices की खास बातें क्या हैं?**

* Highly secure (256-bit encryption)
* Tamper-proof
* Portable (airplane impact सह सकते हैं)
* Offline data transfer possible
* Edge computing support

**Q10. Snow Family कब use करते हैं?**
जब –

* Internet slow या unavailable हो
* Data बहुत बड़ा (TB–PB level) हो
* Remote/isolated location हो
* पूरा data center migrate करना हो
* Disaster recovery setup करना हो

---

### 🔹 भाग 3 – AWS S3 Glacier

**Q11. AWS S3 Glacier क्या है?**
यह AWS की **archival storage service** है — यानी पुराने या rarely accessed data को **कम cost** में store करने के लिए।
Backup, long-term retention, और compliance data के लिए perfect है।

**Q12. Glacier के storage classes कौन से हैं?**

1. **S3 Glacier Instant Retrieval** – तुरंत access (millisecond), थोड़ा महँगा।
2. **S3 Glacier Flexible Retrieval** – कुछ मिनट से घंटे में access, कम cost।
3. **S3 Glacier Deep Archive** – 12 घंटे में restore, सबसे सस्ता।

**Q13. Glacier कहाँ useful है?**

* Backup data
* Long-term archives (years)
* Legal/compliance data
* Rarely accessed files

### 🔹 Summary Comparison Table

| Feature / Service | **EBS**                         | **EFS**             | **S3 Glacier**         | **AWS Snow Family**  |
| ----------------- | ------------------------------- | ------------------- | ---------------------- | -------------------- |
| Storage Type      | Block-level                     | File-level          | Object-level (Archive) | Physical device      |
| Access Type       | One EC2 (Multi-attach up to 16) | Many EC2s           | Rare access            | Offline transfer     |
| Scalability       | Manual                          | Auto                | Auto                   | Physical capacity    |
| Use Case          | OS, DB                          | Shared file storage | Backup/Archive         | Large data migration |
| Connectivity      | AZ-based                        | Regional (Multi-AZ) | Internet               | Offline/Physical     |

## 🧩 **1️⃣ EBS vs EFS vs Glacier vs Snow — Real-life Examples के साथ**

---

### 🟢 **EBS (Elastic Block Store)** — “Laptop की Hard Disk” जैसा है 💽

**सोचो:**
तुम्हारे लैपटॉप में एक **Hard Disk (SSD)** लगी है।
वह सिर्फ **उस लैपटॉप से जुड़ी** होती है।
अगर तुम उसे किसी दूसरे लैपटॉप में लगाना चाहो — manually करना पड़ेगा।

**ऐसे ही AWS में:**

* **EBS** एक **Block Storage** है (Hard Disk जैसा)।
* एक समय में सिर्फ **एक EC2 instance** से जुड़ सकता है।
* Performance बहुत fast होती है (जैसे OS या Database के लिए)।
* अगर EC2 बंद हो जाए तो Disk का data safe रहता है।

🧠 **Example:**
मान लो तुम्हारा EC2 server एक Database चला रहा है (MySQL)।
उसका data एक EBS volume पर stored है।
जब तुम EC2 बंद करते हो — data delete नहीं होता क्योंकि वो disk (EBS) अलग से मौजूद रहती है।

---

### 🔵 **EFS (Elastic File System)** — “Google Drive” या “Network Shared Folder” जैसा है 📁

**सोचो:**
कंपनी में एक shared network drive है — जैसे
“Z:\SharedDocs”
जहाँ से सभी employees एक साथ file खोल सकते हैं, edit कर सकते हैं।

**ऐसे ही AWS में:**

* **EFS** एक **File Storage** है।
* एक ही data को **multiple EC2 servers** एक साथ access कर सकते हैं।
* यह **auto-scale** होता है — तुम्हारे data के size के हिसाब से अपने-आप बढ़ता या घटता है।
* AWS इसके पीछे storage manage करता है (serverless है)।

🧠 **Example:**
मान लो तुम्हारे पास 10 EC2 web servers हैं जो एक ही web application चला रहे हैं।
तुम्हारे static files (images, config files, CSS, etc.) सबको common चाहिए।
तो तुम EFS बनाओगे और सब servers में mount कर दोगे।
अब कोई भी server file update करे — बाकी सबको भी वही change दिखेगा।

🔹 **Comparison:**

* EBS → Single user (like your laptop HDD)
* EFS → Multi-user shared folder (like office shared drive)

---

### 🟣 **AWS Snow Family** — “Data Courier Truck” जैसा है 🚚

**सोचो:**
तुम्हारे पास बहुत सारा data (10 TB या 100 TB) है,
और तुम्हारा Internet बहुत slow है — upload करने में महीनों लग जाएंगे।
तो तुम क्या करोगे?

AWS कहता है — “भेज दो physical device से।”

**Snow Family वही करता है:**

* AWS तुम्हें एक **device भेजता है (Snowcone/Snowball/Snowmobile)**
* तुम अपने data को उसमें copy कर देते हो
* फिर device को AWS को वापस भेज देते हो
* AWS तुम्हारा data अपने data center में upload कर देता है

🧠 **Example:**

* 10 TB data है — तो **Snowball Edge** मंगवाओ
* Copy करो → Ship करो → AWS upload कर देगा
* 100 PB (Petabyte) data है — तो **Snowmobile (Truck)** भेजते हैं!

🔹 **Comparison:**

* Internet के बजाय **Physical courier way** से data transfer होता है
* Useful जब bandwidth कम हो या data बहुत बड़ा हो

---

### 🟠 **S3 Glacier** — “Old Data Storage Locker” जैसा है 📦

**सोचो:**
तुम्हारे घर में पुराने files, bills, या certificates हैं जो साल में एक बार ही काम आते हैं।
तुम उन्हें bank locker में रख देते हो —
क्योंकि वो **safe** रहते हैं और रोज़ access करने की ज़रूरत नहीं।

**ऐसे ही AWS में:**

* **S3 Glacier** वही “locker” है cloud में।
* यह **archival storage** है — rarely used data के लिए।
* Access slow होता है (कुछ मिनट से घंटे लगते हैं)
* लेकिन cost बहुत सस्ती है।

🧠 **Example:**
तुम्हें किसी company के **10 साल पुराने invoices** या **backup logs** रखने हैं (legal requirement)।
उन्हें Glacier में डाल दो — safe रहेंगे, कम खर्च आएगा, और जरूरत पड़े तो restore कर लो।

## 🧩 **1️⃣ AWS Snow Family क्या करती है (Quick Recap)**

AWS Snow Family का काम है –
**"बहुत बड़े डेटा को AWS Cloud में या AWS से बाहर ट्रांसफर करना"**
जब internet से upload/download करना बहुत slow या महँगा पड़ जाए।

इस family में तीन members होते हैं 👇

| Device            | Capacity  | Use                        |
| ----------------- | --------- | -------------------------- |
| **Snowcone**      | ~8 TB     | Small data, Edge computing |
| **Snowball Edge** | 40–80 TB  | Medium data transfer       |
| **Snowmobile**    | 100 PB तक | पूरा Data Center migration |

## ⚙️ **2️⃣ AWS Snow Family Workflow – Step-by-Step**

नीचे पूरा workflow 6 simple steps में है 👇

---

### 🟢 **Step 1 – Job Creation in AWS Console**

सबसे पहले user (या admin) AWS Console में जाकर **Snow Job** बनाता है।

➡️ वहाँ आपको चुनना होता है:

* कौन सा device चाहिए (Snowcone, Snowball, Snowmobile)
* Source data कहाँ से आएगा (on-premises servers, NAS, etc.)
* Destination (S3 bucket)
* Encryption key (KMS key)
* Shipping address

🧠 **Example:**
तुम्हारे पास 50 TB logs हैं जिन्हें S3 में डालना है → तो तुम **Snowball Edge** चुनोगे।

---

### 🟢 **Step 2 – Device Shipping by AWS**

AWS उसी region के data center से तुम्हें physical device courier करता है।

* Device पहले से ही **encrypted** और **tamper-proof** होता है।
* AWS device को track करने के लिए **AWS OpsHub software** provide करता है।

---

### 🟢 **Step 3 – Data Copying (Local Upload)**

जब device तुम्हारे पास आता है 👇

1. उसे power on करो
2. Laptop/Server से connect करो
3. **AWS OpsHub software** या **CLI commands** से device में data copy करो
4. Device internally data को **AES-256 encryption** से encrypt करता है

📘 **Tech details:**

* File system automatically manage होता है
* Edge computing possible है (Snowball Edge पर EC2 instances भी चल सकते हैं)
* Connectivity: Ethernet या Wi-Fi (Snowcone)

🧠 **Example:**
तुम अपने local NAS से 50 TB logs को copy करते हो → Snowball Edge पर।

---

### 🟢 **Step 4 – Device Return to AWS**

Data upload पूरा होने के बाद:

* Device को securely shut down करो
* AWS को वापस courier कर दो
* Shipment track कर सकते हो AWS Console से

Device में data encrypted होता है, इसलिए कोई बीच में data नहीं पढ़ सकता।

---

### 🟢 **Step 5 – Data Upload to S3 (by AWS)**

जब AWS को device वापस मिल जाता है:

1. AWS device को अपने **import facility** में connect करता है
2. Device के अंदर का encrypted data decrypt करके
   तुम्हारे चुने हुए **S3 bucket** में upload कर देता है
3. Upload complete होने पर device को sanitize (data delete) किया जाता है

📘 **Internal Layer:**

* Device से data → AWS import servers → S3 buckets
* AWS logs maintain करता है (CloudWatch / Snow job status)

---

### 🟢 **Step 6 – Verification & Job Completion**

जब upload पूरा हो जाता है:

* तुम्हें **notification** मिलती है (email या console)
* तुम S3 bucket में अपने data को verify कर सकते हो
* Device का data AWS permanently erase कर देता है (secure wipe)

---

```
     ┌────────────────────────────────────┐
     │          AWS Snow Family           │
     └────────────────────────────────────┘

        ▼ Step 1: Create Job in AWS Console
              ↓
        AWS prepares encrypted Snow device
              ↓
        ▼ Step 2: Device shipped to customer
              ↓
        ▼ Step 3: Customer copies data to device
            (via OpsHub / CLI)
              ↓
        ▼ Step 4: Customer ships device back to AWS
              ↓

              ↓

```

### 🧩 **Session 14 – AWS Database Services (Amazon RDS Introduction)**

🎓 *By: Nehra Classes | Trainer: Vikas Nehra*

---

#### 🧠 **1. Database क्या होता है?**

**Teacher:** Database क्या है?
**Student:** Database एक **structured collection of data** होता है जिसे इस तरह organize और store किया जाता है कि डेटा को efficiently **retrieve, manage और manipulate** किया जा सके।

**Example:**
Employee details वाली टेबल जिसमें ID, Name, Salary आदि stored हों — यह एक database table का हिस्सा है।

---

#### 🧩 **2. DBMS क्या है?**

**Teacher:** DBMS (Database Management System) क्या करता है?
**Student:** DBMS एक software है जो database के साथ interact करने की सुविधा देता है। इससे हम data को:

* Create
* Retrieve
* Modify
* Manage
  कर सकते हैं, साथ ही **security और integrity** बनाए रखते हैं।

---

#### 🧮 **3. RDBMS क्या है?**

**Teacher:** Relational Database क्या होता है?
**Student:** RDBMS में data **tables (rows और columns)** के रूप में store किया जाता है, और टेबल्स के बीच **relationships** बनाए जाते हैं (जैसे primary key, foreign key)।
**Example:** MySQL, PostgreSQL, Oracle, SQL Server आदि।

---

#### 💬 **4. SQL क्या है?**

**Teacher:** SQL का use क्या है?
**Student:** SQL (Structured Query Language) एक standard language है जो relational databases के साथ **query, update और structure define** करने के लिए उपयोग होती है।

---

#### ⚙️ **5. Normalization क्या है?**

**Student:** Normalization एक process है जिससे data को इस तरह organize किया जाता है कि redundancy (duplicate data) और dependency कम हो, जिससे database efficient बनता है।

---

#### 🔍 **6. Indexes क्या करते हैं?**

**Student:** जैसे किताब में Index हमें जल्दी page तक पहुंचाता है, वैसे ही database में Index data retrieval को **fast** करता है।

---

#### ⚔️ **7. DBMS vs RDBMS Difference**

| Feature       | DBMS              | RDBMS                      |
| ------------- | ----------------- | -------------------------- |
| Structure     | Files-based       | Tables (rows/columns)      |
| Relationships | नहीं enforce करता | Enforce करता (keys के साथ) |
| Normalization | Optional          | Mandatory                  |
| Examples      | MS Access         | MySQL, Oracle, SQL Server  |

---

#### 🏗️ **8. Physical Database Server की Problems**

**Teacher:** Traditional (on-premise) database servers में क्या दिक्कतें हैं?
**Student:**

* Hardware failure (CPU, RAM, HDD issues)
* Scalability problem (resources बढ़ाना कठिन)
* Maintenance downtime
* Power & cooling issues
* Space requirement
* High cost (hardware + license + maintenance)
* Backup, recovery, security सब खुद manage करना
* Limited redundancy (high availability मुश्किल)

---

#### ☁️ **9. Cloud क्यों बेहतर है?**

**Teacher:** Cloud databases को क्यों prefer किया जाता है?
**Student:**
क्योंकि Cloud databases (जैसे AWS RDS) में:

* High availability
* Scalability
* Low maintenance
* Automatic backup
* Cost efficiency
* Disaster recovery
* Security और performance बेहतर होती है।

---

#### 🌐 **10. AWS Database Services Overview**

**AWS में Database Services:**

1. **RDS (Relational Database Service)** – Managed relational DB.
2. **DynamoDB** – NoSQL database.
3. **Elasticache** – In-memory cache.
4. **Redshift** – Data warehousing service.

---

#### 🧱 **11. Amazon RDS क्या है?**

**Teacher:** RDS क्या है — Database या Service?
**Student:** RDS एक **database नहीं** है, यह एक **managed database service** है जो AWS पर relational databases को **setup, operate और scale** करने की सुविधा देती है।

**RDS Features:**

* AWS खुद database instance manage करता है
* User को infrastructure manage करने की जरूरत नहीं
* Focus सिर्फ application logic पर रह सकता है

---

#### 💡 **12. RDS कौन-कौन से Database Engines को Support करता है?**

| Database Engine | Owner                                            |
| --------------- | ------------------------------------------------ |
| MySQL           | Open Source                                      |
| PostgreSQL      | Open Source                                      |
| Oracle          | Oracle Corporation                               |
| SQL Server      | Microsoft                                        |
| MariaDB         | Open Source                                      |
| Amazon Aurora   | AWS (proprietary, MySQL & PostgreSQL compatible) |

---

#### 🧭 **13. RDS के Benefits**

* Fully managed (no manual maintenance)
* Automatic backup & recovery
* High availability (Multi-AZ)
* Easy scaling
* Cost-effective pay-as-you-go model
* Secure (encryption & IAM integration)

---

### ✅ **Summary Notes**

* **Database** = structured data collection
* **DBMS** = software to manage databases
* **RDBMS** = relational model (tables, keys)
* **SQL** = language for database operations
* **Normalization & Indexing** = improve efficiency
* **AWS RDS** = managed relational database service
* **Supports 6 Engines:** MySQL, PostgreSQL, Oracle, SQL Server, MariaDB, Aurora
* **Solves:** hardware, scaling, maintenance & cost issues of traditional servers

## 🧾 **AWS IAM Service – Getting Started with IAM Users & Groups**

### 🎯 **Objective:**

To understand and perform basic IAM (Identity and Access Management) operations — creating **Users**, **Groups**, and assigning **Permissions** in AWS.

---

### 🧠 **Concept Summary**

* **IAM (Identity and Access Management)** is an AWS service used to **securely control access** to AWS resources.
* With IAM, you can **create users, groups, and roles**, and assign permissions using **policies**.
* It’s a **global service** (not region-specific).
* IAM ensures **least privilege principle** — give only the permissions required.

---

### 🧩 **Step-by-Step Practical**

#### 🪪 **1. Open AWS IAM Console**

* Go to AWS Console → Search **IAM** → Open the IAM Dashboard.
* Left side menu shows options: Users, Groups, Roles, Policies.

---

#### 👥 **2. Create IAM User**

1. Click **Users → Add user**
2. Enter username (e.g., `developer1`)
3. Select **Access type**:

   * ✅ *AWS Management Console access* (for GUI login)
   * ✅ *Programmatic access* (for CLI / SDK)
4. Set a custom password (e.g., `Dev@1234`)
5. Choose **Require password reset** (optional)
6. Click **Next** to set permissions.

---

#### 👨‍👩‍👦 **3. Create IAM Group**

1. Go to **Groups → Create group**
2. Name it (e.g., `Developers`)
3. Attach a policy:

   * Example: **AmazonS3FullAccess** or **EC2ReadOnlyAccess**
4. Click **Create group**
5. Now add your user (`developer1`) into this group.

---

#### 🔑 **4. Assign Permissions to User or Group**

* If user is part of a group → permissions are inherited from the group.
* Alternatively, attach a policy directly to the user.

Example:

* Policy name: `AmazonEC2FullAccess`
* Effect: Allow
* Action: All EC2 actions
* Resource: All resources

---

#### 🧾 **5. Test the Access**

1. Sign out of the root account.
2. Login using the new IAM user credentials.
3. Try accessing allowed and restricted services — verify permission boundaries.

---

### 💻 **6. Optional: Access Keys (for CLI)**

If programmatic access was chosen:

* Go to IAM → Users → Select user → **Security credentials** → Create Access key
* Use these in AWS CLI:

  ```bash
  aws configure
  AWS Access Key ID [None]: AKIAxxxxxxx
  AWS Secret Access Key [None]: XXXXXXXXXXXXX
  Default region name [None]: ap-south-1
  Default output format [None]: json
  ```

---

### 🧾 **Output / Result**

✅ IAM User `developer1` created successfully.
✅ IAM Group `Developers` created with attached policy.
✅ User inherits permissions from the group and can access allowed services only.

---

### ⚙️ **Key Points**

* Root account should not be used for daily operations.
* Always create IAM users for team members.
* IAM is **Global**, not tied to a region.
* Use **Policies** to define what actions are allowed/denied.
* Follow **Principle of Least Privilege**.

---

### ❌ **Common Errors & Fixes**

| Error                 | Cause                    | Solution                               |
| --------------------- | ------------------------ | -------------------------------------- |
| “Access Denied”       | Missing permission       | Attach required policy                 |
| “User cannot login”   | Console access not given | Enable “AWS Management Console Access” |
| “Invalid credentials” | Wrong username/password  | Reset from IAM console                 |

## 🔹 **IAM Role क्या होता है (What is a Role in AWS IAM)?**

**👉 Simple Definition:**
IAM Role एक **temporary permission identity** है जिसे **AWS services या users** adopt करते हैं ताकि वो कुछ specific actions perform कर सकें — **बिना permanent credentials** के।

---

### 💡 **Example से समझो:**

मान लो तुम्हारे पास एक **EC2 instance** है, और तुम्हें उस EC2 को **S3 bucket access** देना है।

❌ तुम ऐसा नहीं कर सकते कि EC2 में S3 के लिए Access Key और Secret Key डाल दो — क्योंकि ये **insecure** तरीका है।

✅ इसके बजाय तुम एक **IAM Role** बनाते हो जिसमें **S3 access की permission** होती है,
और फिर उस role को EC2 instance से attach कर देते हो।

अब EC2 instance **securely और automatically** S3 access कर सकता है, बिना किसी key के।

---

## 🔹 **Main Features of IAM Roles:**

| Feature                       | Description                                                           |
| ----------------------------- | --------------------------------------------------------------------- |
| **Temporary credentials**     | Roles credentials short-lived होते हैं                                |
| **No password / access key**  | Role login नहीं करता, सिर्फ assume किया जाता है                       |
| **Used by AWS services**      | जैसे EC2, Lambda, ECS, Glue, etc.                                     |
| **Cross-account access**      | एक AWS account का user दूसरे account में access पा सकता है (via role) |
| **Least privilege principle** | Roles से हम सिर्फ उतनी ही permission देते हैं जितनी जरूरत है          |

## 🔸 **Answer:**

IAM **Roles** उन situations में काम करते हैं जहाँ **AWS resources (services)** को **temporarily दूसरे resources** तक पहुँच चाहिए — बिना username-password या access keys के।

मतलब, **Roles services पर काम करते हैं, users पर नहीं।**
(Users के पास permanent credentials होते हैं, Roles के पास temporary credentials होते हैं।)

## 🧩 **Roles kis par kaam karte hain (Where Roles Work):**

| Sr. | AWS Service / Entity                  | Role का Purpose                                                                                              |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 1️⃣ | **EC2 Instance**                      | EC2 को S3, DynamoDB या CloudWatch जैसी services access करने देना।                                            |
| 2️⃣ | **AWS Lambda**                        | Lambda function को DynamoDB, S3, SNS आदि access करने की permission देना।                                     |
| 3️⃣ | **ECS / EKS Tasks**                   | Containers को specific AWS resources access करने देना।                                                       |
| 4️⃣ | **AWS Glue / EMR**                    | Data analytics services को S3 buckets और databases तक पहुँच देना।                                            |
| 5️⃣ | **AWS CodeBuild / CodePipeline**      | Build और deploy automation के दौरान resources manage करने देना।                                              |
| 6️⃣ | **Cross-account Access**              | एक AWS account के user को दूसरे account के resources तक पहुँच देना।                                          |
| 7️⃣ | **Federated Users (SSO or AD users)** | External identity provider (जैसे Google, Okta, Active Directory) से आने वाले users को temporary access देना। |

---

## 🧠 **Concept Summary:**

* IAM **User** → real human होता है (username, password, access keys)।
* IAM **Role** → virtual identity है जो **AWS services** या **applications** के लिए होती है।
* Role को **assume** किया जाता है, **login नहीं किया जाता**।

---

## 💡 **Example: EC2 Role Use Case**

1. EC2 instance को `AmazonS3ReadOnlyAccess` role attach किया गया।
2. अब EC2 पर कोई भी app बिना access keys के S3 से data read कर सकता है।
3. EC2 internally **STS (Security Token Service)** से temporary credentials लेता है।

➡️ यह temporary credentials AWS SDK या CLI में auto-manage हो जाते हैं।

---

## ⚙️ **Working Flow (Simple Diagram Explanation):**

```
[ EC2 Instance ]
       │
       │  (Assume Role)
       ▼
[ IAM Role → Attached Policy (e.g., S3 ReadOnly) ]
       │
       ▼
[ AWS STS provides Temporary Credentials ]
       │
       ▼
[ EC2 securely accesses S3 ]
```

| Concept                    | Explanation                                 |
| -------------------------- | ------------------------------------------- |
| **Role works on**          | AWS Services (EC2, Lambda, ECS, Glue, etc.) |
| **Provides**               | Temporary permissions                       |
| **Purpose**                | Secure resource-to-resource access          |
| **No need of**             | Access keys or passwords                    |
| **Created and managed in** | AWS IAM Console                             |

## 🔹 **1️⃣ Policy क्या होती है (What is a Policy in AWS IAM)?**

👉 **Policy** एक **permission rule document** होती है जो बताती है कि —
**कौन (Who)** क्या **action (What)** किस **resource (Which)** पर कर सकता है या नहीं कर सकता।

मतलब, policy AWS को बताती है कि —

> “इस user/role/group को कौन-सी services या actions की permission है।”

---

### 💡 **Example:**

अगर किसी user को S3 की read-only access देनी है,
तो उसकी policy होगी:

> “Allow s3:ListBucket and s3:GetObject on all buckets.”

---

## 🔸 **2️⃣ Policy का Format (JSON Structure)**

AWS policies हमेशा **JSON format** में होती हैं।

👇 Example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetObject"
      ],
      "Resource": "*"
    }
  ]
}
```

### Explanation:

| Key          | Meaning                                                 |
| ------------ | ------------------------------------------------------- |
| **Version**  | Policy format version (always `"2012-10-17"`)           |
| **Effect**   | `"Allow"` या `"Deny"` – क्या करना है                    |
| **Action**   | कौन-से operations allow करने हैं (e.g., `s3:GetObject`) |
| **Resource** | किस resource पर (e.g., `"arn:aws:s3:::mybucket/*"`)     |

---

## 🔹 **3️⃣ AWS में Policy के Types**

| Type                             | Description                                                             | Example                                     |
| -------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------- |
| **AWS Managed Policy**           | AWS द्वारा predefined ready-made policies                               | `AmazonS3FullAccess`, `AdministratorAccess` |
| **Customer Managed Policy**      | User खुद बनाता है (custom JSON rules)                                   | Custom policy for limited S3 + EC2 access   |
| **Inline Policy**                | किसी specific user/role/group के अंदर directly attach की जाती है        | Only for one entity                         |
| **Permission Boundary**          | Limit करती है कि max permission क्या हो सकती है                         | Boundary for developers                     |
| **Service Control Policy (SCP)** | AWS Organizations में use होती है multiple accounts control करने के लिए | Deny certain services for all accounts      |

---

## 🔹 **4️⃣ Policies का Use कहाँ होता है**

Policies attach की जाती हैं:

* **IAM User**
* **IAM Group**
* **IAM Role**

👉 इससे ये entities AWS resources पर specific actions कर सकती हैं।

---

### 💡 Example Use Cases:

| Entity            | Attached Policy           | Result                                 |
| ----------------- | ------------------------- | -------------------------------------- |
| `developer1`      | `AmazonS3FullAccess`      | User can access all S3 buckets         |
| `DevelopersGroup` | `AmazonEC2ReadOnlyAccess` | All group users can only view EC2 info |
| `EC2S3Role`       | `AmazonS3ReadOnlyAccess`  | EC2 can read data from S3 bucket       |

---

## 🔹 **5️⃣ Policy कैसे बनाते हैं (Create Policy Steps)**

### 🔧 Using AWS Console:

1. **Open IAM Console** → Left panel → **Policies → Create Policy**
2. Choose method:

   * **Visual editor:** Click and choose service + actions
   * **JSON:** Paste your own JSON code
3. Example JSON:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": [
           "ec2:DescribeInstances",
           "ec2:StartInstances",
           "ec2:StopInstances"
         ],
         "Resource": "*"
       }
     ]
   }
   ```
4. Click **Next** → Review
5. Give a name → Example: `EC2StartStopPolicy`
6. Click **Create policy** ✅

अब ये policy **user**, **group**, या **role** पर attach की जा सकती है।

## 🔹 **6️⃣ Policy कैसे Attach करते हैं**

### For User:

IAM → Users → Select user → **Permissions → Add permissions → Attach policies directly**

### For Group:

IAM → User groups → Select group → **Permissions → Attach policies**

### For Role:

IAM → Roles → Select role → **Permissions → Attach policies**

---

## 🧠 **7️⃣ Important Points to Remember**

* Default behavior: **“Deny everything”** — जब तक Allow policy नहीं लगती।
* **Deny always overrides Allow.**
* Policy को हमेशा **least privilege principle** के साथ design करो (only what is necessary).
* Policies reusable होती हैं (Managed policies multiple users को assign हो सकती हैं)।

| **Effect**        | Allow / Deny                                 |
| **Attached to**   | User / Group / Role                          |
| **Types**         | Managed, Inline, Boundary, SCP               |
| **Created in**    | IAM → Policies → Create Policy               |
| **Best Practice** | Least privilege + Managed policies preferred |

## 🔹 1️⃣ सबसे पहले — Role क्या होता है (Recap)

👉 AWS में **Role** basically एक **temporary permission identity** होती है।
यह **User की तरह होती है**, लेकिन इसके पास **permanent credentials (username/password)** नहीं होते।

> यानी Role = Identity + Permissions (Policies)

जब कोई service या user ये Role **assume करता है**,
तो वो temporarily उस Role की permissions ले लेता है।

---

## 🔸 2️⃣ अब बात करते हैं — “**Account Role**” क्या होता है?

### 🔹 Meaning:

**Account Role** का मतलब है एक ऐसा Role जो
या तो **एक ही AWS account के अंदर** use होता है
या **cross-account access** के लिए create किया जाता है।

> मतलब – एक AWS account दूसरे account को कुछ limited permission देने के लिए Role बना सकता है।

---

## 🔹 3️⃣ Types of Account Roles

| Type                   | Description                                                               | Example                                                 |
| ---------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------- |
| **Same Account Role**  | Role जो उसी AWS account में users/services use करते हैं                   | EC2 instance को S3 access देने वाला role                |
| **Cross-Account Role** | Role जो किसी *दूसरे AWS account* के user या service को permission देता है | Account A में Role create करके Account B को access देना |

---

## 🔸 4️⃣ Example 1 — Same Account Role (for EC2 or Lambda)

🎯 **Scenario:**
तुम्हें अपने EC2 instance से S3 bucket access करनी है।

तो तुम ये steps follow करोगे 👇

### 🔧 Steps:

1. IAM → **Roles → Create Role**
2. Choose trusted entity: **AWS Service**
3. Select service: **EC2**
4. Attach policy: `AmazonS3ReadOnlyAccess`
5. Name the role: `EC2_S3ReadOnly_Role`
6. Launch EC2 → Attach role → Done ✅

अब वो EC2 instance S3 से data read कर सकता है, क्योंकि
उसने EC2_S3ReadOnly_Role “assume” किया हुआ है।

---

## 🔸 5️⃣ Example 2 — Cross-Account Role

🎯 **Scenario:**
Account A का user चाहता है कि वो Account B के S3 bucket में data upload कर सके।

### 🔧 Steps:

#### In **Account B** (Resource Owner):

1. IAM → Roles → Create Role
2. Choose trusted entity: **Another AWS Account**
3. Enter Account A ID (the one who needs access)
4. Attach Policy: (e.g. `AmazonS3FullAccess`)
5. Create Role → e.g., `CrossAccountS3AccessRole`

#### In **Account A** (User Side):

1. User calls `sts:AssumeRole` API with Role ARN of Account B
2. AWS STS gives **temporary credentials**
3. User now acts as that Role and can access Account B resources 🎯

---

## 🔹 6️⃣ Policy Example (Cross Account Trust Policy)

👇 यह trust policy Account B की role definition में होगी:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:root"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

👉 यहाँ `111122223333` Account A का ID है — जिसे access दी जा रही है।

---

## 🔸 7️⃣ Account Role कहाँ-कहाँ काम आता है

| Use Case                 | Description                                                                  |
| ------------------------ | ---------------------------------------------------------------------------- |
| **Cross-account access** | एक AWS account दूसरे को temporary access देता है                             |
| **Service Role**         | EC2, Lambda जैसी services को permission देने के लिए                          |
| **Delegated Admin Role** | किसी account को admin-like permissions देने के लिए                           |
| **External ID Role**     | Third-party vendors (जैसे monitoring tools) को controlled access देने के लिए |

---

## 🔹 8️⃣ Important Points

* Role **temporary credentials** generate करता है via `STS (Security Token Service)`
* Role को **assume** करने के लिए `sts:AssumeRole` permission चाहिए
* Account Role हमेशा **trusted entity + permission policy** से बनता है
* Role passwords या keys store नहीं करता — security ज़्यादा strong होती है
* **Least privilege** principle हमेशा follow करें

## 🔹 1️⃣ IAM Identity Center (पूर्व नाम: AWS SSO)

👉 पहले इसे **AWS Single Sign-On (SSO)** कहा जाता था,
अब इसका नया नाम है — **AWS IAM Identity Center**.

📘 इसका काम है:

> “एक centralized place देना जहाँ से users multiple AWS accounts और applications में login कर सकें — वो भी सिर्फ एक बार password डालकर।”

यानि यह **Single Sign-On (SSO)** system है AWS के अंदर।

---

## 🔸 2️⃣ Real-life Example से समझो

मान लो तुम्हारी company के पास कई AWS accounts हैं:

* Dev Account
* Test Account
* Prod Account

अब अगर हर user को अलग-अलग IAM user बनाकर access देना पड़े,
तो ये बहुत complex हो जाएगा।

इसलिए आप **IAM Identity Center (SSO)** setup करते हो।

> अब हर employee अपने corporate email या identity provider (जैसे Google Workspace, Microsoft AD) से login करेगा सिर्फ **एक बार**
> और फिर वो directly multiple AWS accounts और apps access कर सकेगा — बिना बार-बार password डाले हुए 🔐

---

## 🔹 3️⃣ Simple Definition

| Concept                  | Explanation                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------- |
| **IAM Identity Center**  | Centralized system for managing user login and permissions across multiple AWS accounts |
| **SSO (Single Sign-On)** | Login once → Access all assigned AWS accounts and applications                          |
| **Integration**          | Works with external identity providers (like Microsoft AD, Okta, Google)                |

---

## 🔸 4️⃣ IAM Identity Center कैसे काम करता है (Working Process)

### 🔧 Step-by-Step Flow:

1. **User logs in** at IAM Identity Center (SSO portal).
2. System verifies identity (either internal or via external IdP).
3. Once authenticated, user sees all **assigned AWS accounts & apps** on the dashboard.
4. When the user clicks one account →
   IAM Identity Center automatically issues **temporary credentials** via AWS STS.
5. User gets into AWS Console or CLI without entering password again ✅

---

## 🔹 5️⃣ Architecture Diagram (Conceptual)

```
User → IAM Identity Center (SSO Portal)
           ↓ verifies identity via
        ┌──────────────┐
        │ Identity Provider │ (Google, AD, Okta)
        └──────────────┘
           ↓
       Temporary Credentials via STS
           ↓
     Access AWS Accounts / Apps
```

## 🔸 6️⃣ Main Components of IAM Identity Center

| Component                   | Description                                                  |
| --------------------------- | ------------------------------------------------------------ |
| **Users & Groups**          | Manage users manually or sync from external IdP              |
| **Permission Sets**         | Define what actions user can perform (like IAM policies)     |
| **AWS Account Assignments** | Map users/groups → permission sets → accounts                |
| **SSO Portal**              | Web page where users login once and access all accounts/apps |

---

## 🔹 7️⃣ Example Setup (Step-by-Step)

🎯 **Goal:**
Company employees should access multiple AWS accounts with one login.

### 🔧 Steps:

1. Go to **IAM Identity Center (SSO)** in AWS Console
2. Choose **Enable IAM Identity Center**
3. Choose your identity source:

   * **Default Identity Center Directory** (manage users directly)
   * **External Identity Provider** (Google, Azure AD, Okta, etc.)
4. Create **Users** or **Groups**
5. Create **Permission Set** (like “AdministratorAccess”, “ReadOnlyAccess”)
6. Assign user/group to:

   * AWS Account → Permission Set
7. User logs in via:

   * **https://<your-sso-portal>.awsapps.com/start**

✅ अब user अपने SSO portal से किसी भी assigned AWS account में login कर सकता है।

### 🧾 **1. Access Analyzer**

👉 **Purpose:** यह बताता है कि कौन से AWS resources (जैसे S3 bucket, IAM role, KMS key आदि) **publicly accessible** हैं या **cross-account** share हो रहे हैं।
**Use:** Security audit और compliance check के लिए।

#### Sub-options:

* **🔹 Resource analysis (New)**
  → ये analyze करता है कि आपके resources externally (publicly या दूसरे account से) accessible तो नहीं हैं।
  → Example: कोई S3 bucket accidentally public हो गई है या cross-account access दे रही है — यह identify करता है।

* **🔹 Unused access**
  → यह बताता है कि कौन-से **users, roles या permissions** लंबे समय से use नहीं हुए हैं।
  → Example: कोई IAM user है जिसने 90 दिन से login नहीं किया — इसे आप identify करके deactivate या delete कर सकते हो।

* **🔹 Analyzer settings**
  → यहाँ से आप नए analyzers create कर सकते हैं और existing analyzers के region व scope सेट कर सकते हैं (जैसे entire organization या specific account के लिए)।

---

### 📜 **2. Credential Report**

👉 **Purpose:** Account में मौजूद सभी IAM users की credentials (passwords, access keys, MFA status, etc.) की एक consolidated report देता है।
**Use:** Security monitoring के लिए।
**Example:**
तुम देख सकते हो कौन-से user का password expire हुआ, किसने MFA enable नहीं किया, किसकी access key old है, etc.
Report CSV format में download की जा सकती है।

---

### 🏢 **3. Organization Activity**

👉 **Purpose:** यह बताता है कि organization level (अगर AWS Organizations use हो रही है) पर कौन-से users या accounts क्या actions perform कर रहे हैं।
**Use:** Cross-account access और consolidated audit देखने के लिए।

---

### 🧰 **4. Service Control Policies (SCPs)**

👉 **Purpose:** यह AWS Organizations में policy boundaries define करता है।
**Use:**
तुम organization के root या OU (Organizational Unit) पर restriction लगा सकते हो कि कौन-से services/accounts को access किया जा सकता है।
**Example:**

> “Developers OU” केवल S3 और EC2 use कर सके, लेकिन RDS नहीं — ऐसा SCP से control किया जा सकता है।

---

### 🧩 **5. Resource Control Policies**

👉 **Purpose:** नए type की policies जो granular resource-level access control के लिए होती हैं।
**Use:** Resource-based conditions define करने के लिए (e.g., कौन user कौन-सी resource modify कर सकता है)।
**Example:**
कह सकते हो — केवल admin user ही “production” tag वाले EC2 instances terminate कर सके।

## 🧠 **Session 25 – AWS EC2 (Elastic Compute Cloud) Notes (Nehra Classes)**

### 👨‍🏫 Teacher: EC2 kya hai?

👨‍🎓 Student:
**EC2 (Elastic Compute Cloud)** एक **वेब सर्विस** है जो **AWS** द्वारा दी जाती है।
यह हमें **resizable compute capacity** देती है — यानी हम अपने virtual servers (instances) को
**scale up / scale down या scale in / scale out** कर सकते हैं।

---

### 👨‍🏫 Teacher: EC2 किस मॉडल पर काम करता है?

👨‍🎓 Student:
यह **Pay-as-you-go** मॉडल पर काम करता है —
मतलब जितना उपयोग करेंगे, उतना ही पैसा देना है।

---

### 👨‍🏫 Teacher: EC2 Instances क्या होते हैं?

👨‍🎓 Student:
EC2 Instances असल में **virtual machines** होते हैं
जो AWS के cloud data centers में run होती हैं।

---

### 👨‍🏫 Teacher: EC2 के साथ कौन-कौन सी services जुड़ी होती हैं?

👨‍🎓 Student:

1. **Security Groups** → Virtual firewall जो incoming/outgoing traffic को control करता है।
2. **Key Pairs** → SSH login के लिए private–public key mechanism।
3. **Elastic Load Balancer (ELB)** → Incoming traffic को distribute करता है।
4. **Auto Scaling** → Demand के हिसाब से instances को auto बढ़ाना/घटाना।
5. **Elastic Block Store (EBS)** → Block level storage जो instance में attach होता है।

---

### 👨‍🏫 Teacher: Free Tier में EC2 को कैसे use कर सकते हैं?

👨‍🎓 Student:
Free Tier में हम केवल **t2.micro instance** use कर सकते हैं
और हर महीने **750 घंटे** तक run कर सकते हैं (12 महीनों के लिए)।
भले ही instance 10 मिनट चले या 50 मिनट — AWS उसे **1 घंटा** मानेगा।

### 👨‍🏫 Teacher: EC2 के pricing models कितने प्रकार के हैं?

👨‍🎓 Student:
EC2 में **5 pricing models** होते हैं 👇

| प्रकार                      | विवरण                                     | उपयोग                              |
| --------------------------- | ----------------------------------------- | ---------------------------------- |
| 1️⃣ **On-Demand Instances** | Pay per hour/second, no upfront           | Short-term unpredictable workloads |
| 2️⃣ **Reserved Instances**  | 1 या 3 साल का commitment, discount 60–75% | Stable predictable workloads       |
| 3️⃣ **Spot Instances**      | AWS unused capacity पर bidding            | Fault-tolerant & flexible apps     |
| 4️⃣ **Dedicated Hosts**     | Physical server reserved for one customer | Compliance & licensing needs       |
| 5️⃣ **Savings Plans**       | 1 या 3 साल का commitment, cheap rates     | Flexible instance usage            |

**Example:**
अगर तुम्हारे server पर traffic बढ़ जाए तो

* तुम **ज़्यादा CPU, RAM या Storage** जोड़ दो (Vertical Scaling),
* या **नए servers** add कर दो (Horizontal Scaling)।

🟢 **Key Point:** Scaling **manual** या pre-planned होती है।
जैसे तुम्हें पहले से अंदाज़ा है कि festival season में traffic बढ़ेगा।

---

### ⚙️ **2️⃣ Elasticity (इलास्टिसिटी)**

> मतलब — सिस्टम का **automatically scale up और scale down** होना, demand के हिसाब से।

**Example:**
अगर रात में traffic कम है तो system अपने आप कुछ instances **remove** कर देता है,
और सुबह ज़्यादा load आने पर **instances बढ़ा देता है**।

🟢 **Key Point:** Elasticity **auto scaling** पर आधारित होती है — real-time में adjust होती है।

---

### 🔍 **Difference Table**

| Feature     | **Scalability**          | **Elasticity**                           |
| ----------- | ------------------------ | ---------------------------------------- |
| **Meaning** | Capacity बढ़ाना या घटाना | Automatically capacity adjust करना       |
| **Type**    | Manual / Planned         | Automatic / Real-time                    |
| **Focus**   | Growth handle करना       | Demand के अनुसार flexibility देना        |
| **Example** | Server manually add करना | Auto Scaling group instance बढ़ाना/घटाना |
| **Used In** | Long-term planning       | Cloud environments (AWS, Azure)          |

---

### 🧠 **Simple याद रखने का तरीका:**

> **Scalability = Growth ke liye scale karna**
> **Elasticity = Demand ke hisaab se auto scale karna**

### ⚙️ **Burstable Performance Instances kya hote hain?**

> ये ऐसे **EC2 instance types** होते हैं जो **normal (baseline) performance** पर चलते हैं,
> लेकिन जरूरत पड़ने पर **temporary high performance (burst)** दे सकते हैं।

---

### 💡 **Simple Example:**

मान लो तुम्हारे पास एक छोटी website है —
ज़्यादातर समय पर traffic कम रहता है,
लेकिन कभी-कभी अचानक visitors बढ़ जाते हैं 🚀

ऐसे cases में **Burstable instance** normal time में low CPU use करेगा,
और traffic बढ़ने पर **temporarily ज़्यादा CPU power** दे देगा।

---

### ⚙️ **Burst कैसे काम करता है? (CPU Credit System)**

1️⃣ हर Burstable instance को कुछ **CPU credits** मिलते हैं।
2️⃣ जब instance **idle रहता है (काम कम करता है)** → वो **credits earn करता है**।
3️⃣ जब instance पर **load बढ़ता है** → वो credits को **use करके burst करता है**
यानी temporarily high CPU power देता है।
4️⃣ जब credits खत्म हो जाते हैं → performance वापस **baseline** पर आ जाती है।

### 🧩 **Common Burstable Instance Families:**

| Family       | Description                                                 |
| ------------ | ----------------------------------------------------------- |
| **T2**       | पुराना version, shared CPU model                            |
| **T3 / T4g** | Modern generation, better cost-efficiency                   |
| **T4g**      | ARM-based (Graviton processor) → low cost, high performance |

```bash
aws ec2 run-instances --instance-type t3.micro --image-id <ami-id>
```

➡️ ये command एक **burstable instance** launch करेगा।

> **Burstable Instance = Normal performance + Temporary boost**
> जब load बढ़े → **Burst** करे, जब load कम हो → **Credit earn** करे।

### 💬 **Use Cases:**

* Low traffic websites 🌐
* Development or testing servers 🧪
* Applications with variable or unpredictable workloads ⚙️

चलो इसे **simple aur short** तरीके से समझते हैं 👇

---

### ⚙️ **CPU Credit kya hai?**

> **CPU Credit** मतलब — AWS EC2 instance को मिलने वाली **CPU power की currency** 💰

हर credit का मतलब है कि तुम्हारा instance कुछ समय तक **CPU का 100% use** कर सकता है।
यानी, credits accumulate (जुड़ते) रहते हैं जब instance idle होता है,
और use होते हैं जब instance high performance देता है (burst करता है)।

---

### 🧩 **Kaise kaam karta hai (Step-by-Step):**

1️⃣ **Idle time:**
जब instance कम काम कर रहा होता है → CPU कम use करता है →
AWS उसे **CPU credits earn** करने देता है।

2️⃣ **Busy time:**
जब अचानक load बढ़ता है → instance अपने **earned credits spend** करता है
ताकि temporarily CPU performance बढ़ सके (burst हो सके)।

3️⃣ **Credit खत्म:**
अगर credits खत्म हो जाते हैं → instance **baseline performance** पर लौट आता है
(मतलब, limited CPU speed)।

---

### 💡 **Example:**

* तुम्हारा instance type है **t3.micro**
* उसे **baseline = 10% CPU performance** मिलती है
* Idle रहने पर वो CPU credits earn करता है
* जब traffic बढ़ता है → वो credits use करके temporarily **100% CPU** तक burst कर सकता है

---

### 📊 **1 CPU Credit =**

> 1 minute के लिए **1 vCPU का 100% utilization**

यानि 1 credit = 1 vCPU × 1 minute = **60 seconds full CPU time**

---

### ⚙️ **Monitoring CPU Credits:**

AWS Console या CLI से check कर सकते हैं:

```bash
aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 \
  --metric-name CPUCreditBalance \
  --dimensions Name=InstanceId,Value=<your-instance-id> \
  --statistics Average \
  --period 300 \
  --start-time 2025-10-27T00:00:00Z \
  --end-time 2025-10-27T01:00:00Z
```

* **CPUCreditBalance** → अभी कितने credits बचे हैं
* **CPUCreditUsage** → कितने credits consume हुए हैं

### 🧠 **Simple याद रखने का तरीका:**

> **CPU Credit = Performance Points**
> Earn when idle 💤 → Spend when busy ⚙️

Low-cost workloads जहाँ
CPU usage कभी-कभी बढ़ता है — जैसे:

* Small websites
* Microservices
* Development & testing environments

### 🧩 पहले समझो “vCPU” क्या है

👉 **vCPU (Virtual CPU)** मतलब — एक virtual processor core
जैसे हमारे laptop में 4 cores होते हैं, वैसे ही EC2 instance में कुछ vCPUs होते हैं।

उदाहरण:

* `t3.micro` = **2 vCPUs**
* `t3.small` = **2 vCPUs**
* `t3.medium` = **2 vCPUs**

### ⚙️ अब समझो “1 CPU Credit = क्या करता है”

👉 **1 CPU Credit = 1 vCPU को 1 minute तक 100% चलाने की permission**

मतलब:

* तुम्हारे instance को AWS ने 1 CPU credit दिया है
* तो वो **1 minute (60 seconds)** तक अपना **पूरा CPU power** use कर सकता है

### 🎯 Example 1 (Simple case)

मान लो:

* तुम्हारे पास **1 vCPU** वाला instance है
* और तुम्हारे पास **5 CPU credits** हैं

➡ इसका मतलब:

> तुम **5 minute** तक उस vCPU को 100% speed से चला सकते हो।

उसके बाद अगर credits खत्म हो गए →

> क्योंकि 2 vCPUs × 5 minutes = 10 CPU credits

---

| Credits | vCPU | Time (Full Speed) | Meaning                      |
| ------- | ---- | ----------------- | ---------------------------- |
| 1       | 1    | 1 min             | 1 vCPU full speed for 60 sec |

## 🎯 **Topic: AWS EC2 Volumes – EBS & Instance Store**

---

### **Q1. EC2 Volume क्या होता है?**

**A:**
जब हम EC2 instance लॉन्च करते हैं, तो डेटा स्टोर करने के लिए डिस्क (storage) की जरूरत होती है।
वही storage EC2 volumes कहलाती हैं।
इनका उपयोग OS install करने और user data स्टोर करने के लिए किया जाता है।

---

### **Q2. EC2 में कितने प्रकार के वॉल्यूम्स होते हैं?**

**A:**
दो प्रकार के वॉल्यूम्स होते हैं:

1. **Instance Store Volumes** (Temporary)
2. **EBS Volumes (Elastic Block Store)** (Permanent)

---

### **Q3. Instance Store Volume क्या है?**

**A:**

* यह **temporary storage** होता है।
* जब instance **stop या terminate** होता है → डेटा **delete** हो जाता है।
* यह host machine के **local storage** का हिस्सा होता है।
* By default instance launch करते समय attach हो जाता है।
* इसे **ephemeral storage** भी कहते हैं।
* Free में मिलता है (extra charge नहीं)।
* Size depends करता है instance type पर।

---

### **Q4. EBS Volume क्या है?**

**A:**

* **Elastic Block Store** – एक dedicated AWS storage service है।
* डेटा **permanent** रहता है, भले ही instance stop/start हो।
* केवल terminate करने पर delete होता है (अगर “Delete on Termination” enabled है)।
* Manually attach/detach कर सकते हैं किसी भी instance से।
* Size up to **16 TB** हो सकता है।
* Paid service है।

---

### **Q5. EBS Volume की खासियतें क्या हैं?**

**A:**

1. **Elasticity:** Size increase/change कर सकते हैं आसानी से।
2. **Snapshot:** Backup लेने की सुविधा।
3. **Encryption:** डेटा secure रहता है।
4. **Performance Options:** अलग-अलग workloads के लिए अलग types।
5. **Attach/Detach:** जरूरत अनुसार instance से जोड़/अलग कर सकते हैं।
6. **Multi-Attach:** कुछ types को एक से ज़्यादा instances से attach किया जा सकता है।
7. **Lifecycle Management:** Snapshots को automate किया जा सकता है।

---

### **Q6. EBS Volume Types कौन-कौन से हैं?**

| Type                    | Full Form / Meaning      | Use Case                              | Notes             |
| ----------------------- | ------------------------ | ------------------------------------- | ----------------- |
| **gp2 / gp3**           | General Purpose SSD      | Balanced performance                  | Default volume    |
| **io1 / io2**           | Provisioned IOPS SSD     | High performance apps                 | Configurable IOPS |
| **st1**                 | Throughput Optimized HDD | Frequent data access (Big data, logs) | Low cost          |
| **sc1**                 | Cold HDD                 | Rarely accessed data                  | Lowest cost       |
| **magnetic / standard** | Magnetic volume          | Small datasets                        | Very slow         |

---

### **Q7. IOPS क्या है?**

**A:**

* **IOPS = Input/Output Operations per Second**
* यह storage की **speed** और **performance** मापता है।
* Higher IOPS → Faster performance → Higher cost.

---

### **Q8. Root Volume और Additional Volume में क्या फर्क है?**

**A:**

* **Root Volume:** OS install होता है, default attach होता है।
* **Additional Volume:** User manually attach कर सकता है data के लिए।
* Terminate करते समय root volume delete हो जाता है (by default)।
* Additional volume delete नहीं होता (unless manually configured)।

---

### **Q9. EC2 Instance में Stop/Start vs Reboot में क्या फर्क है?**

| Feature             | Stop/Start                                | Reboot        |
| ------------------- | ----------------------------------------- | ------------- |
| **Public IP & DNS** | बदल जाते हैं (unless Elastic IP assigned)     | Same रहते हैं |
| **Host Machine**    | बदल जाती है (migrated to another host)      | Same रहती है  |
| **Temporary Data**  | Instance Store डेटा lost                    | Safe          |
| **EBS Volume Data** | Safe रहता है                                 | Safe रहता है  |

---

### **Q10. Delete on Termination क्या करता है?**

**A:**

* यह तय करता है कि instance terminate होने पर volume delete होगा या नहीं।
* **Root volume:** By default checked → delete होता है।
* **Additional volume:** By default unchecked → delete नहीं होता।

---

### **Q11. Multi-Attach Feature किसे कहा जाता है?**

**A:**

* कुछ EBS types (जैसे io1/io2) को **एक साथ 16 तक instances** में attach किया जा सकता है।
* सभी instances एक ही **Availability Zone** में होने चाहिए।
* इसका उपयोग shared data access के लिए किया जाता है।

---

### **Q12. Snapshot क्या होता है?**

**A:**

* Snapshot = किसी समय पर लिया गया **backup** of EBS volume।
* Future में restore करने या duplicate volume बनाने में मदद करता है।

---

## 🧠 **Quick Summary:**

* **Instance Store = Temporary storage (Free)**
* **EBS = Permanent storage (Paid)**
* **EBS Volume Types = gp2/gp3, io1/io2, st1, sc1, magnetic**
* **Stop/Start → Hardware & IP change**
* **Reboot → Same hardware & IP remain**
* **Delete on Termination → Volume deletion control**
* **Snapshot → Backup of volume**

## ⚙️ 1. **EC2 Instance क्या है (Short Recap)**

EC2 instance एक **virtual machine** है जो AWS के physical server पर चलती है।
हर instance के पीछे एक **host machine** होती है — उस पर आपका OS boot होता है, EBS volume attach होता है, और आपको network IP मिलता है।

---

## 🚦 2. **Reboot (Restart) क्या करता है**

जब आप **Reboot** करते हैं:

* यह वैसा ही होता है जैसे अपने laptop को “Restart” करना।
* **OS level पर reboot होता है**, physical host वही रहती है।
* EC2 service instance को shutdown नहीं करती — सिर्फ OS को restart करती है।

### 🔍 **Reboot के दौरान क्या होता है**

| Layer                                  | क्या होता है                               |
| -------------------------------------- | ------------------------------------------ |
| **OS Level**                           | Operating system restart होता है           |
| **Physical Host**                      | वही host machine बनी रहती है               |
| **EBS Volumes**                        | Reattached रहते हैं, data safe रहता है     |
| **Public/Private IP & DNS**            | वही रहते हैं                               |
| **Instance Store (Ephemeral Storage)** | Data safe रहता है (क्योंकि host नहीं बदली) |

➡️ इसलिए **Reboot बहुत fast होता है (1-2 मिनट)** और **network identity नहीं बदलती**।

---

## 🧩 3. **Stop/Start क्या करता है**

जब आप instance को **Stop** करते हैं:

* EC2 instance **completely shutdown** हो जाता है (जैसे power off करना)।
* AWS उस instance का connection उसके current **host machine से हटा देता है**।
* जब आप **Start** करते हैं, AWS उसी EBS volume को **किसी नए host** पर attach करके boot करता है।

### 🔍 **Stop/Start के दौरान क्या होता है**

| Layer                                  | क्या होता है                                                       |
| -------------------------------------- | ------------------------------------------------------------------ |
| **OS Level**                           | पूरी तरह shutdown होता है                                          |
| **Physical Host**                      | बदल जाती है (क्योंकि AWS dynamically assign करता है)               |
| **EBS Volumes**                        | Safe रहते हैं (persistent storage)                                 |
| **Public IP & DNS**                    | बदल जाते हैं (क्योंकि नई host और network interface attach होती है) |
| **Private IP (VPC)**                   | Default VPC में बदल सकती है, लेकिन custom VPC में same रहती है     |
| **Instance Store (Ephemeral Storage)** | Data lost हो जाता है (क्योंकि host बदलती है)                       |

➡️ इसलिए Stop/Start के बाद **नया underlying hardware और network** मिल सकता है।

---

## 🔐 4. **Elastic IP के साथ Behavior**

अगर instance को **Elastic IP (EIP)** assign किया है:

* Stop/Start के बाद भी **Public IP same रहता है** क्योंकि EIP static होता है।
* बिना EIP के, हर Start पर **नया public IP** मिलेगा।

---

## 🧠 5. **Use Cases**

| Case                                           | Reboot कब करें               | Stop/Start कब करें                      |
| ---------------------------------------------- | ---------------------------- | --------------------------------------- |
| **Minor OS issue**                             | जब सिर्फ OS hang या stuck है | ❌                                       |
| **Patch installation या memory clear करनी हो** | ✔️                           | ❌                                       |
| **Hardware issue या performance degrade हो**   | ❌                            | ✔️ (क्योंकि नई host मिलेगी)             |
| **Billing रोकना (EBS-backed instance)**        | ❌                            | ✔️ (Stopped state में billing रुकती है) |
| **Instance type change करना हो (t2 → t3)**     | ❌                            | ✔️ (Stop करके ही possible है)           |

---

## 💡 Summary Table

| Feature             | **Reboot**       | **Stop/Start**                   |
| ------------------- | ---------------- | -------------------------------- |
| Public IP & DNS     | Same रहते हैं    | बदल जाते हैं (unless Elastic IP) |
| Host Machine        | Same रहती है     | बदल जाती है                      |
| Instance Store Data | Safe रहता है     | Lost हो जाता है                  |
| EBS Data            | Safe रहता है     | Safe रहता है                     |
| Boot Time           | Fast (1–2 min)   | थोड़ा Slow (2–5 min)             |
| Billing             | Continue होती है | Stopped state में रुकी रहती है   |

## 🧠 **Definition:**

> ताकि यह verify किया जा सके कि —
> 1️⃣ आपका **instance का OS सही से चल रहा है**, और
> 2️⃣ उसका **underlying hardware / network ठीक है**।

## ⚙️ **Types of EC2 Status Checks**

| Type                         | Test किस Level पर होता है | क्या Check करता है                                                                  | Responsible Party      |
| ---------------------------- | ------------------------- | ----------------------------------------------------------------------------------- | ---------------------- |
| **1. System Status Check**   | AWS Infrastructure Level  | Host machine (hardware), power, network connectivity, AWS internal issue            | **AWS की जिम्मेदारी**  |
| **2. Instance Status Check** | OS / VM Level             | आपके instance का OS boot हुआ या नहीं, kernel crash हुआ या नहीं, system hang तो नहीं | **User की जिम्मेदारी** |

### 🔍 **1. System Status Check (AWS Side)**

यह check करता है कि AWS की **underlying physical host machine** ठीक चल रही है या नहीं।

✅ पास होने का मतलब:

* AWS host machine, network, power सब ठीक हैं।

❌ Fail होने का मतलब:

* AWS के hardware या network में issue है
  (जैसे disk failure, hypervisor crash, rack network down आदि)।

🔧 Solution:

* AWS auto-healing कर सकता है या
* आप खुद instance को **Stop/Start** कर सकते हैं (जिससे नई host machine मिल जाएगी)।

---

### 🔍 **2. Instance Status Check (Your Side)**

यह check आपके EC2 instance के **OS level health** को monitor करता है।

✅ पास होने का मतलब:

* OS booted, kernel active, system responding.

❌ Fail होने का मतलब:

* Boot error, kernel panic, corrupted OS files, firewall blocking SSH/RDP आदि।

🔧 Solution:

* SSH से login करके troubleshoot करें
* या instance को reboot/start करें
* या नया instance बनाकर volume reattach करें।

## 🧠 **AWS EC2 Volume Snapshot — Summary Notes**

### 🔹 Snapshot क्या है?

* **Snapshot = Point-in-time copy of data**
  मतलब किसी वॉल्यूम या फाइल सिस्टम का उस समय का **exact backup**।
* इसे आप ऐसे समझो जैसे एक **फोटो** — जिस पल आपने ली, उस पल की स्थिति सेव हो गई।
* क्लाउड में यह एक **backup mechanism** होता है, जो data protection और disaster recovery के लिए उपयोग किया जाता है।

---

### 🔹 क्यों Snapshot बनाते हैं?

1. **Data backup** रखने के लिए
2. **Disaster recovery** setup करने के लिए
3. **Data replication** या cloning के लिए (e.g., दूसरी region में copy करना)

---

### 🔹 Snapshot कैसे काम करता है?

* EBS Volume से Snapshot बनाया जाता है → backup के लिए
* Snapshot से EBS Volume बनाया जा सकता है → restore/recovery के लिए
  👉 यानी **Volume → Snapshot (backup)** और **Snapshot → Volume (restore)**

---

### 🔹 Incremental Backup

* पहला snapshot पूरा volume copy करता है
* उसके बाद वाले snapshots सिर्फ **बदले हुए blocks (changed data)** save करते हैं
* इसलिए space और cost दोनों कम लगते हैं
  💡 *Incremental का मतलब: पिछले snapshot से अब तक के बदलाव ही store होंगे।*

---

### 🔹 Snapshot Storage

* Snapshots internally **Amazon S3** में store होते हैं
* लेकिन यूजर को यह S3 में दिखाई नहीं देते — ये **EBS console** में दिखते हैं
* Snapshot एक **regional service** है → एक ही AWS region में रहता है
* चाहें तो snapshot को **copy या share** किया जा सकता है:

  * दूसरे AWS account के साथ (private sharing)
  * दूसरे region में (data migration के लिए)

---

### 🔹 Snapshot और Encryption

* By default **unencrypted** होते हैं
* अगर EBS Volume encrypted है → Snapshot भी encrypted होगा
* Unencrypted Volume से encrypted Snapshot बनाना हो तो “Copy” option से किया जाता है
* **Encrypted Snapshots को share नहीं किया जा सकता** (security reason)

---

### 🔹 Snapshot Lifecycle Management

* Snapshots को manually भी बना सकते हैं
* लेकिन automate करने के लिए **Amazon Data Lifecycle Manager (DLM)** का use करते हैं
  → यह snapshots को create/delete automatically schedule करता है

---

### 🔹 Snapshot Cost Optimization

* Snapshots **S3 Standard tier** में stored रहते हैं → costly
* पुराने या rarely used snapshots को **Archive tier (Glacier)** में move कर सकते हैं
  → इससे cost ~75% तक कम हो जाती है
* Archive snapshot को restore करने में 72 घंटे तक लग सकते हैं

---

### 🔹 Fast Snapshot Restore (FSR)

* एक **premium feature** है
* इसका use तब करते हैं जब आपको snapshot से volume **तेजी से provision** करना हो
  (जैसे failure recovery या rapid scale-up)
* यह feature **paid** होता है

---

### 🔹 Key Points Summary

| Concept               | Explanation                        |
| --------------------- | ---------------------------------- |
| **Snapshot**          | EBS Volume का point-in-time backup |
| **Storage**           | Internally S3 में save होता है     |
| **Type**              | Incremental                        |
| **Scope**             | Regional                           |
| **Encryption**        | KMS key से possible                |
| **Automation**        | Data Lifecycle Manager (DLM)       |
| **Cost Optimization** | Archive tier (Glacier)             |
| **Fast Recovery**     | Fast Snapshot Restore (FSR)        |

## ⚙️ **Features of EC2 Volume Snapshot**

| 🔢     | **Feature**                                | **Explanation (विवरण)**                                                                                                                    |
| ------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1️⃣    | **Point-in-Time Backup**                   | Snapshot आपके EBS volume का उस समय का exact copy बनाता है — यानी एक instant backup (data loss से बचाव के लिए)।                             |
| 2️⃣    | **Incremental Backup**                     | पहला snapshot पूरा volume save करता है, और अगले snapshots केवल बदले हुए data blocks को store करते हैं → जिससे **storage cost कम** होती है। |
| 3️⃣    | **Stored in S3 (Internally)**              | Snapshot data AWS S3 storage में securely रखा जाता है (लेकिन user को S3 bucket में दिखाई नहीं देता)।                                       |
| 4️⃣    | **Regional Resource**                      | हर snapshot एक region-specific होता है → लेकिन आप उसे **copy करके दूसरे region में ले जा सकते हैं**।                                       |
| 5️⃣    | **Create Volume from Snapshot**            | Snapshot से आप कभी भी नया EBS volume बना सकते हैं — useful for recovery, cloning, or scaling।                                              |
| 6️⃣    | **Automation via Lifecycle Manager (DLM)** | AWS Data Lifecycle Manager से आप snapshots को **automatically create, retain, और delete** करा सकते हैं।                                    |
| 7️⃣    | **Encryption Support**                     | Snapshot encrypted हो सकता है (KMS key से)। अगर source volume encrypted है तो snapshot भी encrypted होगा।                                  |
| 8️⃣    | **Sharing & Copying**                      | Snapshot को आप **दूसरे AWS account के साथ share** कर सकते हैं या **दूसरे region में copy** कर सकते हैं।                                    |
| 9️⃣    | **Archive Tier (Low-Cost Storage)**        | Rarely used snapshots को आप **Archive tier** में move कर सकते हैं → जिससे storage cost लगभग 75% तक घट जाती है।                             |
| 🔟     | **Fast Snapshot Restore (FSR)**            | यह feature snapshot से volume को बहुत **तेज़ी से provision** करने देता है (normal restore से कई गुना faster)।                              |
| 1️⃣1️⃣ | **Cross-Region Disaster Recovery**         | Snapshot को दूसरे region में copy करके आप **DR (Disaster Recovery)** setup बना सकते हैं।                                                   |
| 1️⃣2️⃣ | **Consistency Option**                     | AWS ensures **crash-consistent snapshots** — मतलब data corruption नहीं होता (specially when using file system freeze options)।             |
| 1️⃣3️⃣ | **Cost Effective**                         | Incremental nature और archive options के कारण snapshots बहुत cost-efficient होते हैं।                                                      |

---

## 🧠 **In Short (Summary Line):**

> **EBS Snapshot** एक **secure, incremental, point-in-time backup** system है
> जो **S3 में stored**, **encrypted**, **shareable**, और **regionally managed** होता है —
> जिससे data recovery, cloning, और disaster recovery आसान और reliable बनते हैं।

**EC2 Images (AMI)** — yaani **Amazon Machine Image** — ek **template (template image)** hoti hai jisse **naye EC2 instances** launch kiye jaate hain.

Aap ise simple shabdon mein **“server ka snapshot”** keh sakte ho, jisme **operating system, software configuration, aur application setup** pehle se hota hai.

---

### 🔹 Definition (Simple Words Me)

**AMI (Amazon Machine Image)** ek **ready-made image** hai jisse aapka EC2 instance banega.
Isme woh sab kuch hota hai jo ek server ko chalane ke liye chahiye hota hai —

* OS (Operating System)
* Application server (e.g. Apache, Nginx, Tomcat)
* Software / Application code
* System settings

* Ubuntu OS installed hai

* Aapka web application deployed hai

   → Default images jaise Amazon Linux, Ubuntu, Windows Server, etc.

2. **Custom AMIs**
   → Aap apne EC2 instance ka snapshot le kar khud ka AMI bana sakte ho.

3. **Marketplace AMIs**
   → Third-party vendors ke AMIs (e.g. WordPress, Jenkins, etc. pre-installed).

### 🔹 Benefits

* **Fast Deployment:** Har baar setup karne ki zarurat nahi.
* **Backup/Recovery:** AMI ko backup ke tarah use kar sakte ho.
* **Scalability:** Same AMI se multiple servers launch kar sakte ho.

### 🧑‍🏫 Teacher: Kya AMI share bhi kar sakte hain?

### 🧑‍🏫 Teacher: AWS Marketplace kya hai?

👩‍🎓 Student: **AWS Marketplace** ek platform hai jahan par **public AMIs** available hoti hain.

### 🧑‍🏫 Teacher: EC2 Image Builder kya karta hai?

👩‍🎓 Student: Sir, **EC2 Image Builder** ek AWS tool hai jo **automatic AMI creation** me help karta hai.

### 🧑‍🏫 Teacher: AMI ke benefits kya hain?

👩‍🎓 Student: Sir, AMI ke main 4 benefits hain 👇

## 🌟 Topic: **AWS EC2 Key Pair – Explained Step-by-Step**

---

### **Teacher:** What is a Key Pair in AWS EC2?

**Student:** A **Key Pair** in AWS EC2 is a **combination of two cryptographic keys** — one **Public Key** and one **Private Key**.
It is used to **securely log in** to your EC2 instance **without using a password**.

---

### **Teacher:** Why do we need a Key Pair in EC2?

**Student:**
We need it for **secure authentication**.
When we connect remotely to an EC2 instance (Linux or Windows), instead of typing a password, we use this **key pair** to verify our identity and ensure that **only authorized users** can log in.

---

### **Teacher:** What are Public and Private Keys?

**Student:**

* The **Public Key** is stored by **AWS** with your EC2 instance.
* The **Private Key** is downloaded by **you** and saved securely on your local system.
  Both work together like a **lock and key system** — the public key locks (encrypts) the access, and the private key unlocks (decrypts) it.

---

### **Teacher:** How does encryption help in Key Pair communication?

**Student:**
Encryption makes the connection **secure**.
Even if someone tries to intercept the data, they cannot read it because it’s encrypted.
Only the person with the correct **Private Key** can decrypt and access the system.

---

### **Teacher:** When do we attach a Key Pair to an EC2 instance?

**Student:**
We attach a Key Pair **at the time of launching** the EC2 instance.
AWS asks you to either **create a new Key Pair** or **use an existing one**.
Without attaching a key pair, you **cannot log in** to that instance later.

---

### **Teacher:** What is the file format of the downloaded key?

**Student:**
The downloaded private key file has the extension **“.pem”** (Privacy Enhanced Mail).
If you use **PuTTY** for Windows connections, you can convert `.pem` into `.ppk` (PuTTY Private Key) format.

---

### **Teacher:** What happens if you lose the Private Key file?

**Student:**
If you lose your **Private Key (.pem file)**, you will **not be able to access your instance** anymore.
So, it’s very important to **store it securely** in a safe location and take backups if needed.

---

### **Teacher:** Can one Key Pair be used for multiple EC2 instances?

**Student:**
Yes, one key pair can be used for **multiple EC2 instances**.
But you must **attach that same key pair** to each instance **during creation**.
However, in large organizations, it’s better to **create different key pairs** for different teams for security.

---

### **Teacher:** Why should each team or user have separate key pairs?

**Student:**
Because if one key gets compromised, only that team’s access is affected.
Also, sharing a single key across teams is risky — anyone can log in anywhere, which can cause **security breaches**.
So, **Development**, **Testing**, **Operations**, and **Production** teams usually have their **own key pairs**.

---

### **Teacher:** What if many users need access to the same machine?

**Student:**
Instead of sharing one private key (which is unsafe), we can:

1. Create **individual user accounts** on the instance and assign them separate key pairs, or
2. Use **AWS Directory Service (Active Directory)** for centralized user authentication.

---

### **Teacher:** What is Active Directory in this context?

**Student:**
**Active Directory (AD)** is a centralized authentication system.
It allows multiple users (like Dev1, Dev2, Test1, etc.) to log in with their own **username and password** instead of sharing a key file.
AWS provides this through its **Directory Services**.

---

### **Teacher:** How does Active Directory improve security?

**Student:**
With Active Directory, each user has their own **login credentials** and **access permissions**.
The admin doesn’t need to distribute `.pem` keys to everyone, reducing the risk of **key misuse or data breaches**.

---

### **Teacher:** Can we still use passwords instead of key pairs?

**Student:**
Technically yes, by changing SSH configurations to allow password login.
But it’s **not recommended** for **security reasons**.
AWS always prefers **key-based authentication**.

---

### **Teacher:** How to protect the Key Pair properly?

**Student:**

* Keep the `.pem` file in a **safe and private folder**.
* Do **not share** it with anyone.
* Set proper **file permissions** (e.g., `chmod 400 key.pem` on Linux).
* Take **secure backups** if required.

---

### **Teacher:** What is the main takeaway from this session?

**Student:**

* A **Key Pair = Public Key + Private Key**.
* Used for **secure login** to EC2 instances.
* **Public key** stays with AWS, **Private key** stays with you.
* You must **attach a key pair when launching** your EC2 instance.
* **Never share or lose your private key.**
* For multiple users, prefer **Active Directory integration** instead of sharing `.pem` files.

## 🛡️ **AWS Security Group क्या होता है?**

👉 **Security Group (SG)** एक तरह का **Virtual Firewall (फ़ायरवॉल)** है
जो आपके **EC2 instance (या अन्य AWS resource)** के अंदर और बाहर जाने वाले **network traffic** को **control (allow या deny)** करता है।

मतलब —
यह decide करता है कि कौन-से **port, protocol, और IP address** आपके server से connect हो सकते हैं या नहीं।

---

## ⚙️ **Security Group कैसे काम करता है**

Security Group दो तरह के rules रखता है 👇

| Rule Type          | मतलब                                                       |
| ------------------ | ---------------------------------------------------------- |
| **Inbound Rules**  | कौन आपके instance से connect हो सकता है (incoming traffic) |
| **Outbound Rules** | आपका instance किससे connect हो सकता है (outgoing traffic)  |

AWS Security Group में **डिफ़ॉल्ट रूप से सभी inbound traffic block होता है**,
लेकिन **outbound traffic allow होता है**।

---

## 🧩 **Example समझिए**

मान लीजिए आपने एक EC2 instance बनाया (Linux server)।
आप चाहते हैं कि —

* आप SSH (port 22) से login कर सकें
* आपकी वेबसाइट HTTP (port 80) और HTTPS (port 443) पर खुले

तो आपको ये Security Group rules लगाने होंगे 👇

| Type  | Protocol | Port Range | Source                       |
| ----- | -------- | ---------- | ---------------------------- |
| SSH   | TCP      | 22         | Your IP (e.g., 49.32.x.x/32) |
| HTTP  | TCP      | 80         | 0.0.0.0/0                    |
| HTTPS | TCP      | 443        | 0.0.0.0/0                    |

👉 इसका मतलब —

* Port 22 सिर्फ आपके सिस्टम के IP से खुलेगा
* Port 80 और 443 किसी भी user के लिए खुले होंगे

---

## 🔁 **Security Group कैसे assign करते हैं**

Security Group को आप दो जगह से assign कर सकते हैं —

1. EC2 instance बनाते समय
2. बाद में EC2 → Networking → Security → Change security groups

---

## 🚫 **Security Group की खास बातें**

| Feature                       | Description                                                                                                                                   |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stateful**                  | SG “stateful” होता है — अगर inbound में कोई traffic allow किया है, तो उसका reply अपने आप allow होता है (outbound में अलग से rule नहीं चाहिए)। |
| **Only Allow Rules**          | SG में आप सिर्फ allow कर सकते हैं; deny rule नहीं होता।                                                                                       |
| **Multiple Groups**           | एक instance को एक से ज़्यादा SG assign किए जा सकते हैं।                                                                                       |
| **Applied at Instance Level** | SG EC2 instance या ENI (Elastic Network Interface) पर apply होता है।                                                                          |

---

## 🔒 **Example Scenario**

**Scenario:**
आपका EC2 database server है (MySQL on port 3306)
आप चाहते हैं कि सिर्फ आपके application server से ही connect हो सके।

तो inbound rule इस तरह रहेगा 👇

| Type         | Protocol | Port | Source                              |
| ------------ | -------- | ---- | ----------------------------------- |
| MySQL/Aurora | TCP      | 3306 | Application Server’s Security Group |

👉 यहाँ “source” में किसी IP की जगह आप **दूसरे Security Group का नाम** भी दे सकते हैं।
इससे tightly controlled access मिलता है।

## ✅ **Short Summary**

| Point      | Explanation                                      |
| ---------- | ------------------------------------------------ |
| Definition | Virtual firewall for EC2 instances               |
| Controls   | Inbound (incoming) & Outbound (outgoing) traffic |
| Default    | All inbound denied, all outbound allowed         |
| Stateful   | Response traffic automatically allowed           |
| Example    | Allow SSH (22), HTTP (80), HTTPS (443)           |
| Source     | IP, CIDR, or another SG                          |
| Works On   | Instance or Network Interface                    |

## 🔐 **AWS Security Group (SG) – Explained in Simple Hindi-English**

---

### 🧠 **Question:** AWS me **Security Group** kya hota hai?

**Answer:** AWS me **Security Group** ek **virtual firewall** hota hai jo aapke **EC2 instance** ke liye **traffic control** karta hai.
Yeh decide karta hai ki kaunsa **traffic andar aayega (inbound)** aur kaunsa **bahar jaayega (outbound)**.

---

### ⚙️ **Question:** Security Group kis level pe kaam karta hai?

**Answer:** Security Group **instance level** pe kaam karta hai.
Matlab har EC2 instance ka apna alag security group ho sakta hai aur uske alag rules bhi.

---

### 🔒 **Question:** Security Group ki zarurat kyu padti hai?

**Answer:** Jab hum EC2 instance Internet pe run karte hain, to hume usko **secure** rakhna hota hai.
Security Group allow karta hai sirf **trusted traffic** ko aur baki sabko block karta hai.

---

### 🚧 **Question:** Firewall kya hota hai?

**Answer:** Firewall ek **security wall** hoti hai jo **network traffic ko monitor aur control** karti hai.
Yeh decide karti hai kaunsa data andar jaaye aur kaunsa bahar aaye.
Jaise ek **security guard** building ke gate pe check karta hai kaun andar jaa sakta hai — waise hi firewall bhi traffic check karti hai.

---

### 🧩 **Question:** Firewall ke types kya hote hain?

**Answer:**

1. **Software Firewall** – System ke andar install hoti hai (jaise Windows Firewall, Linux iptables).
2. **Hardware Firewall** – Ek physical device hoti hai jo Internet aur LAN ke beech lagti hai.

---

### ⚠️ **Question:** Default behavior kya hota hai Security Group ka?

**Answer:**

* **Inbound (andar aane wala)** traffic – by default **DENY (block)** hota hai
* **Outbound (bahar jaane wala)** traffic – by default **ALLOW (permit)** hota hai

Iska matlab: humara instance easily internet se connect kar sakta hai, par koi bhi bahar wala bina permission ke andar nahi aa sakta.

---

### 💻 **Question:** Agar inbound block hai to hum EC2 instance me kaise jaayenge?

**Answer:** Uske liye humko **inbound rule** add karna padta hai.
Example:

* SSH ke liye → **Port 22 (TCP)** allow karte hain
* Website access ke liye → **Port 80 (HTTP)** ya **Port 443 (HTTPS)** allow karte hain

---

### 🧳 **Question:** Agar SSH (port 22) allow nahi kiya to kya hoga?

**Answer:** To hum apne instance me **login hi nahi kar payenge**.
Jaise gate lock ho gaya to koi andar nahi jaa sakta — waise hi, SSH port close hua to EC2 inaccessible ho jaata hai.

---

### 🔁 **Question:** Inbound aur Outbound me kya difference hai?

**Answer:**

* **Inbound Rule:** Bahar se aane wale traffic ko control karta hai (entry gate).
* **Outbound Rule:** Bahar jaane wale traffic ko control karta hai (exit gate).

Inbound = Kaun andar aa sakta hai
Outbound = Kaun bahar jaa sakta hai

---

### 🧑‍🏫 **Teacher:** EC2 में Security Group क्या होता है?

**👨‍🎓 Student:** Sir, **Security Group** basically एक **Virtual Firewall** होता है जो हमारे **EC2 Instances** को **unauthorized access** से protect करता है।
यह decide करता है कि **कौन सा traffic अंदर (inbound)** आएगा और **कौन सा बाहर (outbound)** जाएगा।

---

### 🧑‍🏫 Security Group कहाँ apply होता है?

**👨‍🎓** यह **Instance level** पर apply होता है।
हर EC2 instance के साथ **कम से कम एक Security Group** attach करना जरूरी है।

---

### 🧑‍🏫 क्या Security Group और Firewall एक ही चीज़ हैं?

**👨‍🎓** हाँ sir, conceptually Security Group भी एक **Firewall** की तरह काम करता है — यह ports और IP ranges के through **traffic allow/deny** करता है।

---

### 🧑‍🏫 EC2 instance तक पहुँचने वाला traffic किन-किन layers से गुजरता है?

**👨‍🎓**

1. **AWS Region**
2. **VPC (Virtual Private Cloud)**
3. **NACL (Network Access Control List)**
4. **Security Group**
5. **EC2 Instance**
   इससे multi-layered security ensure होती है।

---

### 🧑‍🏫 Security Group inbound और outbound traffic को कैसे handle करता है?

**👨‍🎓**

* **Inbound Rules:** कौन-सा traffic instance में आ सकता है।
* **Outbound Rules:** कौन-सा traffic instance से बाहर जा सकता है।

---

### 🧑‍🏫 Default behaviour क्या होता है Security Groups का?

**👨‍🎓**

* **Inbound rules → Denied by default** (कोई traffic अंदर नहीं आता जब तक allow न करें)
* **Outbound rules → Allowed by default** (सारा traffic बाहर जा सकता है)

---

### 🧑‍🏫 Example दीजिए — SSH access कैसे allow करते हैं?

**👨‍🎓**
अगर Linux instance है और हमें SSH से access चाहिए तो:

* **Protocol:** TCP
* **Port:** 22
* **Source:** My IP / Anywhere

Windows instance के लिए RDP access चाहिए तो:

* **Protocol:** TCP
* **Port:** 3389

---

### 🧑‍🏫 क्या Security Group में “deny” rule होता है?

**👨‍🎓** नहीं sir ❌, Security Group में **deny rule नहीं होता**।
अगर कुछ allow नहीं किया गया है, तो वो automatically denied होता है।

---

### 🧑‍🏫 क्या एक instance में multiple Security Groups हो सकते हैं?

**👨‍🎓** हाँ sir ✅
एक instance पर **maximum 5 Security Groups** attach किए जा सकते हैं।
और एक ही Security Group को multiple instances पर भी use किया जा सकता है।

---

### 🧑‍🏫 Security Group के अंदर Rules कैसे काम करते हैं?

**👨‍🎓**
हर Rule में define होता है:

* Protocol (TCP, UDP, ICMP etc.)
* Port Range (22, 80, 443)
* Source (CIDR/IP, My IP, another SG, etc.)

---

### 🧑‍🏫 Source options कौन-कौन से होते हैं Security Group में?

**👨‍🎓**

1. **CIDR IP Range** – जैसे `192.168.1.0/24`
2. **Another Security Group** – एक SG से दूसरे SG का traffic allow करना
3. **Prefix List** – multiple IP ranges की list
4. **Self** – same SG से आने वाला traffic
5. **Load Balancer** – ELB से आने वाला traffic
6. **Anywhere (0.0.0.0/0)** – हर जगह से access (⚠️ risky)

---

### 🧑‍🏫 Stateful vs Stateless में क्या फर्क है?

**👨‍🎓**

* **Security Groups → Stateful** होते हैं → incoming allow है तो outgoing response auto-allowed होता है।
* **NACL → Stateless** होते हैं → incoming और outgoing दोनों के लिए अलग-अलग rules define करने पड़ते हैं।

---

### 🧑‍🏫 अब बताइए NACL क्या होता है?

**👨‍🎓**
**NACL (Network Access Control List)** भी एक firewall है,
जो **Subnet level** पर काम करता है।
यह VPC के अंदर एक और **extra security layer** देता है।

---

### 🧑‍🏫 Security Group और NACL में क्या फर्क है?

| Feature          | Security Group | NACL         |
| ---------------- | -------------- | ------------ |
| Level            | Instance Level | Subnet Level |
| Type             | Stateful       | Stateless    |
| Default Inbound  | Denied         | Allowed      |
| Default Outbound | Allowed        | Allowed      |
| Rules            | Only Allow     | Allow & Deny |
| Attach           | Instance से    | Subnet से    |

---

### 🧑‍🏫 VPC के अंदर NACL कैसे काम करता है?

**👨‍🎓**
VPC में कई Subnets होते हैं।
हर Subnet में NACL assign किया जा सकता है।
जब कोई request आती है, वो पहले **NACL rules** से गुजरती है,
फिर **Security Group** से,
और तब instance तक पहुँचती है।

---

### 🧑‍🏫 Example – Load Balancer और Application Server का setup

**👨‍🎓**

* **Load Balancer (LB-SG):** Allow ports 80 (HTTP) & 443 (HTTPS) from Anywhere
* **App Server (App-SG):** Allow traffic only from LB-SG
* **Database Server (DB-SG):** Allow traffic only from App-SG

इससे layered security बनती है:
User → LB → App → DB

---

### 🧑‍🏫 Best Practices क्या हैं Security Groups के लिए?

**👨‍🎓**

* Only required ports allow करें
* “Anywhere (0.0.0.0/0)” को avoid करें
* Separate SG बनाएं – LB, App, DB के लिए
* Regularly review inbound rules
* Use “My IP” for admin access

---

## ✅ **Summary:**

* **Security Group = Virtual Firewall at Instance Level (Stateful)**
* **NACL = Firewall at Subnet Level (Stateless)**
* **Inbound Rules:** define allowed incoming traffic
* **Outbound Rules:** define allowed outgoing traffic
* **Multiple SGs per Instance allowed (up to 5)**
* **NACL adds extra protection on top of SG**

## 🔹 **NACL (Network Access Control List) क्या होता है?**

**NACL** का पूरा नाम है 👉 **Network Access Control List**
यह AWS में एक **Firewall** होता है जो **Subnet Level** पर काम करता है।

मतलब —
जब कोई **request** या **data packet** आपके **VPC (Virtual Private Cloud)** में आता या बाहर जाता है,
तो वह पहले **NACL** से गुजरता है।
यानी यह **VPC की पहली security layer** होती है।

---

## 🔹 **NACL का काम क्या है?**

➡️ यह तय करता है कि
कौन-सा **traffic subnet में आएगा (inbound)**
और कौन-सा **subnet से बाहर जाएगा (outbound)**

हर traffic packet को NACL check करता है और
**Allow** या **Deny** करता है based on rules.

---

## 🔹 **Important Points:**

| Feature         | Description                                                                          |
| --------------- | ------------------------------------------------------------------------------------ |
| 🔸 Level        | Subnet Level (हर subnet के साथ एक NACL जुड़ा होता है)                                |
| 🔸 Type         | **Stateless** — मतलब inbound और outbound के लिए अलग rules बनाने पड़ते हैं            |
| 🔸 Rules        | Both **Allow** और **Deny** rules define कर सकते हैं                                  |
| 🔸 Default NACL | हर VPC के साथ एक **default NACL** आता है जो **सब कुछ allow करता है**                 |
| 🔸 Custom NACL  | खुद बनाओ तो by default **सब कुछ deny होता है**, जब तक आप rules add न करें            |
| 🔸 Rule Number  | हर rule का एक **number (1–32766)** होता है — छोटे नंबर वाले rule पहले check होते हैं |

---

## 🔹 **Example:**

मान लो तुम्हारे VPC में एक subnet है जिसमें EC2 instance चल रहा है।

अब तुमने NACL में ये inbound rules बनाए 👇

| Rule # | Type        | Protocol | Port | Source    | Action |
| ------ | ----------- | -------- | ---- | --------- | ------ |
| 100    | HTTP        | TCP      | 80   | 0.0.0.0/0 | ALLOW  |
| 200    | SSH         | TCP      | 22   | My IP     | ALLOW  |
| 300    | All Traffic | —        | —    | —         | DENY   |

➡️ मतलब:

* कोई भी browser (port 80) से request भेज सकता है
* सिर्फ तुम्हारा IP SSH से connect कर सकता है
* बाकी सब कुछ deny होगा

---

## 🔹 **Stateful vs Stateless Difference**

| Property         | Security Group | NACL                 |
| ---------------- | -------------- | -------------------- |
| Level            | Instance Level | Subnet Level         |
| Type             | Stateful       | Stateless            |
| Rules            | Only Allow     | Allow + Deny         |
| Default Inbound  | Denied         | Allowed              |
| Default Outbound | Allowed        | Allowed              |
| Response Traffic | Auto Allowed   | Separate rule needed |

👉 **Example:**
अगर NACL में आपने port 80 inbound allow किया है,
तो आपको outbound में भी port 80 allow करना पड़ेगा
(क्योंकि NACL stateless है)।

---

## 🔹 **NACL क्यों ज़रूरी है?**

* यह **extra layer of security** देता है
* Subnet level पर unwanted traffic रोकता है
* Security Groups से पहले filter करता है

---

## 🔹 **Simple Real-Life Example:**

सोचो तुम्हारा घर (VPC) है,
उसके बाहर colony gate (NACL) है,
और घर का main door (Security Group)।

➡️ Colony gate तय करता है कि कौन colony में आएगा (Subnet में)।
➡️ Main door तय करता है कि कौन तुम्हारे घर तक आएगा (Instance तक)।

## 🧠 **AWS EC2 Auto Scaling & Elastic Load Balancer – Q&A Notes (Hindi-English Mix)**

---

### **1. Teacher:** What is **Auto Scaling** in AWS EC2?

**Student:** Sir, **Auto Scaling** ek AWS service hai jo automatically EC2 instances ke number ko increase ya decrease karti hai — based on the **traffic** or **load** on the application.
Agar load badhta hai → new EC2 instances launch hote hain (scale out).
Agar load kam hota hai → extra instances terminate ho jaate hain (scale in).

---

### **2. Teacher:** Why do we need Auto Scaling?

**Student:** Auto Scaling help karta hai maintain karne me:

* **High availability** of applications
* **Stable performance** even when user traffic changes
* **Cost optimization**, kyunki unnecessary instances terminate ho jaate hain

Example:
Agar Monday-Friday traffic zyada hai, to Auto Scaling automatically extra instances run karega.
Saturday-Sunday ko traffic kam hone par, ye instances remove ho jaate hain.

---

### **3. Teacher:** What is **Elastic Load Balancer (ELB)**?

**Student:** **Elastic Load Balancer** ek service hai jo **incoming traffic** ko evenly distribute karti hai multiple EC2 instances me.
It ensures that no single instance is overloaded.

Example:
User → request → Load Balancer → Instance-1 / Instance-2 / Instance-3 (even distribution)

---

### **4. Teacher:** What is the relationship between **Auto Scaling** and **Load Balancer**?

**Student:**

* **Load Balancer** divide karta hai load among all available EC2 instances.
* **Auto Scaling** ensure karta hai ki required number of EC2 instances always available rahe.
  Together they maintain both **availability** and **performance** of the application.

---

### **5. Teacher:** What are **Scale Out** and **Scale In**?

**Student:**

* **Scale Out:** Jab load badhta hai to new EC2 instances add hote hain.
  Example: 4 se badh kar 8 instances ho jana.
* **Scale In:** Jab load kam hota hai to extra EC2 instances remove ho jaate hain.
  Example: 8 se kam ho kar 4 instances reh jana.

---

### **6. Teacher:** What are **Minimum**, **Maximum**, and **Desired Capacity** in Auto Scaling?

**Student:**

* **Minimum Capacity:** Kam se kam kitne instances hamesha running rehne chahiye.
* **Maximum Capacity:** Max limit tak kitne instances Auto Scaling create kar sakta hai.
* **Desired Capacity:** Normal condition me kitne instances application ke liye required hain.

Example:
Min = 2, Desired = 4, Max = 6
→ Load badhne par instances 6 tak ja sakte hain.
→ Load kam hone par 2 tak reduce ho sakte hain.

---

### **7. Teacher:** What is an **Auto Scaling Group (ASG)?**

**Student:**
**Auto Scaling Group** ek logical group hota hai jisme multiple EC2 instances hote hain.
Ye group automatically monitor karta hai aur traffic ke according instances launch/terminate karta hai.

---

### **8. Teacher:** How does AWS decide when to Scale Out or Scale In?

**Student:** Ye decision **Scaling Policies** ke base par hota hai —
jaise CPU utilization, network traffic, ya custom CloudWatch metrics.

Example:

* Agar CPU utilization > 70% (5 min tak) → Scale Out
* Agar CPU utilization < 30% (10 min tak) → Scale In

---

### **9. Teacher:** What are the **types of scaling** in AWS Auto Scaling?

**Student:** Four main types hain:

1. **Manual Scaling** – User manually increase/decrease instances.
2. **Dynamic Scaling** – Automatically based on real-time metrics (CPU, network, etc.).
3. **Scheduled Scaling** – Specific time/date par scaling (like weekends).
4. **Predictive Scaling** – Machine Learning based, past data ke basis par future load predict karta hai.

---

## 🧠 **EC2 IP Addresses & Global Accelerator in AWS**

### 🌐 **1. EC2 IP Addresses kya hote hain?**

जब hum AWS me **EC2 instance** banate hain, to usko communicate karne ke liye **IP address** diya jata hai.

#### **Types of IP Addresses:**

| Type                 | Description                                                              | Example Use                                   |
| -------------------- | ------------------------------------------------------------------------ | --------------------------------------------- |
| **Private IP**       | Internal communication ke liye (VPC ke andar)                            | Backend servers ka communication              |
| **Public IP**        | Internet se access ke liye                                               | Web server, API, etc.                         |
| **Elastic IP (EIP)** | Static Public IP hoti hai (change nahi hoti even if instance restart ho) | Production servers jinke IP fix rehne chahiye |

#### **🧩 Example:**

* Jab aap EC2 instance start karte ho, AWS automatically **Private IP** assign karta hai.
* Agar aap chahte ho ki instance **Internet se access ho**, to aapko **Public IP** (ya Elastic IP) attach karni padti hai.

---

### ⚙️ **2. IP Address kaise kaam karta hai:**

* **Private IP**:

  * Used **inside VPC** only.
  * Example: 10.0.0.5, 172.31.16.7
  * Not routable on the internet.

* **Public IP**:

  * AWS assigns dynamically when instance starts.
  * **Releases automatically** when instance stops.

* **Elastic IP (Static)**:

  * Aap manually allocate karte ho.
  * Same IP ko multiple times reuse kar sakte ho.
  * Recommended for **production environments**.

---

### ⚡ **3. AWS Global Accelerator kya hota hai?**

**AWS Global Accelerator** ek networking service hai jo aapke global users ke liye **application performance aur availability** improve karta hai.

#### **Kaise kaam karta hai:**

* Global Accelerator aapko **2 static IPs** deta hai.
* Ye IPs aapke users ke liye **entry point** ka kaam karte hain.
* Traffic automatically **nearest AWS edge location** se route hota hai (low latency path).

#### **Use Case:**

* Aapke users world-wide hain (India, US, Europe, etc.)
* Aapke backend EC2 instances multiple AWS regions me deployed hain.
* Global Accelerator intelligently user ko **nearest healthy region** me bhejta hai.

#### **Example:**

* User (India) → Mumbai Region EC2
* User (US) → N. Virginia EC2
* Agar Mumbai instance down ho gaya → Automatically N. Virginia region me route kar dega.

---

### ⚙️ **4. Benefits of Global Accelerator:**

| Benefit                     | Description                                    |
| --------------------------- | ---------------------------------------------- |
| **Static IPs**              | Don’t change; no need to update DNS records    |
| **Improved latency**        | Routes traffic via AWS global backbone network |
| **Automatic health checks** | Sends traffic to healthy endpoints             |
| **Multi-region redundancy** | Failover between AWS regions                   |

---

### 🧰 **5. Steps to use Global Accelerator:**

1. Go to **AWS Console → Global Accelerator**
2. Create an **Accelerator**
3. Add your **EC2 instances, ALB, or NLB** as endpoints
4. AWS will assign **2 static global IP addresses**
5. Users connect via these IPs → AWS handles routing automatically.

---

### 📘 **6. Summary Table:**

| Feature                  | EC2 IP                    | Global Accelerator         |
| ------------------------ | ------------------------- | -------------------------- |
| **Purpose**              | Identify & connect to EC2 | Improve global performance |
| **IP Type**              | Private, Public, Elastic  | 2 Static Global IPs        |
| **Scope**                | Within a region/VPC       | Global                     |
| **Failover**             | Manual setup needed       | Automatic                  |
| **Latency Optimization** | None                      | AWS Backbone Network       |

---

### 💡 **Example Real-world Use:**

* Netflix or Amazon.com jaisa global website — worldwide users.
* They use **Global Accelerator** to ensure users get **low latency, high availability**, and static entry IPs.

### 🧑‍🏫 Q1: What is an **IP Address** and why do we need it?

👨‍🎓 A: IP Address ka full form hota hai **Internet Protocol Address**.
Ye ek **unique number** hota hai jo har device ko network me identify karne ke liye diya jata hai.
Iske bina devices ek dusre se **communicate** nahi kar sakte.
👉 Example: Jaise letter bhejne ke liye address chahiye hota hai, waise hi network me communication ke liye IP address chahiye.

---

### 🧑‍🏫 Q2: IP Address ke **types** kaun se hote hain?

👨‍🎓 A: Mainly do versions hote hain:

1. **IPv4 (Internet Protocol version 4)**

   * 32-bit address hota hai.
   * Example: `192.168.1.1`
   * Limited number of addresses milte hain.
2. **IPv6 (Internet Protocol version 6)**

   * 128-bit address hota hai.
   * Example: `2001:0db8:85a3:0000:0000:8a2e:0370:7334`
   * Ye larger pool of addresses provide karta hai (zyaada devices connect ho sakte hain).

---

### 🧑‍🏫 Q3: IP Address ke **allocation type** kitne hote hain?

👨‍🎓 A: Teen tarike se IP allocate ho sakta hai:

1. **Static IP** – Fixed hota hai, manually assign karte hain.
2. **Dynamic IP** – Automatically milta hai via **DHCP (Dynamic Host Configuration Protocol)**, aur change hota rehta hai.
3. **Elastic IP** – Special type of static **public IP** in AWS jo change nahi hota even after restarting EC2 instance.

---

### 🧑‍🏫 Q4: What is the difference between **Private** and **Public IP**?

👨‍🎓 A:

| Type           | Used In            | Accessible From           | Example     | Charges       |
| -------------- | ------------------ | ------------------------- | ----------- | ------------- |
| **Private IP** | Internal LAN / VPC | Only inside local network | 192.168.x.x | ❌ Free        |
| **Public IP**  | Internet Access    | Globally accessible       | 13.235.x.x  | 💰 Chargeable |
| **Elastic IP** | Static Public IP   | Internet Access           | Fixed IP    | 💰 Chargeable |

👉 **Note:**

* Private IP → Only within same **VPC or LAN**.
* Public IP → Used to access instance from **Internet**.
* Elastic IP → Used when you want **same IP even after restart**.

---

### 🧑‍🏫 Q5: Why is **Elastic IP** needed in AWS EC2?

👨‍🎓 A:
When you **stop/start** an EC2 instance, AWS assigns a **new public IP** automatically.
If you want your server to have **same IP always** (for website, API, DNS mapping etc.),
then you use **Elastic IP** which remains **static**.

👉 Example:
If your website uses IP `3.109.120.45`, and after restart it changes, your DNS will break.
So, Elastic IP prevents that issue.

### 🧑‍🏫 Q6: What is **Loopback IP Address**?

👨‍🎓 A:

* Used for testing your own machine’s network interface.

* IPv6 loopback: `::1`

### 🧑‍🏫 Q7: How does AWS assign IPs when we launch an EC2 instance?

👨‍🎓 A:

* AWS EC2 automatically gives a **Private IP** inside the VPC.

* If you need a fixed public IP, you allocate an **Elastic IP**.

👉 Example:
Your EC2 in VPC → gets Private IP `10.0.0.5`
You attach Public IP → `54.210.x.x` (Dynamic)
You assign Elastic IP → `13.232.x.x` (Fixed)

### 🧑‍🏫 Q8: What is **VPN (Virtual Private Network)** and how it works with IPs?

👨‍🎓 A:
**VPN** creates a **secure tunnel** between your local system and AWS network.
Even if you’re using the Internet, VPN allows you to access your EC2 instances
via **Private IP** (securely).
👉 Use case: Company employees access AWS servers via VPN securely.

### 🧑‍🏫 Q9: Difference between **Public**, **Private**, and **Elastic IP** (Summary)?

### 🧑‍🏫 Q10: What are **Unicast** and **Anycast**?

👨‍🎓 A:

* **Unicast:** Traffic goes to **one single destination**.
* **Anycast:** Traffic goes to **nearest or best-performing server** automatically.

👉 Example:

* Unicast → Like calling one person directly.
* Anycast → Call goes to nearest available branch office.

### 🧑‍🏫 Q11: What is **AWS Global Accelerator**?

👨‍🎓 A:
AWS **Global Accelerator** is a **networking service** that improves

👉 Example:

### 🧑‍🏫 Q12: How is Global Accelerator different from Route 53?

👨‍🎓 A:

Session - 33 | AWS EC2 Service | EC2 Placement Groups | EC2 Service Dashboard | EC2 Instances
Bahut accha question, Vishnudas 👏
AWS EC2 **Placement Groups** ek **advanced networking feature** hai — jisse hum apne **instances (servers)** ko physically AWS data center ke andar **kaise place karna hai** ye control kar sakte hain.

Chalo ise step-by-step samajhte hain 👇

---

## 🧠 **1. Placement Group kya hota hai?**

👉 **Definition:**
Placement Group AWS me ek **logical grouping** hoti hai jisme aap apne EC2 instances ko **specific placement strategy** ke saath launch karte ho — taaki aapko **better performance**, **low latency**, ya **high availability** mil sake.

Simple words me:

> "Placement Group decides *where* and *how close* your EC2 instances are physically placed in the AWS data center."

---

## ⚙️ **2. Placement Group ke Types (3 types)**

| Type          | Purpose                                                                  | Example Use Case                                           |
| ------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **Cluster**   | Instances are placed *very close together* in a single Availability Zone | High performance computing (HPC), Big Data, real-time apps |
| **Spread**    | Instances are placed *on different hardware racks* (different AZs)       | Fault tolerance, critical apps                             |
| **Partition** | Instances are divided into *logical partitions*, each on different racks | Big distributed systems like Hadoop, Cassandra             |

---

### 🔸 **(1) Cluster Placement Group**

* All instances placed **physically close together** (same rack or nearby racks).
* **Low latency** and **high network throughput** between instances.
* Must be in the **same Availability Zone**.
* If one rack fails → all instances may fail.

🧩 **Use Case:**

* High Performance Computing (HPC)
* Machine Learning
* Real-time data analytics

⚠️ **Limitation:**

* Limited scalability — all must fit in one AZ and cluster capacity must be available.

---

### 🔸 **(2) Spread Placement Group**

* Instances are placed **on different racks**, even across **different AZs**.
* Each instance gets its **own rack, power, and network**.
* Designed for **high availability** and **fault isolation**.
* Max **7 instances per AZ** (for Spread groups).

🧩 **Use Case:**

* Critical systems (e.g., master nodes, database servers)
* When you want to avoid single point of failure.

---

### 🔸 **(3) Partition Placement Group**

* Instances divided into **partitions** (logical groups).
* Each partition placed on **separate racks** — no shared hardware.
* You can have **up to 7 partitions per AZ**.
* You can run **hundreds of instances** safely distributed.

🧩 **Use Case:**

* Big Data clusters (Hadoop, HDFS, Cassandra, Kafka)
* When you need **large scale + fault isolation**.

---

## 📊 **3. Comparison Table**

| Feature              | Cluster                    | Spread            | Partition                 |
| -------------------- | -------------------------- | ----------------- | ------------------------- |
| **AZ Scope**         | Single AZ                  | Multi-AZ          | Multi-AZ                  |
| **Purpose**          | High performance           | High availability | Both (for large clusters) |
| **Rack Sharing**     | Same rack                  | Different racks   | Grouped racks             |
| **Instances per AZ** | Many (depends on capacity) | Max 7             | Hundreds                  |
| **Latency**          | Lowest                     | Higher            | Medium                    |
| **Fault Tolerance**  | Low                        | High              | Medium-High               |

---

## 🧰 **4. Commands (AWS CLI Examples)**

**Create Placement Group:**

```bash
aws ec2 create-placement-group \
    --group-name my-cluster-group \
    --strategy cluster
```

**Launch Instance inside Placement Group:**

```bash
aws ec2 run-instances \
    --placement GroupName=my-cluster-group \
    --image-id ami-0abcdef12345 \
    --instance-type c5n.large \
    --count 2
```

**View Placement Groups:**

```bash
aws ec2 describe-placement-groups
```

---

## 🧩 **5. Example Real-world Use Cases**

| Scenario                                     | Recommended Group |
| -------------------------------------------- | ----------------- |
| High-performance scientific computation      | **Cluster**       |
| 7 important database servers (each critical) | **Spread**        |
| Hadoop / Kafka / Cassandra cluster           | **Partition**     |

---

## 🧠 **6. Key Points to Remember**

* Placement Group = **Physical placement control** of EC2s.
* Once created, you can launch instances into it.
* **Cannot move existing instances** into a placement group (must stop & relaunch).
* Cluster = performance; Spread = safety; Partition = both (at scale).

---

### ✅ **Summary**

| Type          | Key Benefit             | Example               |
| ------------- | ----------------------- | --------------------- |
| **Cluster**   | Low latency             | Real-time gaming, HPC |
| **Spread**    | High availability       | Database nodes        |
| **Partition** | Scalable fault-tolerant | Hadoop, Cassandra     |
