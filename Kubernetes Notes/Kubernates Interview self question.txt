# Kubernetes Components Interview Questions & Answers

## Q1. What are the main components of Kubernetes?

**Answer:**
Kubernetes ke components 3 categories me divide hote hain:

1. **Control Plane Components** → Cluster ko manage karte hain.
2. **Worker Node Components** → Applications (Pods) ko run karte hain.
3. **Kubernetes Objects** → Resources jo hum create karte hain (Pod, Service, Deployment, etc.)

**Easy Line:**

> Control Plane manages the cluster, Worker Node runs applications, and Kubernetes Objects define resources.

---

## Q2. What is the role of kube-apiserver?

**Answer:**
**kube-apiserver** Kubernetes ka **entry point** hai.

* Har request pehle API Server ke paas aati hai.
* Ye baaki components ke beech communication karwata hai.

**Example:**
Jab hum `kubectl apply -f deployment.yaml` chalate hain, request sabse pehle **API Server** ke paas jaati hai.

**Easy Line:**

> API Server is the front door of Kubernetes.

---

## Q3. What is etcd and why is it used?

**Answer:**
**etcd** ek **distributed key-value database** hai.

Ye cluster ki sari information store karta hai jaise:

* Pods
* Nodes
* Deployments
* Configuration

Agar etcd data lose ho gaya to cluster ki state bhi lose ho sakti hai.

**Easy Line:**

> etcd stores the complete state of the Kubernetes cluster.

---

## Q4. What is the work of kube-scheduler?

**Answer:**
**kube-scheduler** decide karta hai ki naya Pod kis Worker Node par run hoga.

Ye CPU, Memory aur available resources check karta hai.

**Easy Line:**

> Scheduler decides where a Pod should run.

---

## Q5. What is kube-controller-manager?

**Answer:**
Ye multiple controllers ko manage karta hai.

Controllers ensure karte hain ki cluster **desired state** me rahe.

**Example:**
Agar Deployment me 3 replicas diye aur 1 Pod delete ho gaya, Controller automatically naya Pod create karega.

**Easy Line:**

> Controller Manager maintains the desired state of the cluster.

---

## Q6. What is cloud-controller-manager?

**Answer:**
Ye sirf Cloud environment (AWS, Azure, GCP) me use hota hai.

Ye cloud resources manage karta hai jaise:

* Load Balancer
* Storage
* Network

**Easy Line:**

> Cloud Controller Manager integrates Kubernetes with cloud providers.

---

## Q7. What is kubelet?

**Answer:**
**kubelet** Worker Node ka agent hai.

Ye API Server se instructions leta hai aur ensure karta hai ki Pod properly run ho raha hai.

**Easy Line:**

> Kubelet makes sure Pods are running on the node.

---

## Q8. What is kube-proxy?

**Answer:**
**kube-proxy** networking manage karta hai.

Ye traffic ko correct Pod tak route karta hai aur load balancing me help karta hai.

**Easy Line:**

> kube-proxy routes network traffic to the correct Pod.

---

## Q9. What is Container Runtime?

**Answer:**
Container Runtime actual containers ko run karta hai.

Examples:

* Docker
* containerd
* CRI-O

Kubelet Container Runtime ko instruction deta hai container start karne ke liye.

**Easy Line:**

> Container Runtime runs the containers.

---

## Q10. What is the difference between Control Plane and Worker Node?

| Control Plane               | Worker Node                  |
| --------------------------- | ---------------------------- |
| Cluster manage karta hai    | Applications run karta hai   |
| API Server, Scheduler, etcd | kubelet, kube-proxy, Runtime |
| Decision leta hai           | Decision execute karta hai   |

**Easy Line:**

> Control Plane manages the cluster, Worker Node runs the workload.

# Kubernetes Objects & Pod Interview Questions (Part-2)

---

# Q1. What are Kubernetes Objects?

### Answer:

**Kubernetes Objects** woh resources hote hain jo hum cluster me create karte hain taaki application ko deploy aur manage kar sake.

Examples:

* Pod
* Service
* Deployment
* ReplicaSet
* StatefulSet
* DaemonSet
* Job
* CronJob
* ConfigMap
* Secret
* Namespace

**Easy Line:**

> Kubernetes Objects are resources used to deploy and manage applications.

---

# Q2. What is a Pod in Kubernetes?

### Answer:

**Pod** Kubernetes ki **smallest deployable unit** hai.

Ek Pod me **one ya multiple containers** ho sakte hain jo same **IP, Network aur Storage** share karte hain.

**Easy Line:**

> Pod is the smallest deployable unit in Kubernetes.

---

# Q3. Why can't we create containers directly in Kubernetes?

### Answer:

Kubernetes containers ko directly manage nahi karta.

Container hamesha **Pod ke andar** run hota hai.

Pod container ko networking, storage aur lifecycle provide karta hai.

**Easy Line:**

> Kubernetes manages Pods, not individual containers.

---

# Q4. How does a Pod work internally?

### Answer:

Jab Pod create hota hai:

1. API Server request receive karta hai.
2. Scheduler decide karta hai Pod kis Node par chalega.
3. kubelet Pod create karta hai.
4. Container Runtime container start karta hai.

**Easy Flow:**

```
kubectl
    ↓
API Server
    ↓
Scheduler
    ↓
Worker Node
    ↓
kubelet
    ↓
Container Runtime
    ↓
Pod Running
```

**Easy Line:**

> Scheduler selects the node, kubelet creates the Pod, and Container Runtime starts the container.

---

# Q5. Can a Pod contain multiple containers?

### Answer:

Yes.

Ek Pod me multiple containers ho sakte hain.

Ye containers:

* Same IP share karte hain.
* Same Volume share kar sakte hain.
* localhost se communicate karte hain.

**Example:**

* Main Application Container
* Logging Container (Sidecar)

**Easy Line:**

> Multiple containers inside a Pod share the same network and storage.

---

# Q6. What resources are shared inside a Pod?

### Answer:

Pod ke andar containers share karte hain:

* Network
* IP Address
* Volumes
* localhost communication

Lekin har container ka apna filesystem aur process hota hai.

**Easy Line:**

> Containers inside a Pod share network and storage.

---

# Q7. What is a Kubernetes Node?

### Answer:

Node ek **Physical Machine** ya **Virtual Machine** hota hai jahan Pods run hote hain.

Har Worker Node par kubelet, kube-proxy aur Container Runtime installed hota hai.

**Easy Line:**

> Node is the machine where Pods actually run.

---

# Q8. What are the types of Nodes?

### Answer:

### 1. Control Plane (Master Node)

Cluster ko manage karta hai.

Examples:

* API Server
* Scheduler
* etcd

---

### 2. Worker Node

Applications run karta hai.

Examples:

* kubelet
* kube-proxy
* Container Runtime

**Easy Line:**

> Master manages the cluster, Worker runs the application.

---

# Q9. What is the difference between Pod and Node?

| Pod                                | Node                               |
| ---------------------------------- | ---------------------------------- |
| Smallest deployment unit           | Physical/Virtual Machine           |
| Container run karta hai            | Pods run karta hai                 |
| Temporary                          | Machine hai                        |
| Scheduler Node par place karta hai | Worker resources provide karta hai |

**Easy Line:**

> Pod runs inside a Node.

---

# Q10. Can multiple Pods run on one Node?

### Answer:

Yes.

Ek Node par multiple Pods run kar sakte hain.

Ye Node ke available CPU aur Memory par depend karta hai.

**Easy Line:**

> One Node can run many Pods.

---

# Q11. What happens if a Pod crashes?

### Answer:

Agar Pod Deployment ya ReplicaSet ke through create hua hai, to Kubernetes automatically naya Pod create kar deta hai.

Agar standalone Pod tha, to automatically recreate nahi hoga.

**Easy Line:**

> Deployment recreates failed Pods automatically.

---

# ⭐ Scenario-Based Interview Question

## Q12. Suppose one Worker Node goes down. What happens?

### Answer:

* Us Node ke Pods unavailable ho jayenge.
* Kubernetes detect karega ki Node down hai.
* Agar Pods Deployment/ReplicaSet ke under hain, to Scheduler unhe kisi healthy Node par recreate kar dega.

**Easy Line:**

> Kubernetes automatically shifts Pods to another healthy Node.

# Kubernetes Service, ConfigMap & Secret Interview Questions (Part-3)

## Q1. What is a Service in Kubernetes?

### Answer:

**Service** ek Kubernetes Object hai jo **Pods ko stable IP aur DNS Name** provide karta hai.

Pods ka IP change ho sakta hai, lekin Service ka IP same rehta hai.

**Easy Line:**

> Service provides a stable endpoint to access Pods.

---

# Q2. Why do we need a Service in Kubernetes?

### Answer:

Pods dynamic hote hain aur recreate hone par unka IP change ho jata hai.

Service:

* Stable IP deti hai.
* Stable DNS Name deti hai.
* Load Balancing karti hai.
* Client ko Pod IP yaad rakhne ki zarurat nahi hoti.

**Easy Line:**

> Service solves the Pod IP change problem.

---

# Q3. What problem does Kubernetes Service solve?

### Answer:

Agar Pod delete ho jaye aur naya Pod create ho jaye to uska IP change ho jata hai.

Service ek permanent endpoint provide karti hai jisse application hamesha accessible rehti hai.

**Easy Line:**

> Service hides the changing Pod IP.

---

# Q4. How does a Service find the correct Pods?

### Answer:

Service **Labels** aur **Selectors** ka use karti hai.

Jin Pods ke labels match hote hain, Service unhi Pods ko request forward karti hai.

Example:

```yaml
selector:
   app: my-app
```

Ye selector sirf `app=my-app` wale Pods ko traffic bhejega.

**Easy Line:**

> Service uses Labels and Selectors to identify Pods.

---

# Q5. How does load balancing work in Kubernetes Service?

### Answer:

Agar Deployment me multiple Pods hain, Service automatically requests ko un sab Pods me distribute karti hai.

Example:

```
Request 1 → Pod A

Request 2 → Pod B

Request 3 → Pod C
```

**Easy Line:**

> Service automatically distributes traffic among Pods.

---

# Q6. What are the different types of Services in Kubernetes?

### Answer:

| Service Type     | Use                                     |
| ---------------- | --------------------------------------- |
| **ClusterIP**    | Internal communication                  |
| **NodePort**     | External access using Node IP + Port    |
| **LoadBalancer** | Public access using Cloud Load Balancer |
| **ExternalName** | Connect to an external service          |

**Easy Line:**

> ClusterIP, NodePort, LoadBalancer and ExternalName are the four Service types.

---

# Q7. What is ClusterIP?

### Answer:

ClusterIP default Service type hai.

Ye application ko sirf cluster ke andar access karne deta hai.

Internet se access nahi kar sakte.

**Easy Line:**

> ClusterIP provides internal access only.

---

# Q8. What is NodePort?

### Answer:

NodePort har Worker Node par ek fixed port open karta hai.

Application ko access karte hain:

```
<NodeIP>:<NodePort>
```

Example:

```
192.168.1.10:30080
```

**Easy Line:**

> NodePort exposes the application through Node IP and Port.

---

# Q9. What is LoadBalancer Service?

### Answer:

LoadBalancer cloud provider ke through ek **Public IP** create karta hai.

Ye external users ko application access karne deta hai aur traffic ko multiple Pods me distribute karta hai.

**Easy Line:**

> LoadBalancer exposes the application to the Internet.

---

# Q10. What is ExternalName Service?

### Answer:

ExternalName external service ka DNS alias banata hai.

Example:

```
mysql-db
↓

mydb.aws.com
```

Application sirf alias use karti hai.

**Easy Line:**

> ExternalName maps an external service using DNS.

---

# Q11. What is ConfigMap?

### Answer:

ConfigMap non-sensitive configuration store karta hai.

Example:

* Database URL
* Application Mode
* Port Number
* Environment Variables

**Easy Line:**

> ConfigMap stores application configuration.

---

# Q12. What is Secret?

### Answer:

Secret sensitive information store karta hai.

Example:

* Password
* API Key
* SSL Certificate
* Access Token

Ye Base64 encoded format me store hota hai.

**Easy Line:**

> Secret stores sensitive data securely.

---

# Q13. Difference between ConfigMap and Secret?

| ConfigMap          | Secret              |
| ------------------ | ------------------- |
| Non-sensitive data | Sensitive data      |
| Plain text         | Base64 encoded      |
| App configuration  | Passwords, API Keys |
| Less secure        | More secure         |

**Easy Line:**

> ConfigMap stores configuration, Secret stores confidential data.

---

# Q14. Can ConfigMap and Secret be used inside Pods?

### Answer:

Yes.

Dono ko Pod me inject kar sakte hain:

* Environment Variables
* Volume
* Configuration Files

**Easy Line:**

> ConfigMap and Secret can be mounted as Environment Variables or Volumes.

---

# ⭐ Scenario-Based Interview Question

## Q15. Suppose your database password changes. Will you rebuild the Docker image?

No.

Password Docker image me store nahi karna chahiye.

Usse **Secret** me update karenge aur Pod usi Secret ko use karega.

**Easy Line:**

> Store passwords in Secret, not inside the Docker image.

---

Agar configuration hardcode karenge to chhote se change ke liye bhi image rebuild aur redeploy karna padega.

ConfigMap use karne se bina image change kiye configuration update kar sakte hain.

**Easy Line:**

> ConfigMap separates configuration from application code.

# Kubernetes NodePort vs LoadBalancer Interview Questions (Part-6)

## Q1. What is NodePort Service?

### Answer:

**NodePort** Service application ko **Node IP + Port** ke through bahar se access karne deti hai.

Format:

```text
http://<NodeIP>:<NodePort>
```

Example:

```text
http://192.168.1.10:30080
```

**Easy Line:**

> NodePort exposes the application using Node IP and a fixed port.

---

# Q2. What is the default NodePort range?

### Answer:

By default, Kubernetes NodePort range hoti hai:

```text
30000 - 32767
```

Agar manually port specify nahi karte, to Kubernetes isi range se automatically ek port assign karta hai.

**Easy Line:**

> Default NodePort range is **30000–32767**.

---

# Q3. How do users access an application using NodePort?

### Answer:

User application ko access karta hai:

```text
http://<NodeIP>:<NodePort>
```

Example:

```text
http://192.168.1.10:30080
```

Request Flow:

```text
User
   ↓
NodeIP:30080
   ↓
Service
   ↓
Pod
```

**Easy Line:**

> Access format is NodeIP + NodePort.

---

# Q4. Why is NodePort not preferred in Production?

### Answer:

NodePort me:

* Node IP yaad rakhna padta hai.
* Port number yaad rakhna padta hai.
* User-friendly URL nahi hota.
* Direct Internet exposure secure nahi hota.

Isliye Production me generally **LoadBalancer** ya **Ingress** use kiya jata hai.

**Easy Line:**

> NodePort is mainly used for development and testing.

---

# Q5. How does LoadBalancer work internally?

### Answer:

Jab hum `type: LoadBalancer` use karte hain:

1. Kubernetes internally ek **NodePort** create karta hai.
2. Cloud Provider us NodePort ke upar Public Load Balancer create karta hai.
3. Public traffic Service ke through Pods tak pahunchti hai.

Flow:

```text
Internet
   ↓
Cloud Load Balancer
   ↓
NodePort
   ↓
Service
   ↓
Pods
```

**Easy Line:**

> LoadBalancer works on top of NodePort.

---

# Q6. Does LoadBalancer create a NodePort internally?

### Answer:

**Yes.**

LoadBalancer Service internally ek NodePort create karti hai aur Cloud Load Balancer usi NodePort ko use karta hai.

**Easy Line:**

> LoadBalancer = NodePort + Cloud Load Balancer.

> NodePort is best for development and testing.

LoadBalancer use karte hain:

* Public APIs
* Banking Applications
* E-commerce Websites
* Cloud Deployments

**Easy Line:**

> LoadBalancer is best for production environments.

---

# Q9. What is the main advantage of LoadBalancer over NodePort?

LoadBalancer:

* Public IP provide karta hai.
* User-friendly access deta hai.
* Automatic load balancing karta hai.
* Cloud provider manage karta hai.

NodePort me manually Node IP aur Port use karna padta hai.

**Easy Line:**

> LoadBalancer provides easier and more scalable public access.

# Kubernetes Scheduler Interview Questions (New Questions Only)

## Q1. What factors does kube-scheduler consider before assigning a Pod to a Node?

### Answer:

kube-scheduler Pod ko Node assign karne se pehle ye check karta hai:

* CPU availability
* Memory availability
* Node Labels
* Taints & Tolerations
* Node Affinity / Anti-Affinity
* Resource Requests & Limits

**Easy Line:**

> Scheduler selects the best node based on resources and scheduling rules.

---

# Q2. Does kube-scheduler create Pods?

### Answer:

**No.**

Scheduler sirf Pod ke liye suitable Node select karta hai.

Pod create aur run karne ka kaam **kubelet** aur **Container Runtime** karte hain.

**Easy Line:**

> Scheduler assigns the Pod; kubelet runs the Pod.

---

# Q3. What is an Unscheduled Pod?

### Answer:

Jab Pod create hota hai aur abhi kisi Node par assign nahi hua hota, use **Unscheduled Pod** kehte hain.

Scheduler uske liye suitable Node choose karta hai.

**Easy Line:**

> An unscheduled Pod has no assigned Node.

---

# Q4. What happens immediately after kube-scheduler selects a Node?

### Answer:

Scheduler Node select karta hai.

Uske baad:

* API Server assignment update karta hai.
* Selected Node ka **kubelet** Pod create karta hai.
* Container Runtime container start karta hai.

**Easy Line:**

> After scheduling, kubelet starts the Pod.

---

# Q5. Can kube-scheduler move a running Pod to another Node automatically?

### Answer:

**No.**

Ek baar Pod schedule ho gaya to scheduler usse automatically dusre Node par move nahi karta.

Agar Pod recreate hoga ya Node fail hoga, tab naya Pod kisi aur Node par schedule ho sakta hai.

**Easy Line:**

> Scheduler places a Pod only during scheduling, not after it is running.

---

# ⭐⭐⭐ Scenario-Based Questions

## Q6. Suppose a Node doesn't have enough CPU and Memory. Will kube-scheduler place the Pod there?

### Answer:

**No.**

Scheduler available resources check karta hai.

Agar resources insufficient hain, to dusra suitable Node choose karega.

Agar koi suitable Node nahi mila to Pod **Pending** state me rahega.

**Easy Line:**

> No resources → Pod stays Pending.

---

Sabse pehle **kube-scheduler** aur Pod events check karenge.

```bash
kubectl describe pod <pod-name>
```

Isse scheduling failure ka reason mil sakta hai.

**Easy Line:**

> Pending Pod → Check scheduler events.
