# Part 1 : Concept

## What is Spring for Apache Kafka?

Spring Kafka ek Spring Framework library hai jo Java applications ko Apache Kafka ke saath integrate karne ke liye use hoti hai.

Simple language me,

> Spring Kafka hume Producer aur Consumer banane ka easy tarika provide karta hai.

Agar hum pure Kafka Java Client use kare to bahut sari configuration manually karni padti hai.

Spring Kafka ye sari complexity hide kar deta hai.

---

## Without Spring Kafka

```text
Java Application
        │
        ▼
Kafka Java Client
        │
        ▼
Producer Configuration
Consumer Configuration
Serialization
Connection
Retry
Error Handling
Topic Management
```

Developer ko sab kuch manually likhna padta hai.

---

## With Spring Kafka

```text
Spring Boot Application
        │
        ▼
Spring Kafka
        │
        ▼
Kafka Broker
```

Spring Kafka automatically bahut sari configuration manage kar deta hai.

Developer sirf business logic likhta hai.

---

# Why do we use Spring Kafka?

Agar normal Kafka Client use kare to

* Producer manually banana padta hai.
* Consumer manually banana padta hai.
* Configuration manually karni padti hai.
* Listener create karna padta hai.
* Serialization manually configure karni padti hai.
* Error handling bhi manually karna padta hai.

Spring Kafka ye sab easy bana deta hai.

# 📝 Quick Revision Notes

## Connecting to Kafka

* Spring Kafka me Kafka connection ke liye 3 main components hote hain:

  * `KafkaAdmin`
  * `ProducerFactory`
  * `ConsumerFactory`
* `KafkaAdmin` topic aur admin operations manage karta hai.
* `ProducerFactory` Kafka Producer create karta hai.
* `ConsumerFactory` Kafka Consumer create karta hai.
* Ye tino `KafkaResourceFactory` ko extend karte hain (Spring Kafka 2.5+).
* `bootstrap-servers` batata hai application kis Kafka Broker se connect karegi.
* `setBootstrapServersSupplier()` runtime me naya Kafka cluster choose karne ki facility deta hai.
* Producer ko naye broker se connect karne ke liye `DefaultKafkaProducerFactory.reset()` use hota hai.
* Consumer ko naye broker se connect karne ke liye listener containers ko `stop()` aur `start()` karna padta hai.
* `ABSwitchCluster` Primary aur Secondary Kafka cluster ke beech switch karne ke liye use hota hai.
* Factory Listeners producer/consumer create ya close hone par notifications dete hain (monitoring aur metrics ke liye).
* `spring.application.name` set karne se auto-generated Kafka client IDs meaningful ban jaate hain (jaise `loan-service-producer-1`), jo production troubleshooting me bahut useful hote hain.

> **Ye chapter foundation hai.** Isme sirf infrastructure introduce hua hai. Agle chapters me hum in components ko practical project me implement karenge aur line-by-line code samjhenge.

# 📝 Revision Notes

## Configuring Topics

* `KafkaAdmin` Kafka Broker ke admin operations perform karta hai.
* `NewTopic` ek Java object hai jo Kafka Topic ko represent karta hai.
* `TopicBuilder` Builder Pattern se Topic create karna easy banata hai.
* `name()` topic ka naam set karta hai.
* `partitions()` parallel processing ke liye partition count define karta hai.
* `replicas()` fault tolerance ke liye backup copies define karta hai.
* `compact()` `cleanup.policy=compact` set karta hai aur har key ki latest value retain karta hai.
* `config()` se topic-level properties (compression, retention, cleanup policy, etc.) set kar sakte hain.
* Spring Kafka 2.6+ me partition aur replica omit karne par broker defaults use hote hain.
* Spring Kafka 2.7+ me `KafkaAdmin.NewTopics` se ek bean me multiple topics define kar sakte hain.
* Spring Boot me `KafkaAdmin` automatically configure ho jata hai; sirf `NewTopic` bean define karna hota hai.
* `fatalIfBrokerNotAvailable(true)` application ko Kafka unavailable hone par fail kar deta hai.
* `initialize()` baad me topic creation retry karne ke liye use hota hai.
* Existing topic ke partitions increase kiye ja sakte hain; partitions decrease nahi kiye ja sakte.
* Runtime topic operations: `createOrModifyTopics()`, `describeTopics()`, aur `deleteTopics()`.
* Advanced Kafka administration ke liye `AdminClient` use hota hai.
* `Predicate<NewTopic>` multiple Kafka clusters me selective topic creation ke liye use hota hai.

---

## 📌 Practical Reality

Real Spring Boot projects me tum aksar sirf itna likhoge:

```java
@Bean
public NewTopic orderCreatedTopic() {
    return TopicBuilder
            .name("order-created")
            .partitions(3)
            .replicas(1)
            .build();
}
```

Baaki `KafkaAdmin`, topic creation aur broker interaction ka kaam Spring Boot background me automatically handle kar leta hai. Isi wajah se Spring Kafka ka topic configuration bahut clean aur maintainable lagta hai.

# Interview Questions

### Q1. What is KafkaTemplate?

**Answer:**
KafkaTemplate is a Spring Kafka class that wraps the Kafka Producer and provides simple methods to send messages to Kafka topics.

---

### Q2. Why do we use KafkaTemplate instead of KafkaProducer?

**Answer:**
Because it reduces boilerplate code, integrates with Spring, manages the producer through `ProducerFactory`, supports asynchronous sending, callbacks, retries, and transactions.

---

### Q3. Is KafkaTemplate itself a Producer?

**Answer:**
No. It is a wrapper/helper class that internally uses a Kafka Producer.

---

### Q4. Who creates KafkaTemplate?

**Answer:**
Spring creates it as a bean, usually using a `ProducerFactory`.

---

### Q5. Is KafkaTemplate synchronous?

**Answer:**
No. By default, it is asynchronous and returns a `CompletableFuture<SendResult<...>>`.

---

### Q6. What is the flow of sending a message?

**Answer:**

```
Application
   ↓
KafkaTemplate
   ↓
ProducerFactory
   ↓
KafkaProducer
   ↓
Serializer
   ↓
Kafka Broker
   ↓
Topic
```

---

# 📌 Key Points to Remember

* **KafkaTemplate** is the main Spring class used to send messages to Kafka.
* It wraps the **Kafka Producer** and simplifies message publishing.
* It obtains producers from a **ProducerFactory**.
* By default, sending is **asynchronous**.
* It can send different payload types (String, JSON, Objects, byte[]), depending on the configured serializer.
* In Spring applications, use the **KafkaTemplate bean** managed by Spring instead of creating it manually.

# Interview Questions

## Q1. Difference between `send()` and `sendDefault()`?

**Answer:**

* `send()` requires the topic name in the method call.
* `sendDefault()` sends to the default topic configured in the `KafkaTemplate`.

---

## Q2. Why do we pass a key?

**Answer:**

The key is used by Kafka to determine the partition (unless a partition is explicitly provided) and to maintain ordering for records with the same key.

---

## Q3. When should we use `ProducerRecord`?

**Answer:**

When we need complete control over the record, such as adding headers, custom timestamps, or other metadata.

---

## Q4. What is the difference between `send(ProducerRecord)` and `send(Message<?>)`?

**Answer:**

* `ProducerRecord` is the native Kafka API object.
* `Message<?>` is the Spring Messaging abstraction, where Kafka details are carried in message headers.

---

## Q5. What happens internally when `send()` is called?

**Answer:**

```text
KafkaTemplate
      ↓
Creates ProducerRecord
      ↓
Serializes the key/value
      ↓
KafkaProducer sends the record
      ↓
Broker stores it in the selected topic and partition
```

---

# 📌 Key Points to Remember

* `send(topic, data)` is the **most commonly used** method.
* Use a **key** when you need ordering for related messages.
* If a **partition** is provided explicitly, Kafka does not use the key to choose the partition.
* `sendDefault()` works only when a **default topic** is configured.
* `ProducerRecord` gives you full control over the Kafka record.
* `Message<?>` integrates Kafka with the Spring Messaging framework.

# Interview Questions

## Q1. What is ProducerFactory?

**Answer:**

`ProducerFactory` is responsible for creating and managing `KafkaProducer` instances. `KafkaTemplate` uses it to obtain a producer.

---

## Q2. Why do we need ProducerFactory?

**Answer:**

It separates producer creation from message sending, making configuration reusable and allowing Spring to manage producer instances efficiently.

---

## Q3. What is DefaultKafkaProducerFactory?

**Answer:**

It is the default implementation of the `ProducerFactory` interface that creates `KafkaProducer` objects using the supplied configuration.

---

## Q4. What is the purpose of `bootstrap.servers`?

**Answer:**

It specifies the Kafka broker(s) that the producer connects to. In production, multiple broker addresses are usually provided for high availability.

---

## Q5. Why do we need serializers?

**Answer:**

Kafka stores data as bytes. Serializers convert Java objects (String, JSON, Integer, etc.) into bytes before sending them to Kafka.

---

## Q6. Does KafkaTemplate create KafkaProducer directly?

**Answer:**

No. It obtains a producer from the `ProducerFactory`.

---

## Q7. In Spring Boot, do we always create KafkaTemplate manually?

**Answer:**

No. Spring Boot auto-configures `ProducerFactory` and `KafkaTemplate` when the required dependencies and `spring.kafka.*` properties are present.

---

# 📌 Key Points to Remember

* **ProducerFactory** creates `KafkaProducer` instances.
* **DefaultKafkaProducerFactory** is the default implementation used in Spring Kafka.
* **KafkaTemplate** depends on `ProducerFactory`; it does not create producers itself.
* **bootstrap.servers** tells the producer how to connect to the Kafka cluster.
* **Serializers** convert Java objects into bytes before sending them.
* In most Spring Boot projects, **ProducerFactory** and **KafkaTemplate** are auto-configured through `application.properties` or `application.yml`.

# Interview Questions

## Q1. What are Kafka Headers?

**Answer:**

Kafka Headers are metadata attached to a record. They carry information such as topic, key, partition, timestamp, correlation ID, and custom application-specific values without changing the message payload.

---

## Q2. What is the difference between Payload and Header?

| Payload              | Header                       |
| -------------------- | ---------------------------- |
| Actual business data | Metadata about the message   |
| Example: Order JSON  | Example: Topic, Key, TraceId |

---

## Q3. Why do we use `KafkaHeaders.KEY`?

**Answer:**

To ensure messages with the same key are routed to the same partition, preserving ordering.

---

## Q4. What is Correlation ID?

**Answer:**

A unique identifier used to match a reply with its original request in request-reply messaging.

---

## Q5. Why do microservices use Trace IDs?

**Answer:**

To trace a single request as it travels across multiple services, making debugging and monitoring much easier.

---

## Q6. Can we create custom Kafka headers?

**Answer:**

Yes. Spring's `MessageBuilder.setHeader()` allows us to add custom headers such as `request-id`, `user-id`, `tenant-id`, or `trace-id`.

---

# 📌 Key Points to Remember

* A Kafka record consists of **Payload + Headers**.
* **Payload** contains the actual business data.
* **Headers** contain metadata such as topic, key, partition, timestamp, and custom values.
* `MessageBuilder` is used to create a `Message<?>` with both payload and headers.
* Common production headers include **Request ID**, **Correlation ID**, and **Trace ID**.
* Headers make distributed systems easier to debug, trace, and monitor.

# Interview Questions

## Q1. What does `KafkaTemplate.send()` return?

**Answer:**

It returns a `CompletableFuture<SendResult<K,V>>`, allowing asynchronous processing of the send result.

---

## Q2. Why does KafkaTemplate use `CompletableFuture`?

**Answer:**

Because Kafka sends messages asynchronously. The application can continue executing while Kafka processes the message in the background.

---

## Q3. What is `whenComplete()`?

**Answer:**

It is a callback that executes after the asynchronous operation finishes, whether it succeeds or fails.

---

## Q4. What information does `SendResult` contain?

**Answer:**

`SendResult` contains:

* `ProducerRecord` (the message sent)
* `RecordMetadata` (topic, partition, offset, timestamp returned by the broker)

---

## Q5. What is `RecordMetadata`?

**Answer:**

It contains metadata about the stored record, such as topic name, partition number, offset, and timestamp.

---

## Q6. What is the difference between Async and Sync send?

| Async                             | Sync                                              |
| --------------------------------- | ------------------------------------------------- |
| Does not block the calling thread | Blocks until broker responds                      |
| Returns `CompletableFuture`       | Uses `.get()` to wait                             |
| Best for high throughput          | Used only when immediate confirmation is required |

---

# 📌 Key Points to Remember

* `KafkaTemplate.send()` is **asynchronous by default**.
* It returns a `CompletableFuture<SendResult<K,V>>`.
* Use `whenComplete()` to handle both success and failure.
* `SendResult` contains the original `ProducerRecord` and broker `RecordMetadata`.
* `RecordMetadata` provides the topic, partition, offset, and timestamp.
* Calling `.get()` makes the send operation synchronous and blocks the current thread until the broker responds.

* `CompletableFuture` is ideal for **message-specific business logic**.

# Interview Questions

## Q1. What is `flush()`?

**Answer:**

`flush()` forces the producer to immediately send all buffered records to the Kafka broker without waiting for batching conditions.

---

## Q2. Why do producers buffer messages?

**Answer:**

To create batches, reduce network calls, and improve throughput.

---

## Q3. What is `linger.ms`?

**Answer:**

`linger.ms` is the maximum time the producer waits for additional messages before sending a batch.

---

## Q4. When should we use `flush()`?

**Answer:**

Only when immediate delivery is required, such as critical transactions, shutdown scenarios, or testing. It should not be used after every send in normal production code.

---

## Q5. What is Auto Flush?

**Answer:**

When `KafkaTemplate` is created with the `autoFlush` constructor (`new KafkaTemplate<>(producerFactory, true)`), it automatically calls `flush()` after each `send()`.

---

## Q6. What is the difference between Blocking and Non-Blocking send?

**Answer:**

* **Blocking:** Uses `.get()` and waits for the broker response.
* **Non-Blocking:** Returns immediately with a `CompletableFuture` and handles the result asynchronously.

---

## Q7. Why is asynchronous sending preferred?

**Answer:**

It improves application throughput because threads are not blocked waiting for Kafka acknowledgments.

---

# ⭐ Real Interview Scenario

### Interviewer:

**Your producer is configured with `linger.ms=10`. Immediately after calling `send()`, your application exits. What can happen?**

### Best Answer

> "The message may still be in the producer's buffer and might not be sent before the application exits. Before shutdown, the application should ensure pending messages are sent by allowing the producer to close gracefully or by explicitly flushing when appropriate."

---

# 📌 Key Points to Remember

* Kafka producers use a **buffer** to batch messages before sending.
* **`linger.ms`** controls how long the producer waits to form a batch.
* **`flush()`** forces all buffered messages to be sent immediately.
* Avoid calling `flush()` after every `send()` because it reduces batching and hurts performance.
* **`autoFlush=true`** automatically flushes after each send but is rarely used in high-throughput production systems.
* **Async (`CompletableFuture`)** is the default and preferred approach.
* **Blocking (`get()`)** should be reserved for cases where immediate confirmation is essential.

# Interview Questions

## Q1. What is RoutingKafkaTemplate?

**Answer:**

`RoutingKafkaTemplate` is a Spring Kafka template that selects the appropriate `ProducerFactory` at runtime based on the destination topic.

---

## Q2. Why do we use RoutingKafkaTemplate?

**Answer:**

It allows a single application to send different types of data (String, JSON, `byte[]`, etc.) using different serializers without creating multiple `KafkaTemplate` instances.

---

## Q3. How does RoutingKafkaTemplate select the producer?

**Answer:**

It matches the destination topic name against an ordered map of **regular expression patterns** (`Pattern`) to `ProducerFactory` instances. The first matching pattern is used.

---

## Q4. Why is `LinkedHashMap` used?

**Answer:**

Because pattern matching is order-sensitive. Spring checks the patterns from top to bottom, so the most specific patterns should be added first.

---

## Q5. Does RoutingKafkaTemplate support transactions?

**Answer:**

No. It does not support transactions, `flush()`, `execute()`, or `metrics()` because the producer cannot be determined until the destination topic is known.

---

## Q6. When should we use RoutingKafkaTemplate?

**Answer:**

When an application needs to publish to different topics using different serializers or different producer configurations.

---

# 📌 Key Points to Remember

* `RoutingKafkaTemplate` selects the **ProducerFactory at runtime**.
* It is ideal when **different topics require different serializers**.
* It uses an ordered **`Pattern` → `ProducerFactory`** mapping.
* **`LinkedHashMap`** preserves the matching order, so specific patterns should come first.
* It **does not support** transactions, `flush()`, `execute()`, or `metrics()`.
* It helps reduce the need for multiple `KafkaTemplate` beans in applications that publish multiple data types.

# Interview Questions

## Q1. What is DefaultKafkaProducerFactory?

**Answer:**

It is the default implementation of `ProducerFactory` that creates and manages `KafkaProducer` instances for `KafkaTemplate`.

---

## Q2. Does Spring create a new KafkaProducer for every send()?

**Answer:**

No. By default, Spring creates a **singleton KafkaProducer** and reuses it for all send operations.

---

## Q3. Why does Spring use a singleton producer?

**Answer:**

Creating a KafkaProducer is expensive because it initializes network connections, buffers, metadata, and background threads. Reusing a single producer improves performance.

---

## Q4. What is `producerPerThread`?

**Answer:**

When enabled, `DefaultKafkaProducerFactory` creates a separate KafkaProducer for each thread, preventing one thread's `flush()` from affecting others.

---

## Q5. What must you do when using `producerPerThread=true`?

**Answer:**

Call `closeThreadBoundProducer()` after the producer is no longer needed to release thread-local resources.

---

## Q6. What is the purpose of `Supplier<Serializer>`?

**Answer:**

It creates a separate serializer instance for each producer instead of sharing a single serializer object.

---

## Q7. What is `updateConfigs()` used for?

**Answer:**

It updates producer configuration properties at runtime. Existing producers are not affected until new producers are created.

---

## Q8. Why is `reset()` required after `updateConfigs()`?

**Answer:**

Because existing producer instances continue using the old configuration. `reset()` closes them so that the next request creates new producers with the updated settings.

---

# ⭐ Real Interview Scenario

### Interviewer:

**Your Kafka producer is using a singleton producer. One thread frequently calls `flush()`, and other threads experience delays. How would you solve this?**

### Best Answer

> "By default, `DefaultKafkaProducerFactory` uses a singleton producer shared by all threads. Frequent `flush()` calls can affect other threads. If this becomes a performance bottleneck, I can enable `producerPerThread=true`, which gives each thread its own producer. I would also ensure `closeThreadBoundProducer()` is called when the thread finishes using the producer."

# 📌 Key Points to Remember

* `DefaultKafkaProducerFactory` is the default implementation of `ProducerFactory`.
* It **creates and manages** `KafkaProducer` instances.
* By default, Spring uses a **singleton KafkaProducer** shared across threads.
* `producerPerThread=true` creates a separate producer for each thread.
* When using `producerPerThread`, you must call **`closeThreadBoundProducer()`** to clean up thread-local producers.
* `Supplier<Serializer>` creates a new serializer instance for each producer.
* `updateConfigs()` changes producer configuration for future producers.
* `reset()` closes existing producers so that new ones use the updated configuration.

# Interview Questions

## Q1. What is ReplyingKafkaTemplate?

**Answer:**

`ReplyingKafkaTemplate` is a Spring Kafka template that implements the Request-Reply messaging pattern over Kafka.

---

## Q2. Why do we use ReplyingKafkaTemplate?

**Answer:**

When the producer requires a response from the consumer instead of using one-way asynchronous messaging.

---

## Q3. What is `sendAndReceive()`?

**Answer:**

It sends a request message and returns a `RequestReplyFuture` that completes when the reply is received or when a timeout occurs.

---

## Q4. What is `RequestReplyFuture`?

**Answer:**

It represents the asynchronous request-reply operation and provides access to both the send result and the reply.

---

## Q5. What is the purpose of `@SendTo`?

**Answer:**

`@SendTo` sends the return value of a `@KafkaListener` method to the reply topic.

---

## Q6. Why is Correlation ID required?

**Answer:**

It uniquely matches each reply with its corresponding request, especially when many requests are processed concurrently.

---

## Q7. Why do we need a Reply Container?

**Answer:**

The reply container listens on the reply topic and delivers the response back to the `ReplyingKafkaTemplate`.

---

## Q8. What happens if no reply is received?

**Answer:**

The request waits until the configured timeout expires, after which a timeout exception is raised.

---

# ⭐ Real Interview Scenario

### Interviewer:

**Kafka is asynchronous by nature. Why would you use ReplyingKafkaTemplate instead of a REST API?**

### Best Answer

> "I would use `ReplyingKafkaTemplate` when the communication must remain event-driven and Kafka-based, but the caller still needs a response. It avoids mixing REST with Kafka, supports asynchronous request-reply messaging, and works well in microservice architectures where services already communicate through Kafka."

---

# 📌 Key Points to Remember

* `ReplyingKafkaTemplate` implements the **Request-Reply** pattern over Kafka.
* `sendAndReceive()` sends a request and waits asynchronously for a reply.
* `RequestReplyFuture` represents the request-reply operation.
* A dedicated **Reply Topic** and **Reply Container** are required.
* `@KafkaListener` with `@SendTo` sends the reply automatically.
* **Correlation ID** is used to match replies with requests.
* A configurable **reply timeout** prevents waiting indefinitely.
* `waitForAssignment()` helps ensure the reply listener is ready before sending requests.

# Interview Questions

## Q1. What is `replyErrorChecker()`?

**Answer:**

It checks the reply message after it is received. If it detects an application-specific error (usually through headers), it converts that into an exception instead of returning a successful reply.

---

## Q2. Why do we use `ErrorHandlingDeserializer`?

**Answer:**

It helps detect and safely handle deserialization failures instead of allowing malformed replies to crash request processing.

---

## Q3. What is `KafkaHeaders.REPLY_TOPIC`?

**Answer:**

It specifies the topic where the consumer should send the reply.

---

## Q4. What is `KafkaHeaders.REPLY_PARTITION`?

**Answer:**

It specifies the partition within the reply topic where the response should be sent.

---

## Q5. What is a Shared Reply Topic?

**Answer:**

Multiple producer instances use the same reply topic. Replies are matched to the correct request using the Correlation ID.

---

## Q6. Why should every instance have a unique Group ID when using a shared reply topic?

**Answer:**

So that every application instance receives replies independently, while Correlation IDs determine which reply belongs to which request.

---

## Q7. When do we use `RequestReplyTypedMessageFuture`?

**Answer:**

When the reply payload is a typed object (such as `Order`) or a generic type (such as `List<Order>`), instead of a simple `String`.

---

## Q8. Why do we need `ParameterizedTypeReference`?

**Answer:**

Because Java removes generic type information at runtime. `ParameterizedTypeReference` tells Spring the exact reply type to deserialize.

---

# ⭐ Real Interview Scenario

### Interviewer:

**Suppose your Payment Service returns `List<Payment>` instead of `String`. How will ReplyingKafkaTemplate deserialize it correctly?**

### Best Answer

> "I would use `RequestReplyTypedMessageFuture` together with `ParameterizedTypeReference<List<Payment>>`. This preserves the generic type information so Spring can correctly deserialize the JSON reply into a `List<Payment>`."

---

# 📌 Key Points to Remember

* **`replyErrorChecker()`** converts business-error replies into exceptions.
* **`ErrorHandlingDeserializer`** helps handle deserialization failures safely.
* **`KafkaHeaders.REPLY_TOPIC`** tells the consumer where to send the reply.
* **`KafkaHeaders.REPLY_PARTITION`** controls which partition receives the reply.
* **Shared Reply Topics** allow multiple clients to use the same reply topic, relying on **Correlation IDs** to match responses.
* **`sendAndReceive(Message<?>)`** integrates ReplyingKafkaTemplate with Spring Messaging.
* **`RequestReplyTypedMessageFuture`** supports strongly typed replies such as custom objects and generic collections.
* **`ParameterizedTypeReference`** is required for generic reply types like `List<Order>`.

# Interview Questions

## Q1. What is AggregatingReplyingKafkaTemplate?

**Answer:**

It is a Spring Kafka template that implements the **Scatter-Gather** pattern by collecting replies from multiple consumers for a single request.

---

## Q2. Why do we need AggregatingReplyingKafkaTemplate?

**Answer:**

Because `ReplyingKafkaTemplate` supports only one reply, whereas some business scenarios require collecting replies from multiple services before proceeding.

---

## Q3. What is Scatter-Gather?

**Answer:**

Scatter means sending one request to multiple consumers, and Gather means collecting all their replies before returning the final result.

---

## Q4. What is `releaseStrategy`?

**Answer:**

It is a predicate that decides when enough replies have been received and the aggregated future can be completed.

---

## Q5. What is `returnPartialOnTimeout`?

**Answer:**

If enabled, the template returns the replies received before the timeout instead of throwing a timeout exception.

---

## Q6. Why does AggregatingReplyingKafkaTemplate require manual acknowledgment?

**Answer:**

To prevent losing reply messages while there are still outstanding requests waiting for additional replies.

---

## Q7. What are `aggregatedResults` and `partialResultsAfterTimeout`?

**Answer:**

They are internal pseudo-topic names used by Spring to indicate whether the replies are complete or partial after a timeout. They are **not actual Kafka topics**.

---

# ⭐ Real Interview Scenario

### Interviewer:

**You need approval from Fraud Service, Credit Service, and KYC Service before approving a loan. Which Spring Kafka component will you use?**

### Best Answer

> "I would use `AggregatingReplyingKafkaTemplate` because it supports the Scatter-Gather pattern. The Loan Service sends one request, receives replies from all three services, uses a `releaseStrategy` to determine when all required replies have arrived, and can optionally enable `returnPartialOnTimeout` if partial results are acceptable."

---

# 📌 Key Points to Remember

* `AggregatingReplyingKafkaTemplate` implements the **Scatter-Gather** pattern.
* It is used when **one request requires multiple replies**.
* `releaseStrategy` decides when to complete the aggregated result.
* `returnPartialOnTimeout=true` returns available replies instead of throwing a timeout exception.
* The returned value contains a **collection of ConsumerRecords**, not a single reply.
* It requires **manual acknowledgment** (`AckMode.MANUAL` or `MANUAL_IMMEDIATE`) with `enable.auto.commit=false`.
* Spring uses **`aggregatedResults`** and **`partialResultsAfterTimeout`** as internal pseudo-topic names.
