
This will start the Kafka broker on port **9092** (default).

# 🦁 **ZooKeeper kya hai? (Simple Definition)**

**ZooKeeper = Kafka ka coordination manager.**
Kafka ke multiple brokers ko **milkar kaam karne** me help karta tha.

Kafka ke cluster me jab **multiple brokers** hote the,
to unko manage karna, unko sync me rakhna — ye kaam **ZooKeeper** karta tha.

---

# 🎯 **ZooKeeper kis liye use hota tha?**

# 1️⃣ **Leader Election**

Topic ke har partition ka ek **leader broker** hota hai.

ZooKeeper decide karta tha:

✔ Kaun leader hoga
✔ Kaun follower hoga
✔ Leader down ho jaye to naya leader kaun banega

---

# 2️⃣ **Cluster Metadata Store**

ZooKeeper store karta tha:

✔ Kitne brokers hain
✔ Brokers ke IP
✔ Kaun sa broker alive hai
✔ Kaun sa broker dead hai
✔ Kaun sa partition kahan stored hai

Isse Kafka cluster stable rehta tha.

---

# 3️⃣ **Broker Health Monitoring**

ZooKeeper har broker ko "heartbeat" bhejta tha.

If heartbeat missing → ZooKeeper bolta:

```
Broker dead
```

Fir:

✔ Naya leader select hota
✔ Cluster continue run hota
✔ Data loss nahi hota

---

# 4️⃣ **Topic Configuration Management**

ZooKeeper me topic ki information hoti thi:

* partitions
* replication factor
* assignment
* ISR list

Kafka is info ko use karke cluster manage karta tha.

---

# 5️⃣ **Distributed Locking**

Kafka me bahut saare brokers ek hi resource ko access karte hain.
ZooKeeper ensure karta tha:

✔ data corruption na ho
✔ ek time par ek hi broker important update kare

---

# 🧠 **Simple Real-World Analogy**

**ZooKeeper = Class monitor**
**Kafka brokers = Students**

Monitor:

* attendance check karta hai
* dekhta hai kaun baitha, kaun gaya
* teacher aane tak discipline maintain karta hai
* agar ek student leader chala jaye → naya leader assign karta hai

# ❗ Important Update (Interview Point)

Since **Kafka 2.8** and officially from **Kafka 3.3+**,
Kafka ne **ZooKeeper ko replace kar diya** apne **KRaft protocol** se.

✔ Now Kafka can run *without ZooKeeper*
✔ Kafka is now self-managed
✔ Zookeeper is **deprecated**
✔ Future Kafka completely ZooKeeper-free hai

---

# 📌 Why Kafka removed ZooKeeper?

* Performance bottleneck
* Multi-node management complex
* Too many network round trips
* Not cloud scalable
* Additional component to maintain

So Kafka introduced:

### **KRaft = Kafka Raft Metadata Mode**

Which does:

✔ Leader election
✔ Metadata management
✔ Broker health checks
✔ Topic management

**all inside Kafka — no ZooKeeper required**

---

# 🟦 Summary

| Feature                | ZooKeeper Role           |
| ---------------------- | ------------------------ |
| Leader election        | ✔ Yes                    |
| Broker tracking        | ✔ Yes                    |
| Metadata store         | ✔ Yes                    |
| Cluster coordination   | ✔ Yes                    |
| Topic/partition info   | ✔ Yes                    |
| Required in new Kafka? | ❌ No (KRaft replaces it) |

Kafka cluster में **load distribution** एक बहुत ही important concept है।
Simple भाषा में समझाता हूँ कि **1 cluster में multiple brokers कैसे load share करते हैं**।

# ⭐ **Kafka Cluster = Multiple Brokers + Multiple Partitions**

Load distribution **partition level पर होती है**, broker level पर नहीं।

## ✔ Producer messages → **Partitions** में जाते हैं

## ✔ Partitions → अलग-अलग **brokers** पर stored होते हैं

इससे **load automatically distribute हो जाता है**।

---

# 🟢 **1. Load distribution कैसे होता है?**

Kafka **partitions** को automatically different brokers पर spread कर देता है।

### Example:

Cluster में **3 brokers** हैं:

| Broker   | Responsibility             |
| -------- | -------------------------- |
| Broker 1 | कुछ partitions store करेगा |
| Broker 2 | कुछ partitions store करेगा |
| Broker 3 | कुछ partitions store करेगा |

---

# ⚙ Example Topic Setup

Topic: **orders**
Partitions: **3**

```
Partition 0 → Broker 1
Partition 1 → Broker 2
Partition 2 → Broker 3
```

Now when producers send data:

```
P0 → Broker 1
P1 → Broker 2
P2 → Broker 3
```

👉 **Load equally distributed**
👉 हर broker को उसका हिस्सा मिलता है
👉 कोई भी broker overloaded नहीं होता

---

# 🔥 **2. Producer Partitioning Logic (VERY IMPORTANT)**

Kafka producer तीन तरीकों से partitions select करता है:

---

### **A) Key-based Partitioning**

अगर message में key दी है:

```java
producer.send(new ProducerRecord("orders", "customerId", "value"))
```

Kafka ये formula use करता है:

```
partition = hash(key) % number_of_partitions
```

👉 Same key = always same partition
👉 Same partition = same broker
👉 Perfect ordering guaranteed for that key

---

### **B) Round-Robin (No Key)**

Agar key नहीं दी

Producer इस तरह distribute करता है:

```
P0 → P1 → P2 → P0 → P1 → P2 ...
```

यानी **fair load balancing** सभी brokers में।

---

### **C) Custom Partitioner**

Developer अपना logic लिख सकता है
(very rare but advanced feature)

---

# ⭐ **3. Replicas और Load Distribution**

Partition के दो role होते हैं:

| Role                   | Job                |
| ---------------------- | ------------------ |
| **Leader**             | All reads + writes |
| **Follower (Replica)** | Data backup        |

Only **leader broker** पर load होता है.

Example:

```
Partition 1 → Leader: Broker 2, Replica: Broker 3
```

Producer/Consumer always → Leader: Broker 2
Follower केवल backup copy बनाता है।

---

# 🧠 **4. Broker Failure में load कैसे redistribute होता है?**

Agar Broker 2 crash हो जाए:

```
Partition 1 → New Leader = Broker 3
```

Automatically — no downtime.

Load shift हो जाता है:

```
Producer/Consumer now use Broker 3
```

---

```
Kafka topic = multiple partitions
Partitions = distributed across brokers
Producer sends data to different partitions
Each partition is handled by different broker
Result → Load balancing
```

Kafka **impossible** to run.

# ✅ **1️⃣ Multiple Consumers (same application me)**

Agar aap **same Spring Boot app me 2 ya zyada consumers** rakhna chahte ho →
बस 2 `@KafkaListener` methods bana दो।

### ✔ Example:

```java
@Service
public class WeatherConsumers {

    @KafkaListener(topics = "weather-data", groupId = "weather-group")
    public void consumerA(String msg) {
        System.out.println("Consumer A -> " + msg);
    }

    @KafkaListener(topics = "weather-data", groupId = "weather-group")
    public void consumerB(String msg) {
        System.out.println("Consumer B -> " + msg);
    }
}
```

### ❗Important:

* SAME **groupId = messages load-balance hota hai**
  → मतलब Consumer A aur B **divide** karke messages lenge (50–50 approx)

* Agar topic ke **only 1 partition** hai →
  ✔ केवल **1 consumer hi active** होगा
  ❌ दूसरा idle रहेगा
  (Kafka rule: **1 partition = 1 active consumer per group**)

# ✅ **2️⃣ Multiple Consumers (alag-alag applications)**

Agar aap 2 alag Spring Boot apps chalaoge:

```
App1 → groupId: weather-group
App2 → groupId: weather-group
```

→ Kafka messages **load-balance** karega dono me.

---

# ✅ **3️⃣ Broadcast (ALL consumers ko same message mile)**

Agar aap chahte ho ki sab consumers ko **same message** mile →
हर consumer ko **different groupId** do।

### Example:

```java
@KafkaListener(topics = "weather-data", groupId = "group-1")
public void consumer1(String msg) { ... }

@KafkaListener(topics = "weather-data", groupId = "group-2")
public void consumer2(String msg) { ... }
```

### Result:

* consumer1 → sab messages
* consumer2 → sab messages
* consumer3 → sab messages

मतलब **broadcast** mode.

# 🟢 **Partition-Based Parallel Consumers (Best practice)**

Agar load zyada hai, to topic me partitions banao:

```bash
kafka-topics.sh --alter --topic weather-data --partitions 3 --bootstrap-server 172.x.x.x:9092
```

Then same group me 3 consumers chalao:

✔ Kafka automatically parallel processing karega
✔ Har consumer ek alag partition handle karega

* सारे messages sequential आते हैं
* Speed slow

* Messages multiple lanes में divide होते हैं

# 🔥 **Benefits of Multiple Partitions for Consumers**

## **1️⃣ Parallel Processing (Fast speed)**

1 partition → 1 consumer
3 partitions → 3 consumers
10 partitions → 10 consumers

More partitions = more consumers = more throughput.

Example:

* Partition 0 → Consumer 1
* Partition 1 → Consumer 2
* Partition 2 → Consumer 3

All 3 read messages **at the same time**.

---

## **2️⃣ High Throughput**

If millions of messages aa rahe ho →
Single consumer handle नहीं कर सकता।

Multiple partitions allow **multiple JVM / services** to process data fast.

---

## **3️⃣ Load Balancing**

Kafka automatically distribute karta hai:

* Partition 0 → Consumer A
* Partition 1 → Consumer B
* Partition 2 → Consumer C

Koi consumer overload nahi hota.

---

## **4️⃣ Fault Tolerance**

If one consumer down हो जाए:

* Kafka उसकी partition kisi aur consumer ko assign कर देता है

App crash bhi ho जाए → system रुकेगा नहीं।

---

## **5️⃣ Horizontal Scaling (Unlimited growth)**

Aap number of consumers बढ़ा सकते हो:

* App1
* App2
* App3
* App4

जितनी ज़रूरत उतना scale करो.

---

## **6️⃣ Faster Catch-Up**

If backlog (100k messages) है
Multiple consumers जल्दी process करके backlog खत्म करेंगे।

Single partition → घंटों लग सकते हैं
Multiple partitions → minutes में साफ

# ⭐ RestTemplate — All Important Methods & Their Uses

---

# **1) `getForObject()`**

### 👉 **GET request → Direct body return करता है**

```java
<T> T getForObject(String url, Class<T> responseType)
```

### Use:

* जब आपको केवल **response body** चाहिए
* Status code important नहीं है

### Example:

```java
String result = restTemplate.getForObject(url, String.class);
```

---

# **2) `getForEntity()`**

### 👉 **GET request → Full Response देता है (status + headers + body)**

```java
ResponseEntity<T> getForEntity(String url, Class<T> responseType)
```

### Use:

* जब आप **status code, headers, body** सब check करना चाहते हो

### Example:

```java
ResponseEntity<String> response = restTemplate.getForEntity(url, String.class);
```

---

# **3) `postForObject()`**

### 👉 **POST request → body return**

```java
<T> T postForObject(String url, Object request, Class<T> responseType)
```

### Use:

* Simple POST request
* Response body चाहिए

### Example:

```java
User user = restTemplate.postForObject(url, newUser, User.class);
```

---

# **4) `postForEntity()`**

### 👉 **POST request → full response**

```java
ResponseEntity<T> postForEntity(String url, Object request, Class<T> responseType)
```

### Use:

* Response code + headers भी important हों

---

# **5) `postForLocation()`**

### 👉 **POST request → Creates resource → Returns location URI**

```java
URI location = restTemplate.postForLocation(url, newUser);
```

### Use:

* REST APIs me new resource create karte time
* API "Location" header bhejti hai → new resource ka URL

---

# **6) `put()`**

### 👉 **PUT request (no return)**

```java
void put(String url, Object request)
```

### Use:

* Data update karna
* Response body API nahi bhejti

### Example:

```java
restTemplate.put(url, updatedUser);
```

---

# **7) `delete()`**

### 👉 **DELETE request**

```java
void delete(String url)
```

### Use:

* Record delete karna

### Example:

```java
restTemplate.delete(url + "/1");
```

---

# **8) `exchange()` → MOST POWERFUL METHOD**

### 👉 Any HTTP method (GET/POST/PUT/DELETE/PATCH)

```java
ResponseEntity<T> exchange(
        String url,
        HttpMethod method,
        HttpEntity<?> requestEntity,
        Class<T> responseType)
```

### Use:

* Headers + Body + Method sab customize करना है
* JWT token bhejna है
* Custom headers bhejne हैं

### Example:

```java
HttpHeaders headers = new HttpHeaders();
headers.set("Authorization", "Bearer token");
HttpEntity<?> entity = new HttpEntity<>(headers);

ResponseEntity<String> response =
        restTemplate.exchange(url, HttpMethod.GET, entity, String.class);
```

---

# **9) `execute()` → Lowest level method**

### 👉 Full control over request (rarely used)

```java
<T> T execute(String url, HttpMethod method, RequestCallback callback, ResponseExtractor<T> extractor)
```

### Use:

* Raw control over request
* Custom logic (file download, streaming)

Kafka me **key** bohot important hota hai.
Aapko simple language me samjhata hoon:

---

# 🟦 **Kafka key kya karta hai?**

**Kafka key = message ka address**
Jisse Kafka decide karta hai ki message **kis partition** me jayega.

---

# 🟧 **Key ka main kaam: Partitioning**

Kafka topic me multiple partitions hote hain:

```
topic partitions:
P0 | P1 | P2 | P3 | ...
```

Jab aap message send karte ho:

```java
kafkaTemplate.send("topic", "myKey", data);
```

To Kafka yeh karta hai:

👉 `"myKey".hashCode()` compute karta hai
👉 Partition = hash % number_of_partitions
👉 Message **always** same partition me jayega

---

# ⭐ Simple Example

Agar aap 3 messages same key se bhejte ho:

```java
send("device-101", "data1");
send("device-101", "data2");
send("device-101", "data3");
```

Sab 3 messages **same partition** me jayenge.

---

# 🟢 **Why is this useful?**

## 1️⃣ **Ordering guarantee**

Same key → same partition
Same partition → strict ordering

Example:

```
device-101 reading #1
device-101 reading #2
device-101 reading #3
```

Consumer ko same order me milenge.

---

## 2️⃣ **Load Balancing**

Different keys → different partitions
Kafka load ko spread kar deta hai.

Example:

```
Key: device-101 → P0
Key: device-102 → P1
Key: device-103 → P2
```

---

## 3️⃣ **Grouped data**

Consumer ek specific device/user/group ka data logically group kar sakta hai.

---

# 🟩 **Real-World Example – Weather / IoT**

### Case 1: Same device ka data

Key = deviceId

```java
kafkaTemplate.send("weather-topic", deviceId, jsonData);
```

Device-1 → always same partition
Device-2 → same partition
Device-3 → same partition

Ordering perfect.

---

### Case 2: Plant data

Key = plantId

```java
kafkaTemplate.send("plant-topic", plantId, plantJson);
```

Plant-wise ordering guaranteed.

---

# 🟣 **Consumer Benefits**

Consumer can do:

* per-device processing
* per-plant batch
* per-user analytics
* stateful processing

Because all messages of same key come to **same consumer instance**.

`groupId` Kafka ka **bahut important concept** hai.
Main aapko **simple language + real examples** se samjhaata hoon.

---

# 🟦 **groupId kya hota hai?**

**Kafka Consumer Group ka naam** hai.

Example:

```java
@KafkaListener(
    topics = "havells-plant-topic",
    groupId = "havells-group"
)
```

Yani is consumer ka group name = `havells-group`

---

# 🟩 **groupId ka main kaam kya hai?**

## ✔ 1. **Load Balancing**

Agar ek topic ke multiple consumers same groupId use karte hain:

```
Group: havells-group
Consumers: C1, C2, C3
```

To Kafka partitions ko consumers me distribute karega:

```
Partition 0 → C1
Partition 1 → C2
Partition 2 → C3
```

Ye **parallel processing** create karta hai.

---

## ✔ 2. **Each message is processed ONCE per group**

Agar 3 consumer groups hai:

* group-A
* group-B
* group-C

To **har group ko message milega**, but group ke andar sirf **1 baar process hoga**.

---

## ✔ 3. **Offset Management**

groupId batata hai:

* is group ne kaha tak messages consume kiye
* kis offset tak padh liya
* restart hone par kaha se resume kare

Kafka **offset store karta hai per group**.

---

# 🟧 **Real Example 1: Plant Data Processing**

### Producer sends a lot of plant messages:

```
havells-plant-topic
```

### You start 3 consumer instances:

```java
groupId = "plant-processors"
```

Kafka karega:

* Consumer-1 → some partitions
* Consumer-2 → some partitions
* Consumer-3 → some partitions

💡 **High-speed processing**

---

# 🟧 **Real Example 2: 2 Apps Want Same Data**

App-1: Billing calculation
App-2: Weather analytics

Agar dono same topic ko listen karte hain,
but **different groupId** se:

```java
groupId = "billing-group"
groupId = "analytics-group"
```

To:

✔ Billing app ko messages milenge
✔ Analytics app ko messages milenge
✔ Dono ko **independent copies** milengi

Kafka **message ko duplicate nahi karta**,
group ke hisab se deliver hota hai.

---

# 🟥 **IMPORTANT: Common mistake**

Agar aap 2 consumers ko **same groupId** de dete ho
but **data alag chahiye**:

❌ A consumer will miss data
❌ Because Kafka load-balance karega, duplicate nahi bhejega
