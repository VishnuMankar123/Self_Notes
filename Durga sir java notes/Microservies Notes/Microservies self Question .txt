Great question! Let’s explain **Service Discovery** in simple words:

---

### 🔍 **What is Service Discovery?**

In **microservices architecture**, there are **many small services** running (like user-service, order-service, payment-service, etc.).  
These services often **change IP addresses and ports**, especially in cloud or container environments.

So... how do services **find and talk to each other**?

That’s where **Service Discovery** comes in!

---

### 💬 Simple Definition:

> **Service Discovery** is a way for services to **register themselves** and **find other services** without hardcoding their locations (IP/port).

---

### 🧠 Real-Life Analogy:

Imagine a company where employees don’t know each other’s phone numbers.

So, there's a **central contact directory** (like a receptionist or phonebook).

- Each employee **registers** their contact info with the receptionist.
- When someone wants to talk to another employee, they **ask the receptionist** for the contact info.

That's exactly what **Service Discovery** does!

---

### 🔧 In Spring Boot:
- **Eureka Server** = the directory (service registry)
- **Microservices** = employees
- They use **Eureka Client** to register and discover

---

### 📦 Benefits:
- No hardcoding of URLs
- Automatic service registration/deregistration
- Load balancing becomes easier
- Works well with dynamic environments (e.g., Docker, Kubernetes)

### 💬 Meaning:
> **Should this service download (fetch) the list of other services** from the Eureka server?

### ✅ If `true`:

### ❌ If `false`:  
- Your service **won’t fetch** other services — it can’t discover them.

---

### 🔧 Example:
```properties
eureka.client.fetch-registry=true
```
➡️ This is needed if your service **wants to call other services**.

Great follow-up! Let's see **how Service A and B find each other through Eureka** — without hardcoding URLs.

---

### 🔧 How do services find each other using Eureka?

#### 🔁 Step-by-Step Flow:

1. **Services register with Eureka Server**:
   - Service A (e.g., `user-service`)
   - Service B (e.g., `order-service`)
   - Each service sends its **name, port, and IP** to the Eureka server.

2. **Services fetch the registry**:
   - By default, each service fetches the full list of all registered services (this is what `eureka.client.fetch-registry=true` does).
   - So now each service knows about the others' location (host, port, etc.).

3. **Service A calls Service B using service name**:
   - Instead of calling a hardcoded URL like `http://localhost:8082/api/order`,
   - It calls:  
     ```
     http://ORDER-SERVICE/api/order
     ```
   - Spring Cloud + Eureka + Ribbon (or Spring Cloud LoadBalancer) will:
     - Look up `ORDER-SERVICE` in the Eureka registry
     - Get the correct IP and port
     - Call the correct instance (even if there are multiple)

---

### 🧩 Required Setup for This to Work:

#### ✅ 1. In `application.properties` of Service A:
```properties
spring.application.name=USER-SERVICE
eureka.client.service-url.defaultZone=http://localhost:8761/eureka
```

#### ✅ 2. In `application.properties` of Service B:
```properties
spring.application.name=ORDER-SERVICE
eureka.client.service-url.defaultZone=http://localhost:8761/eureka
```

#### ✅ 3. Use **RestTemplate** or **WebClient** with service name:

##### Example with `RestTemplate`:
```java
@Autowired
private RestTemplate restTemplate;

public String getOrderDetails() {
    String url = "http://ORDER-SERVICE/api/order/123";
    return restTemplate.getForObject(url, String.class);
}
```

> 🔁 Spring will automatically resolve `ORDER-SERVICE` to the real IP and port from Eureka registry.

---

### 📌 Summary

- Services **register** and **discover** using Eureka.
- No need to write fixed IP/port.
- Calls are made using **service names** (like `http://ORDER-SERVICE`).
- Eureka + Spring Cloud handles everything behind the scenes.

---

### 🔐 1. `management.security.enabled=false`

**What it means:**  
This **disables security** for the **Actuator endpoints** (like `/actuator/health`, `/actuator/metrics`, etc.)

**Why it's used:**  
By default, Spring Boot protects these endpoints with basic authentication.  
If you're just testing or in development, you might want to **turn off the security**.

**Example:**
- Without this: Accessing `http://localhost:8080/actuator/health` asks for username & password.
- With this: You can access it directly without login.

**⚠️ Warning:** Don't use this in production unless you secure the endpoints by some other means (like firewall, VPN, or token-based auth).

---

### 🌐 2. `management.endpoints.web.exposure.include=*`

**What it means:**  
This makes **all actuator endpoints available over HTTP**.

**Why it's used:**  
By default, Spring Boot only exposes a few endpoints like `/actuator/health` and `/actuator/info`.  
This setting says: “Expose **everything**, like `/metrics`, `/env`, `/beans`, etc.”

**Example:**
```properties
management.endpoints.web.exposure.include=health,info
```
→ Only exposes `/actuator/health` and `/actuator/info`

```properties
management.endpoints.web.exposure.include=*
```
→ Exposes **all** available actuator endpoints

---

### 🌍 3. `spring.boot.admin.url=http://localhost:9090/`

**What it means:**  
This tells the **Spring Boot Admin Client** (your microservice) where the **Admin Server** is running.

**Why it's used:**  
Your microservice needs to **register itself** to the Admin Server so that it can be monitored.

**Example:**
- If your **Admin Server** is running on port 9090, this URL points to it.
- Your microservice will connect to this Admin Server and send health and status info.

Sure! In **Java microservices architecture**, an **API Gateway** is a **single entry point** for all clients to interact with the backend microservices.
 Think of it as a front door to your system that **routes requests**, **handles authentication**, **performs rate limiting**, and **aggregates data** from multiple services.

---

### 🔧 Key Responsibilities of an API Gateway

1. **Routing**  
   Directs requests to the appropriate microservice based on the URL or request metadata.

2. **Authentication and Authorization**  
   Validates tokens (e.g., JWT) and ensures users have permission to access specific services.

3. **Rate Limiting and Throttling**  
   Controls how many requests are allowed from a client over time.

4. **Load Balancing**  
   Distributes requests among multiple instances of a microservice.

5. **Response Aggregation**  
   Combines responses from multiple microservices into a single one (e.g., for a dashboard UI).

6. **Security**  
   Hides internal microservice details and helps prevent direct access from external users.

---

### ✅ Popular API Gateway Tools in Java Ecosystem

- **Spring Cloud Gateway** – Reactive and built on Spring WebFlux; great with Spring Boot.
- **Zuul** (Netflix) – Older, but still used in some projects.
- **Kong / Ambassador / NGINX** – Language-agnostic API gateways that also work well with Java services.
- **AWS API Gateway** – Useful if you're hosting microservices in AWS.

---

### 💡 Example: Using Spring Cloud Gateway

```yaml
# application.yml
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: http://localhost:8081/
          predicates:
            - Path=/users/**
        - id: order-service
          uri: http://localhost:8082/
          predicates:
            - Path=/orders/**
```

Above config:
- Routes `/users/**` to `user-service`
- Routes `/orders/**` to `order-service`

```java
@Configuration

    @Bean
    public RouteLocator routes(RouteLocatorBuilder builder) {
        return builder.routes()

                .route("order-service", r -> r.path("/orders/**")

    }
}
```

Great question! In a Java microservices architecture, a **Config Server** is used to **centralize configuration management** for all your microservices.
 It ensures that configuration files (like `application.yml`) are managed in one place—usually stored in a **Git repository**—and all services fetch their configs from there.

---

### 🔧 Why Use a Config Server?

- Centralized configuration for all environments (dev, test, prod)
- Dynamic refresh of configurations without restarting services
- Version-controlled configs (using Git)
- Separation of config from code
- Easier to manage secrets and profiles (e.g., `application-dev.yml`, `application-prod.yml`)

---

### ✅ Tool: **Spring Cloud Config Server**

---

### 🔁 How It Works

1. Store config files in a Git repo.
2. Set up a Spring Boot app as a Config Server.
3. Other microservices (clients) fetch config values from the Config Server.

---

### 🛠 Step-by-Step Setup

#### 1. **Create the Config Server**

**`pom.xml`**

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-config-server</artifactId>
</dependency>
```

**`@SpringBootApplication` with `@EnableConfigServer`**

```java
@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
  public static void main(String[] args) {
    SpringApplication.run(ConfigServerApplication.class, args);
  }
}
```

**`application.yml`**

```yaml
server:
  port: 8888

spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/your-org/config-repo
          default-label: main
```

---

#### 2. **Create Config Files in Git Repo**

For example:
- `user-service-dev.yml`
- `order-service-prod.yml`
- `application.yml` (shared config)

---

#### 3. **Set Up a Client Microservice**

**`bootstrap.yml`**

```yaml
spring:
  application:
    name: user-service
  cloud:
    config:
      uri: http://localhost:8888
  profiles:
    active: dev
```

**Dependencies**

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-config</artifactId>
</dependency>
```

## 🌐 1️⃣ `/actuator/refresh` kya karta hai?

Jab aapka microservice **Spring Cloud Config Server** se configuration values le raha hota hai (for example from `application.yml` in Git),
to by default ye values **application startup** ke time load hoti hain.

Agar aap Git repo me configuration change kar do,
to woh change **automatically** running microservice me **reflect nahi hota**.

To changes apply karne ke liye,
aapko `/actuator/refresh` **endpoint** hit karna padta hai 👇

---

## ⚙️ 2️⃣ Working (Step-by-step)

1. **Config Server** me `application.yml` ya Git file change hoti hai

2. **Client Microservice** (jo Config Server se config le raha hai) pe request bhejte ho:

   ```
   POST http://<client-service-host>:<port>/actuator/refresh
   ```

3. Spring Cloud Config client:

   * Config Server se nayi configuration fetch karta hai
   * Updated properties ko **Spring Environment** me reload karta hai
   * Beans marked with `@RefreshScope` ko reinitialize karta hai

---

## 🧩 3️⃣ Example Setup

### 🔹 Config Server (application.yml)

```yaml
server:
  port: 8888

spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/vishnudas/config-repo
```

### 🔹 Microservice Client (application.yml)

```yaml
spring:
  application:
    name: order-service

  cloud:
    config:
      uri: http://localhost:8888
```

### 🔹 Client Service Code

```java
@RestController
@RefreshScope   // 👈 Important
public class MessageController {

    @Value("${service.message}")
    private String message;

    @GetMapping("/msg")
    public String getMessage() {
        return message;
    }
}
```

---

## 📡 4️⃣ Refresh Process in Action

| Step | Action                                            | Result                                |
| ---- | ------------------------------------------------- | ------------------------------------- |
| 1    | Change `service.message` in Git config file       | Config Server updated                 |
| 2    | Run `git push`                                    | Config Server now has new value       |
| 3    | Run `POST http://localhost:8081/actuator/refresh` | Client microservice re-fetches config |
| 4    | Call `/msg` endpoint again                        | You’ll get the **new value** ✅        |

---

## 🔒 5️⃣ Important Notes

* `/actuator/refresh` is **POST** method (not GET).
* You must **enable it explicitly** in `application.yml`:

  ```yaml
  management:
    endpoints:
      web:
        exposure:
          include: refresh
  ```
* Only beans annotated with `@RefreshScope` will get reloaded.
* You can also refresh **all services at once** using **Spring Cloud Bus** with RabbitMQ or Kafka (`/actuator/busrefresh`).

---

## ⚖️ 6️⃣ `/actuator/refresh` vs `/actuator/busrefresh`

| Endpoint               | Used For                                | Affects                       |
| ---------------------- | --------------------------------------- | ----------------------------- |
| `/actuator/refresh`    | Refresh single microservice             | Only that instance            |
| `/actuator/busrefresh` | Refresh **all** connected microservices | All instances via message bus |

---

### 🔚 In Short:

👉 `/actuator/refresh`
= **Manual trigger** to reload latest configuration from Config Server **without restarting** the microservice.

## 🌱 1️⃣ "Spring Environment" kya hota hai?

Spring me **Environment** ek **interface** hai

jo application ke **configuration data** aur **profiles** ko manage karta hai.

Yani:

> Environment = Application ke configuration values + active profiles + property sources

---

## 🧩 2️⃣ Environment ka kaam kya hai?

Spring Environment ka main role hota hai:

1. **Property values manage karna**

   * Jaise `application.properties` / `application.yml` / system variables / environment variables sabse values leke store karna
   * Example:

     ```yaml
     server.port=8081
     service.message=Hello Vishnudas
     ```

     Ye dono values Spring Environment ke andar aa jaati hain.

2. **Profiles handle karna**

   * Jaise `dev`, `test`, `prod` profiles
   * `Environment` decide karta hai kaunsa profile active hai.

3. **Beans ko config values dena**

   * Jab tum `@Value("${service.message}")` likhte ho
     → Spring Environment se value uthata hai aur inject karta hai.

---

## ⚙️ 3️⃣ Internally kaise kaam karta hai?

Spring jab start hota hai:

1. `application.yml` / `application.properties` padhta hai
2. OS ke environment variables, system properties, aur Config Server se aayi values bhi add karta hai
3. Sabko ek **PropertySource list** me rakhta hai
4. Ye sab Environment object ke andar store hota hai

### Example:

```java
@Autowired
private Environment env;

public void show() {
    System.out.println(env.getProperty("server.port")); // prints 8081
    System.out.println(env.getActiveProfiles()); // e.g., ["dev"]
}
```

---

## 🌀 4️⃣ `/actuator/refresh` ke time kya hota hai?

Jab tum `/actuator/refresh` hit karte ho:

1. Spring Cloud Config client **Config Server** se nayi properties fetch karta hai
2. Spring Environment ke andar existing property values **replace** hoti hain
3. Jitne bhi beans `@RefreshScope` me hain → unka naya instance banta hai
   (taaki naye Environment se updated values mil sake)

Config Server priority:

1. `user-service-dev.yml`
2. `user-service.yml`
3. `application-dev.yml`
4. `application.yml`

* **application name** → `spring.application.name` से आता है।
* **profile** → `spring.profiles.active` से आता है।
* दोनों मिलकर तय करते हैं कौन सी config file load होगी।

 @RefreshScope क्या है?
👉 @RefreshScope एक Spring Cloud annotation है।
👉 इसका काम है: कोई bean runtime में नई configuration values के साथ reload करना, बिना पूरा application restart किए।

🔍 कहां काम आता है?
आपका microservice किसी external configuration server (जैसे Spring Cloud Config Server) से config values लेता है:

जैसे database URL, feature flag, discount percentage, API key वगैरह।

अगर ये config आपको runtime में बदलनी हो — तो आप @RefreshScope लगाकर bean को dynamic reconfiguration के लिए eligible बना देते हैं।

✅ Use Case
बिना @RefreshScope	क्या होगा?
आप config value change करोगे	लेकिन app को restart करना पड़ेगा
या फिर नई value pick नहीं होगी	

@RefreshScope लगाकर	क्या होगा?
Config Server से नई value आएगी	/actuator/refresh endpoint को call करोगे
Annotated beans re-create होंगे	नई value apply हो जाएगी — app restart नहीं करना पड़ेगा

✅ कैसे काम करता है?
1️⃣ आप किसी bean (जैसे Controller या Service) पर @RefreshScope लगाते हो।
2️⃣ Bean में @Value या @ConfigurationProperties से config inject करते हो।
3️⃣ जब config server से कोई नई value आती है, तो आप /actuator/refresh endpoint को hit करते हो।
4️⃣ Spring Cloud context उस bean को destroy करके नया bean बनाता है — और नई value apply हो जाती है।

Great question! The `@RefreshScope` annotation is part of **Spring Cloud** and is used to make a Spring bean **refreshable at runtime** when configuration changes in the **Config Server**.

---

## 🌀 What Does `@RefreshScope` Do?

Normally, Spring beans are initialized **once** when the application starts. If a config property changes in the **Config Server**, your application won’t pick it up **unless you restart** the app.

✅ But with `@RefreshScope`, you can **refresh the bean dynamically** using:

```
POST /actuator/refresh
```

---

## 📦 How It Works

- You annotate any class (usually a controller or service) with `@RefreshScope`
- The bean will be reloaded when you trigger the `/actuator/refresh` endpoint
- The new value from the Config Server is injected at runtime

---

### 🔧 Example

#### `user-service-dev.yml` (in Git repo)

```yaml
welcome.message: Hello from Dev Config
```

#### `UserController.java`

```java
@RestController
@RefreshScope
public class UserController {

    @Value("${welcome.message}")
    private String welcomeMessage;

    @GetMapping("/welcome")
    public String getMessage() {
        return welcomeMessage;
    }
}
```

1. Start the app, hit `/welcome` → See "Hello from Dev Config"
2. Change the config in Git to:

```yaml
welcome.message: Updated Welcome Message!
```

3. Run:
```bash
curl -X POST http://localhost:8081/actuator/refresh
```

4. Again visit `/welcome` → See "Updated Welcome Message!" ✅

---

## ⚠️ Without `@RefreshScope`

- The bean won’t re-fetch the new config.
- You’ll need to **restart** the application to apply config changes.

The `/actuator/refresh` endpoint is used by the **Spring Cloud Actuator** to trigger a **refresh of the configuration** in your application. It can be called by anyone (like a service, admin, or automated system) to **reload the configuration properties** from the **Config Server** without restarting the application.

### When and Who Calls `/actuator/refresh`?

Here are some common use cases for this endpoint:

1. **Manual Trigger (Admin/Developer)**
   - If an admin or developer wants to manually apply new configurations without restarting the service, they can call the `/actuator/refresh` endpoint using **curl**, **Postman**, or any HTTP client.
   - Example command:
     ```bash
     curl -X POST http://localhost:8081/actuator/refresh
     ```
   
2. **Automated Trigger (System)**
   - Some systems might want to automatically trigger the refresh when they detect changes in the configuration. This can be done using monitoring tools or scheduled tasks (like **Cron** jobs).

3. **Integration with Spring Cloud Bus**
   - In a more advanced setup, **Spring Cloud Bus** can be used to automatically refresh configuration across multiple instances of a service.
   - The bus can listen for configuration change events and broadcast a **refresh trigger** to all connected services.
   - For this, you would set up a message broker like **RabbitMQ** or **Kafka** to propagate configuration changes automatically.

### Example Scenario:
1. You change a configuration in the Git repository (e.g., `welcome.message` in `user-service-dev.yml`).
2. The `/actuator/refresh` endpoint is triggered, either manually or automatically.
3. Spring Cloud reads the new configuration from the Config Server and updates the relevant beans in the app with the new values.

### Example with Manual Trigger:
After a configuration change in the Git repo, you can manually invoke the `/actuator/refresh` endpoint via `curl`:
```bash
curl -X POST http://localhost:8081/actuator/refresh
```

### 🌩️ What is **Spring Cloud Config Server**?

**Spring Cloud Config Server** is a **centralized configuration management service** for **Spring Boot microservices**. It allows you to manage all your application configurations **in one place** (like a Git repo), rather than in each individual app.

---

| Feature                         | Explanation |
|----------------------------------|-------------|

| 🔐 Supports encryption           | Secure sensitive values like passwords or API keys |
| 🌍 Environment profiles          | Separate config files for `dev`, `test`, `prod`, etc. |
| 🔄 Versioned config              | Since config is in Git, you can track history and roll back |

`@LoadBalanced` annotation Spring Cloud ka ek feature hai jo `RestTemplate` ya `WebClient` ko client-side load balancing ke liye use kiya jata hai.

### 🔧 Use Case:

Agar aap microservices architecture mein kaam kar rahe ho, aur ek service dusre service ko call kar rahi hai (via service name like `http://product-service`), to `@LoadBalanced` help karta hai **Eureka/Discovery Server** ke through service instances ke beech me load distribute karne mein.

---

### ✅ Basic Example with `RestTemplate`:

```java
@Configuration
public class AppConfig {

    @Bean
    @LoadBalanced // 👈 Yeh load balancing enable karta hai
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}
```

Then you can call other services like this:

```java
@Autowired
private RestTemplate restTemplate;

public Product getProduct() {
    return restTemplate.getForObject("http://product-service/products/101", Product.class);
}
```

📌 **Yaha `product-service` actual host/port nahi hai**, yeh ek **service name hai jo Eureka mein register hai**. `@LoadBalanced` ensure karta hai ki:

* `RestTemplate` ko Eureka se list of instances mile.
* Us list me se random ya round-robin se ek instance pick ho.
* Aur request us instance ko bheji jaye.

---

### 🧠 Internally kya hota hai?

* Spring `@LoadBalanced` ke through `RestTemplate` me ek interceptor inject karta hai.
* Yeh interceptor service name ko actual URL me resolve karta hai using service registry.
* Example: `http://product-service` → `http://localhost:8081` ya `http://localhost:8082` depending on load balancing strategy.

---

### ⚠️ Important Notes:

* `@LoadBalanced` kaam karta hai **only if** aap Spring Cloud Netflix Eureka, Consul, etc. use kar rahe ho.
* Agar aap sirf `RestTemplate` use karte ho bina `@LoadBalanced`, to service name resolve nahi hoga (error: UnknownHostException).

---

### 🆚 Alternatives:

* Spring Cloud LoadBalancer (`spring-cloud-starter-loadbalancer`) is newer than Ribbon (Ribbon is deprecated).
* Same annotation (`@LoadBalanced`) ab new LoadBalancer client me bhi use hota hai.

---

### Summary:

| Feature               | Description                                 |
| --------------------- | ------------------------------------------- |
| `@LoadBalanced`       | Client-side load balancing enable karta hai |
| Works with            | `RestTemplate`, `WebClient`                 |
| Requires              | Service discovery (Eureka, Consul)          |
| Resolves service name | Yes (e.g., `product-service` → instance)    |

## 🔄 Load Balancing kya hota hai?

Jab aapke paas **multiple instances** (copies) hon ek hi service ke — jaise:

| Service Name    | Instance | IP Address        |
| --------------- | -------- | ----------------- |
| product-service | 1        | 192.168.1.10:8081 |
| product-service | 2        | 192.168.1.11:8081 |
| product-service | 3        | 192.168.1.12:8081 |

To request ko randomly ya round-robin method se in instances me **distribute** karna hota hai — isse hi **load balancing** kehte hain.

---

## 🚦 Do Tarah ke Load Balancing:

| Type              | Kya karta hai                                                                       |
| ----------------- | ----------------------------------------------------------------------------------- |
| **Server-side**   | Load balancer server (like Nginx, HAProxy) request ko distribute karta hai          |
| **Client-side** ✅ | **Client (aapki app)** khud hi decision leti hai kis instance ko request bhejna hai |

---

## 🧠 Client-side Load Balancing kaise kaam karta hai?

1. Aap `product-service` ko call karna chahte ho.
2. Aap `RestTemplate` use kar rahe ho:

   ```java
   restTemplate.getForObject("http://product-service/products/101", Product.class);
   ```
3. Aapne `@LoadBalanced` lagaya hai.
4. Spring `product-service` ka naam **Eureka** (ya service registry) se resolve karta hai.
5. Eureka ke paas 3 instance hain — Spring unme se ek choose karta hai (random ya round-robin).
6. Fir usi instance ko request bhejti hai.

---

## 🖼️ Diagram:

```
Client App
   |
   |-----> Eureka (Service Registry)
             |
             |-----> product-service instance 1 (192.168.1.10:8081)
             |-----> product-service instance 2 (192.168.1.11:8081)
             |-----> product-service instance 3 (192.168.1.12:8081)
```

👉 `@LoadBalanced` use karne se **Client khud decide karta hai** kis instance pe request bhejna hai.

✅ What is RestTemplate in Spring Boot?
RestTemplate is a synchronous HTTP client provided by Spring to perform HTTP requests (GET, POST, PUT, DELETE, etc.) from your Java application to consume RESTful web services.
Think of it as a way for your Spring Boot app to call another API/server.
________________________________________
+----------------------+--------------+------------------------------------+
| Purpose              | HTTP Method  | Example Method                     |
+----------------------+--------------+------------------------------------+
| Get data from API    | GET          | getForObject(), getForEntity()     |
| Send data to API     | POST         | postForObject(), postForEntity()   |
| Update data on API   | PUT          | put()                              |
| Delete data          | DELETE       | delete()                           |
+----------------------+--------------+------------------------------------+
__________
✅ Example 1: GET Request
@RestController
public class MyController {

    @Autowired
    private RestTemplate restTemplate;

    @GetMapping("/get-user")
    public String getUser() {
        String url = "https://jsonplaceholder.typicode.com/users/1";
        String result = restTemplate.getForObject(url, String.class);
        return result;
    }
}
________________________________________
✅ Example 2: POST Request
@PostMapping("/add-user")
public String createUser() {
    String url = "https://example.com/api/users";
    User user = new User("John", "john@example.com");

    ResponseEntity<String> response = restTemplate.postForEntity(url, user, String.class);
    return response.getBody();
}

**In `pom.xml`:**

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>
```

---

### Step 2: Enable Feign in your application

```java
@SpringBootApplication
@EnableFeignClients
public class MyApplication { }
```

```java
@FeignClient(name = "product-service") // 👈 Eureka service name
public interface ProductClient {

    @GetMapping("/products/{id}")

}
```

### Step 4: Use the interface

```java
@Autowired
private ProductClient productClient;

public void someMethod() {
    Product p = productClient.getProductById(101L); // 👈 Direct method call
}
```

* या बहुत slow respond कर रहा है,
  तो `user-service` भी **hang / crash** हो सकता है।

👉 इसको रोकने के लिए हम **Circuit Breaker + Fallback** का इस्तेमाल करते हैं।

---

## ⚡ Circuit Breaker (Resilience4j)

> **Circuit Breaker** ek safety switch hai jo *failures detect* karta है और *further requests block* करता है ताकि system overload ना हो।

3 States होते हैं:

1. **Closed** (normal) → Calls allowed। अगर failures ज़्यादा हुए → Open।
2. **Open** → Calls block हो जाते हैं (direct fallback लौटेगा)।
3. **Half-Open** → कुछ calls फिर से allow करके test करता है कि service recover हुई या नहीं।

---

## 🔁 Fallback

> **Fallback** ek default response / backup plan है अगर main service fail हो जाती है।

जैसे:

* अगर `product-service` down है → तो `user-service` एक dummy product लौटा दे।
* इससे system टूटेगा नहीं और user को कुछ response फिर भी मिलेगा।

---

## 🔎 Property by Property

### 1. `registerHealthIndicator: true`

* ये property Spring Boot Actuator health endpoint (`/actuator/health`) में **Circuit Breaker की health** दिखाती है।
* मतलब जब आप `http://localhost:8081/actuator/health` call करोगे → आपको पता चलेगा कि circuit breaker *UP / OPEN / HALF-OPEN* किस state में है।

---

### 2. `failureRateThreshold: 50`

* ये **failure % threshold** है।
* मतलब: अगर last N calls (sliding window) में **50% से ज्यादा failures** हुए → Circuit **Open** हो जाएगा।

👉 Example:

* `slidingWindowSize=10`
* अगर 10 calls में से 5 fail हो गईं → Circuit breaker open हो जाएगा।

---

### 3. `waitDurationInOpenState: 10s`

* जब circuit **Open** हो जाता है → वो एक निश्चित समय तक open ही रहेगा।
* इस example में → **10 seconds** तक।
* उसके बाद circuit breaker state बदलकर **Half-Open** हो जाएगा और कुछ limited calls allow करेगा (testing के लिए)।

---

### 4. `permittedNumberOfCallsInHalfOpenState: 3`

* जब circuit **Half-Open** होता है → ये property बताती है कि कितनी test calls allow करनी हैं।
* यहाँ 3 calls allow होंगी।
* अगर वो successful रहीं → Circuit वापस **Closed** हो जाएगा।
* अगर fail हुईं → Circuit फिर से **Open** हो जाएगा और wait timer reset होगा।

---

### 5. `slidingWindowSize: 10`

* ये **window size** है जिसमें Resilience4j failures और successes track करता है।
* Example:

  * अगर आपने `slidingWindowSize=10` दिया → Circuit breaker **पिछली 10 calls** को observe करेगा।
  * उसी data से calculate करेगा कि failure % `failureRateThreshold` से ज्यादा है या नहीं।

---

## 🔁 Full Flow Example (with given config)

1. Circuit start में **Closed** है → सारी requests जा रही हैं।
2. पिछले 10 requests में से 5 fail → failure rate = 50% → threshold cross हुआ → Circuit **Open** हो गया।
3. अब next **10 seconds** तक → सारी requests block होंगी और fallback मिलेगा।
4. 10 sec बाद Circuit **Half-Open** होगा → सिर्फ **3 test calls** allow होंगी।

   * अगर 3 calls successful रहीं → Circuit वापस **Closed**।
   * अगर fail हुईं → Circuit फिर से **Open** और 10 sec wait।

## 🔎 Feign Client Exception Handling

जब आप `@FeignClient` से किसी दूसरे microservice को call करते हो, तो कई तरह की exceptions आ सकती हैं:

* Service down → `FeignException.ServiceUnavailable (503)`
* Bad request → `FeignException.BadRequest (400)`
* Unauthorized → `FeignException.Unauthorized (401)`
* Timeouts → `FeignException.GatewayTimeout`
* Unknown → `FeignException` (generic)

Feign internally सबको **`FeignException`** या उसकी subclasses में wrap कर देता है।

---

## 🛠 1. Try-Catch में Handle करना

```java
@RestController
public class UserController {

    @Autowired
    private ProductClient productClient;

    @GetMapping("/my-product/{id}")
    public ResponseEntity<?> getProduct(@PathVariable Long id) {
        try {
            Product product = productClient.getProductById(id);
            return ResponseEntity.ok(product);
        } catch (FeignException.NotFound ex) {
            return ResponseEntity.status(HttpStatus.NOT_FOUND)
                                 .body("Product not found!");
        } catch (FeignException ex) {
            return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
                                 .body("Product service unavailable!");
        }
    }
}
```

👉 इस तरह आप specific exceptions (जैसे `NotFound`, `BadRequest`) पकड़ सकते हो।

---

## 🛠 2. Global Exception Handler (`@ControllerAdvice`)

अगर बार-बार हर जगह try-catch लिखना नहीं चाहते → एक global handler बना सकते हो:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(FeignException.NotFound.class)
    public ResponseEntity<String> handleNotFound(FeignException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                             .body("Resource not found!");
    }

    @ExceptionHandler(FeignException.class)
    public ResponseEntity<String> handleFeignException(FeignException ex) {
        return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
                             .body("Downstream service error: " + ex.contentUTF8());
    }
}
```

---

## 🛠 3. Fallback (Recommended with Resilience4j)

Best practice यह है कि **direct exceptions throw करने के बजाय fallback provide करो**:

```java
@FeignClient(name = "product-service", fallback = ProductClientFallback.class)
public interface ProductClient {
    @GetMapping("/products/{id}")
    Product getProductById(@PathVariable("id") Long id);
}

@Component
class ProductClientFallback implements ProductClient {
    @Override
    public Product getProductById(Long id) {
        return new Product(id, "Default Product (Fallback)", 0.0);
    }
}
```

👉 अब अगर service down है → Feign exception throw करने के बजाय fallback response देगा।

---

## 🛠 4. Custom Error Decoder (Advanced)

अगर आप Feign की default exception handling change करना चाहते हो, तो `ErrorDecoder` बना सकते हो:

```java
@Component
public class CustomErrorDecoder implements ErrorDecoder {

    private final ErrorDecoder defaultDecoder = new Default();

    @Override
    public Exception decode(String methodKey, Response response) {
        if (response.status() == 404) {
            return new ProductNotFoundException("Product not found!");
        }
        return defaultDecoder.decode(methodKey, response);
    }
}
```

| --------------------------- | ------------------------------------------------ |
| **Try-Catch**               | छोटे scope में exceptions handle करने के लिए     |
| **@ControllerAdvice**       | Global exception handling के लिए                 |
| **Fallback + Resilience4j** | Microservice robust बनाने के लिए (best practice) |

Your Spring Cloud Gateway route configuration in `application.properties` works by **matching incoming request paths** and **forwarding them to the correct microservice** using **service discovery (Eureka)** and **load-balanced URI**.

Let me explain it **step-by-step**:

---

## 🔧 Configuration Breakdown

You have 3 route definitions:

```properties
spring.cloud.gateway.routes[0].id=user-service
spring.cloud.gateway.routes[0].uri=lb://USER-SERVICE
spring.cloud.gateway.routes[0].predicates[0]=Path=/users/**

spring.cloud.gateway.routes[1].id=rating-service
spring.cloud.gateway.routes[1].uri=lb://RATING-SERVICE
spring.cloud.gateway.routes[1].predicates[0]=Path=/ratings/**

spring.cloud.gateway.routes[2].id=hotel-service
spring.cloud.gateway.routes[2].uri=lb://HOTEL-SERVICE
spring.cloud.gateway.routes[2].predicates[0]=Path=/hotels/**
```

Each block represents a **route** in the API Gateway.

---

## ⚙️ How It Works Internally

### 🔹 1. **Predicate: Path=/users/**

This means:

* If a request comes to API Gateway like:
  `http://localhost:8080/users/123`
* It will match the predicate `/users/**`

### 🔹 2. **URI: lb://USER-SERVICE**

* `lb://` means **load-balanced** request.
* `USER-SERVICE` is the name of your microservice registered in **Eureka**.
* Gateway will query **Eureka registry**, get all instances of `USER-SERVICE`, and forward the request to one of them.

✅ Example:

```
INCOMING REQUEST:
http://localhost:8080/users/123

GATEWAY ROUTES TO:
http://localhost:8081/users/123
(assuming USER-SERVICE is running on port 8081)
```

Same applies for:

* `/ratings/**` → goes to `RATING-SERVICE`
* `/hotels/**` → goes to `HOTEL-SERVICE`

---

## 📌 Summary Table

| Property                  | Meaning                                                        |
| ------------------------- | -------------------------------------------------------------- |
| `routes[n].id`            | A unique name for the route (used for logging)                 |
| `routes[n].uri`           | Destination URI (with `lb://` for load-balanced Eureka lookup) |
| `routes[n].predicates[0]` | Match rule (when to apply this route)                          |

---

## 🧪 Test Example

If you call:

```http
GET http://localhost:8080/users/vishnu
```

Spring Cloud Gateway will:

1. Match `/users/**`
2. Lookup Eureka for `USER-SERVICE`
3. Forward the request to:
   `http://<some-instance-of-USER-SERVICE>/users/vishnu`

---

## 🧠 Pro Tip

If you want to **remove the prefix (`/users`)** before forwarding, you can add a filter:

```properties
spring.cloud.gateway.routes[0].filters[0]=StripPrefix=1
```

Now `/users/123` → will be sent to `/123` on USER-SERVICE.

## 🧩 `StripPrefix` kya hota hai?

**`StripPrefix` ek Gateway filter hai** jo request URL ke **starting ke kuch part (path segment)** ko **remove (hatata)** hai **before** woh request aage kisi microservice ko bheji jaaye.

## 🛣️ Example se samjhein

```properties
spring.cloud.gateway.routes[0].predicates[0]=Path=/users/**
spring.cloud.gateway.routes[0].filters[0]=StripPrefix=1
```

### ➡️ Yeh karta hai:

* `/users/123` se **`/users` hata deta hai**
* Aur request forward karta hai **sirf `/123`** as actual path.

---

## 💡 StripPrefix mein number ka matlab

| StripPrefix     | Kya remove karega (Hindi)                   |
| --------------- | ------------------------------------------- |
| `StripPrefix=1` | Pehla path segment (jaise `/users`)         |
| `StripPrefix=2` | Pehle do path segment (jaise `/users/data`) |

Path segment ka matlab hota hai:
`/users/123` → `users` aur `123` 2 segment hain.

## 🔄 Compare (Hindi Table)

| Gateway URL         | Backend without StripPrefix | Backend with `StripPrefix=1` |
| ------------------- | --------------------------- | ---------------------------- |
| `/users/123`        | `/users/123`                | `/123`                       |
| `/ratings/user/abc` | `/ratings/user/abc`         | `/user/abc`                  |

```java
@GetMapping("/{id}")
```

Toh yahaan `StripPrefix=1` **nahi lagana chahiye**, kyunki backend `/users/123` expect karta hai.

| Feature               | Explanation (Hindi + English)                           |

**Fault Tolerance** (फ़ॉल्ट टॉलरेंस) का मतलब होता है:

> **"जब सिस्टम में कोई गड़बड़ी (fault) होती है, तब भी वह बिना रुके या क्रैश हुए काम करता रहे।"**

---

## 🔧 Fault Tolerance in Microservices

Microservices architecture में, हर service अलग-अलग चलती है। Fault tolerance यह सुनिश्चित करता है कि:

* अगर एक service fail हो जाए तो बाकी system **बिना रुके** काम करता रहे।
* System खुद recover करने की कोशिश करे या backup ले।

---

## 🧱 Fault Tolerance कैसे हासिल किया जाता है?

### ✅ 1. **Circuit Breaker Pattern**

* अगर कोई service बार-बार fail हो रही है, तो उससे request भेजना **बंद** कर दो कुछ समय के लिए।
* Tool: `Resilience4j`, `Hystrix`
  🔁 Circuit breaker trip होता है → fallback response दिया जाता है।

### ✅ 2. **Retry Mechanism**

* अगर request fail हो जाए, तो कुछ बार **automatically retry** करना।
* Example: Retry DB connection 3 बार।

### ✅ 3. **Timeouts**

* किसी भी call को infinite wait ना करने देना — timeout fix करना (जैसे 2 सेकंड)।

### ✅ 4. **Fallbacks**

* अगर main logic fail हो जाए, तो **default/fallback response** return करना।

### ✅ 5. **Bulkhead Pattern**

* System के अलग-अलग हिस्सों को isolate रखना ताकि एक हिस्से की failure पूरे system को down न करे।

---

## 🎯 Example

मान लीजिए आप का एक Order Service है जो Product Service को call करता है:

### Without fault tolerance:

* अगर Product Service down है → पूरी Order Service भी crash हो जाएगी.

### With fault tolerance (e.g. Circuit Breaker + Fallback):

* Circuit breaker detect करेगा कि Product Service down है → fallback method run करेगा:

```java
public Product getProductFallback(String productId) {
    return new Product(productId, "Dummy Product", 0.0);
}
```

### 💡 **Circuit Breaker – How it Works (In Microservices)**

---

Circuit Breaker एक **design pattern** है जो यह सुनिश्चित करता है कि जब कोई service बार-बार fail हो रही हो, तो system उसे बार-बार call करने से बचे और fallback mechanism पर switch कर जाए।

---

## 🛠️ Real-World Analogy

सोचो एक खराब fan बार-बार चालू करने की कोशिश करते हो। वो काम नहीं करता, फिर भी try करते हो — time & energy waste होता है।
Circuit breaker कहता है: "कुछ बार try किया, नहीं हुआ? अब बंद करो और fallback लगाओ!"

---

## ⚙️ Circuit Breaker का Working Steps

```
States of Circuit Breaker:
    CLOSED → OPEN → HALF-OPEN → CLOSED (if successful again)
```

---

### 1. **Closed State** (Normal Mode)

* सारी requests **service को भेजी जाती हैं**।
* अगर errors का ratio (e.g. 50%) threshold पार कर जाए → circuit **Open** हो जाता है।

✅ Service working
❌ कुछ failures tolerated

---

### 2. **Open State** (Fail Fast Mode)

* कोई भी request actual service को नहीं भेजी जाती।
* सीधे fallback method या error दिया जाता है।
* कुछ समय बाद (wait duration), circuit **Half-Open** होता है।

❌ Service unhealthy
✔️ Request को block कर देता है

---

### 3. **Half-Open State** (Test Mode)

* कुछ test requests भेजी जाती हैं।

  * अगर ये successful हों → circuit **Closed** (healthy again)
  * अगर fail हों → circuit वापस **Open**

🧪 Test time for service recovery

---

## 🔁 Flow Chart Summary

```text
       Service is OK
   ┌──────────────────┐
   │    CLOSED         │
   └──────┬────────────┘
          │ Errors cross threshold
          ▼
   ┌──────────────────┐
   │     OPEN          │ <── Wait Duration (e.g. 10 sec)
   └──────┬────────────┘
          │ Timer Expired
          ▼
   ┌──────────────────┐
   │   HALF-OPEN       │
   └──────┬────────────┘
      ▲         │
Success        Fail
   │            ▼
   └───────► OPEN again
```

## ✅ Step-by-Step Guide to Implement Circuit Breaker using **Resilience4j**

---

### ✅ 1. **Add Dependency**

If using **Maven**, add this to your `pom.xml`:

```xml
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot3</artifactId>
```

```xml
    <groupId>org.springframework.boot</groupId>
```

### ✅ 2. **Use `@CircuitBreaker` in your Service**

Suppose you have a REST call from `UserService` to `RatingService`.

```java
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;

@Service
public class UserService {

    private final RestTemplate restTemplate;

    public UserService(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    @CircuitBreaker(name = "ratingBreaker", fallbackMethod = "getFallbackRating")
    public List<Rating> getRatings(String userId) {
        String url = "http://RATING-SERVICE/ratings/user/" + userId;
        Rating[] ratings = restTemplate.getForObject(url, Rating[].class);
        return Arrays.asList(ratings);
    }

    public List<Rating> getFallbackRating(String userId, Throwable t) {
        System.out.println("Fallback method called due to: " + t.getMessage());
        return List.of(new Rating("0", 0));
    }
}
```

---

### ✅ 3. **Configure Resilience4j in `application.yml`**

```yaml
resilience4j:
  circuitbreaker:
    instances:
      ratingBreaker:
        registerHealthIndicator: true
        slidingWindowSize: 5
        minimumNumberOfCalls: 5
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
```

### ✅ 4. **Add `RestTemplate` Bean**

```java

    @Bean

}
```

**RateLimiter** ek design pattern hai jo **ek samay mein kitne requests allow kiye jaayenge** usko control karta hai. Ye microservices ya APIs mein **overload se bachane** ke liye use kiya jata hai.

---

### 🔧 **RateLimiter ka Kaam:**

RateLimiter ensure karta hai ki koi bhi client ya user system ko **excessively hit** na kare.

### ✅ **Use Case Example:**

* Suppose ek public API hai jo sabko access dena chahta hai.
* Lekin agar koi client 1000 requests ek second mein bhej de, toh server crash ho sakta hai.
* Isliye hum bolte hain: “Har user sirf **10 requests per second** kar sakta hai.”
  \=> Isko enforce karta hai **RateLimiter**.

---

### 🔒 **Resilience4j RateLimiter Configuration Example (.properties):**

```properties
resilience4j.ratelimiter.instances.userRateLimiter.limit-for-period=10
resilience4j.ratelimiter.instances.userRateLimiter.limit-refresh-period=1s
resilience4j.ratelimiter.instances.userRateLimiter.timeout-duration=500ms
```

### 📘 Explanation:

| Property               | Meaning                                                        |
| ---------------------- | -------------------------------------------------------------- |
| `limit-for-period`     | Har refresh period mein kitne requests allowed hain (e.g., 10) |
| `limit-refresh-period` | Kitne samay mein limit reset hogi (e.g., 1 second)             |
| `timeout-duration`     | Request kitna wait karega token ke liye (e.g., 500 ms)         |

---

### ⚙️ Example:

```java
@RateLimiter(name = "userRateLimiter")
@GetMapping("/users")
public ResponseEntity<List<User>> getUsers() {
    return ResponseEntity.ok(userService.getAllUsers());
}
```

---

### 🔐 `resilience4j.ratelimiter.instances.myLimiter.limit-for-period=5`

➡️ **मतलब**:
एक निश्चित अवधि (refresh period) में **कितनी बार** कोई method call हो सकती है।

🧾 **Example**:
अगर ये value `5` है और refresh period `1s` है, तो एक सेकंड में **5 बार** ही call को allow किया जाएगा।
6वीं बार call होगी तो **fallback method** execute होगा।

---

### ⏱️ `resilience4j.ratelimiter.instances.myLimiter.limit-refresh-period=1s`

➡️ **मतलब**:
हर कितनी देर बाद call count **reset** होगा।

🧾 **Example**:
`1s` यानी हर 1 सेकंड में limit reset होगी।
तो हर सेकंड में फिर से 5 calls की अनुमति मिल जाएगी।

---

### ⌛ `resilience4j.ratelimiter.instances.myLimiter.timeout-duration=0`

➡️ **मतलब**:
अगर current time में call limit exceed हो गई है, तो **कितनी देर तक** caller wait करे।

🧾 **Example**:

* `0` का मतलब – **बिलकुल भी wait नहीं करेगा**, और सीधा fallback method चलेगा।
* अगर इसे `2s` लिखें, तो 2 सेकंड तक wait करेगा कि कोई slot खाली हो जाए।

---

### ✅ Final Summary

| Property                  | Meaning                                             |
| ------------------------- | --------------------------------------------------- |
| `limit-for-period=5`      | 5 calls per refresh window allowed                  |
| `limit-refresh-period=1s` | Every 1 second the limit is reset                   |
| `timeout-duration=0`      | No wait time if limit exceeds; immediately fallback |

```java
import org.springframework.context.annotation.Bean;
```

### ✅ **RestTemplate Interceptor क्या है?** (in Hindi)

**`RestTemplate Interceptor`** एक ऐसा component है जो हर बार जब आप `RestTemplate` से किसी API को call करते हो, तब वह HTTP request या response को **modify**, **log**, या **header add** करने के लिए काम आता है।

यह concept Feign interceptor जैसा ही है, लेकिन यह Feign की जगह `RestTemplate` के लिए काम करता है।

| Use Case                                     | RestTemplate Interceptor करेगा |
| -------------------------------------------- | ------------------------------ |
| हर request में **JWT token** भेजना           | ✅                              |
| हर request या response को **log** करना       | ✅                              |
| Custom headers जोड़ना (`X-Request-ID`, etc.) | ✅                              |
| Retry logic या time logging                  | ✅                              |

## 🔧 कैसे implement करें?

### 🔹 Step 1: `ClientHttpRequestInterceptor` implement करें

```java
import org.springframework.http.HttpRequest;
import org.springframework.http.client.ClientHttpRequestExecution;
import org.springframework.http.client.ClientHttpRequestInterceptor;
import org.springframework.http.client.ClientHttpResponse;

import java.io.IOException;

public class MyRestTemplateInterceptor implements ClientHttpRequestInterceptor {

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body,
                                        ClientHttpRequestExecution execution) throws IOException {

        // Header जोड़ें
        request.getHeaders().add("Authorization", "Bearer <your_token_here>");
        request.getHeaders().add("X-Custom-Header", "MyValue");

        // Proceed with request
        return execution.execute(request, body);
    }
}
```

---

### 🔹 Step 2: इसे `RestTemplate` में add करें

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestTemplate;
import java.util.Collections;

@Configuration
public class RestTemplateConfig {

    @Bean
    public RestTemplate restTemplate() {
        RestTemplate restTemplate = new RestTemplate();

        // Interceptor सेट करें
        restTemplate.setInterceptors(Collections.singletonList(new MyRestTemplateInterceptor()));

        return restTemplate;
    }
}
```

---

## ✅ **What is ELK Stack?**

👉 **ELK** is an acronym for **E**lasticsearch, **L**ogstash, and **K**ibana.
It’s a **powerful open-source log management and analytics stack**, widely used for **centralized logging**, **monitoring**, and **visualizing logs**.

---

## 🔹 **1️⃣ Elasticsearch**

* It’s a **search engine** and analytics engine.
* Stores logs and makes them **searchable**.
* Fast, distributed, scalable — can handle huge log data.

---

## 🔹 **2️⃣ Logstash**

* It’s a **data pipeline** tool.
* Collects logs from different sources (apps, servers, files, beats, etc.)
* Parses, filters, transforms the logs.
* Sends processed logs to **Elasticsearch**.

---

## 🔹 **3️⃣ Kibana**

* It’s a **visualization dashboard**.
* Connects to **Elasticsearch** and lets you **search**, **analyze**, and **visualize** logs.
* You can build charts, dashboards, and monitor live logs.

---

## 🔹 How does it work together?

✅ **Flow:**

1️⃣ **Your App** (Spring Boot) generates logs →
2️⃣ **Logstash** collects & processes logs →
3️⃣ Stores logs in **Elasticsearch** →
4️⃣ You use **Kibana** to view and analyze logs in real-time.

---

## 🔹 🔑 What’s the benefit?

✔ Centralized logging for all servers / services.
✔ Search logs fast (e.g., all ERROR logs for today).
✔ Create alerts and dashboards.
✔ Debug issues across microservices from one place.

---

## 🔹 🧩 Example: Spring Boot + ELK

* Spring Boot generates logs → output to file.
* Filebeat (a lightweight agent) can ship logs → Logstash.
* Logstash parses logs → sends to Elasticsearch.
* Use Kibana for dashboards.

---

## ✅ ✅ ✅ **Summary**

| Component         | Purpose                          |
| ----------------- | -------------------------------- |
| **Elasticsearch** | Stores & indexes logs            |
| **Logstash**      | Collects, processes & sends logs |
| **Kibana**        | Visualizes logs & dashboards     |

---

## 🔹 🔗 Bonus

Many people now use **Elastic Beats** (like Filebeat) with ELK.

* **Filebeat** is lightweight — ships log files directly to Logstash or Elasticsearch.

| 🔑 Feature                | **Sleuth**                                                         | **ELK Stack**                                                                |
| ------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 👉 **क्या है?**           | Distributed Tracing Library                                        | Centralized Log Management System                                            |
| 👉 **क्यों use होता है?** | एक request के flow को multiple microservices में trace करने के लिए | सारे logs collect, store, search और visualize करने के लिए                    |
| 👉 **काम क्या करता है?**  | Request को trace ID और span ID assign करता है                      | Logs को collect करके Elasticsearch में store करता है और Kibana में दिखाता है |
| 👉 **Main Focus**         | कौन सा request कहाँ से कहाँ गया? कितना time लगा?                   | Logs को centralized तरीके से search और analyze करना                          |

| 👉 **Example Use**        | Service A → Service B → Service C के बीच का पूरा flow देखना        | पिछले 1 महीने के सारे ERROR logs निकालना                                     |

## 🔹 **धीरे से समझते हैं:**

### ✅ 1️⃣ **Sleuth**

* सिर्फ **tracing IDs** डालता है।
* जिससे logs correlate हो जाएं।
* Request किस microservice से गुजरा, कितना time लिया, कहां delay हुआ — ये सब पता चलता है।

### ✅ 2️⃣ **ELK Stack**

* आपके **सारे logs** collect करता है — चाहे वो Sleuth वाले trace logs हों या normal debug/error/info logs।
* Logs को store करता है (Elasticsearch)।
* आप उन्हें search कर सकते हैं, dashboards बना सकते हैं (Kibana)।
* Logstash/Beats logs को collect और process करते हैं।

---

## 🔹 **दोनों एक साथ कैसे use होते हैं?**

➡️ आप **Sleuth** से tracing IDs logs में डालते हैं।
➡️ वही logs **Logstash/Filebeat** से ELK में जाते हैं।
➡️ फिर Kibana में आप traceId से search कर सकते हैं — पूरा flow एक ही जगह मिल जाता है।

| काम                                                  | Sleuth                                          | ELK                                                                   |
| ---------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------- |

| आप logs में traceId देखते हैं                        | Sleuth logs में दिखाता है `[traceId: xyz123]`   | Kibana से उस traceId को search करके पूरा log flow देख सकते हैं        |

## ✅ **ACID का मतलब क्या है?**

👉 **ACID** चार properties का short form है:

* **A — Atomicity**
* **C — Consistency**
* **I — Isolation**
* **D — Durability**

ये properties ensure करती हैं कि कोई भी database transaction **सही**, **safe** और **reliable** रहे — चाहे कुछ भी हो जाए।

---

## 🔹 1️⃣ **A — Atomicity (एटॉमिकिटी)**

✔️ मतलब: **All or Nothing**
एक transaction में जितने भी steps हैं, वो \*\*सारे के सारे एक साथ successful होने चाहिए या फिर सब fail हो जाने चाहिए। Partial execution allowed नहीं है।

**उदाहरण:**

* अगर आप बैंक से ₹1000 किसी को transfer करते हैं:

  * आपके account से ₹1000 debit होगा।
  * सामने वाले के account में ₹1000 credit होगा।

👉 अगर debit हुआ लेकिन credit fail हो गया — तो पैसा गायब!
Atomicity कहती है: या तो दोनों काम होंगे या दोनों cancel।

---

## 🔹 2️⃣ **C — Consistency (कंसिस्टेंसी)**

✔️ मतलब: Transaction के बाद database का state **valid** रहना चाहिए।
Rules, constraints, foreign keys सब satisfy होने चाहिए।

**उदाहरण:**

* कोई negative balance allow नहीं है।
* कोई duplicate primary key नहीं होनी चाहिए।

---

## 🔹 3️⃣ **I — Isolation (आइसोलेशन)**

✔️ मतलब: एक transaction को दूसरे के बीच में interfere नहीं करना चाहिए।
Multiple transactions parallel में चल सकते हैं — लेकिन ऐसा लगे जैसे वो serially एक के बाद एक ही चले।

**उदाहरण:**

* आप किसी account में पैसे transfer कर रहे हैं, तभी दूसरा transaction भी वही balance देख रहा है।
* Isolation ensure करता है कि intermediate states बाहर ना दिखें।

---

## 🔹 4️⃣ **D — Durability (ड्यूरैबिलिटी)**

✔️ मतलब: Once transaction commit हो गया, तो data **permanent** है।
चाहे server crash हो जाए, power cut हो जाए — data safe रहेगा।

**उदाहरण:**

* Bank transfer success का message मिल गया = data disk में safely लिखा जा चुका है।

---

## ✅ ✅ ✅ **ACID क्यों जरूरी है?**

👉 ताकि:

* Data corruption ना हो।
* Data में reliability हो।
* Multiple users safe तरीके से parallel काम कर सकें।

---

## 🔹 ✅ Short में:

| Property           | मतलब                                     |
| ------------------ | ---------------------------------------- |
| **A: Atomicity**   | सब या कुछ भी नहीं                        |
| **C: Consistency** | Valid state maintain                     |
| **I: Isolation**   | Transactions एक-दूसरे को disturb ना करें |
| **D: Durability**  | Data safe रहेगा                          |

> **ACID = Database Transactions की reliability guarantee!**

✅ Distributed Transaction मतलब क्या है?
👉 Distributed Transaction मतलब:

एक ऐसा transaction जो एक से ज्यादा अलग-अलग systems या databases पर एक साथ चलता है।

इस transaction में शामिल हर operation को एक साथ success या failure होना चाहिए — ताकि data consistent रहे।

🔹 Simple Example
मान लो एक बैंक का scenario:

Bank Service:
1️⃣ Customer A का account → ₹1000 debit

अगर debit हो जाए लेकिन credit fail हो जाए — तो पैसे कहीं गायब हो जाएंगे।

👉 इसलिए debit और credit दोनों एक atomic transaction में होने चाहिए — या तो दोनों succeed हों या दोनों rollback हों।

✅ Distributed क्यों कहा जाता है?
क्योंकि ये काम:

अलग-अलग databases में हो सकता है।

अलग-अलग servers पर हो सकता है।

अलग-अलग services पर हो सकता है।

🔹 Monolithic vs Distributed

| Aspect                      | Monolithic Transaction                      | Distributed Transaction                                  |
|-----------------------------|---------------------------------------------|-----------------------------------------------------------|
| Database Scope              | Single database                             | Multiple databases                                        |
| Transaction Management      | Local @Transactional is sufficient           | Requires Global Transaction Manager, Saga, or 2PC         |
| ACID Property Maintenance   | Easily maintained                            | Difficult to maintain globally                            |

## ✅ **Saga Pattern क्या है?**

👉 Saga Pattern **Distributed Transaction** को manage करने का **Modern तरीका** है।
👉 यह **Long Running Transactions** को छोटे-छोटे **Local Transactions** में divide करता है।
👉 अगर कोई step fail होता है तो उसके लिए **Compensating Action** होता है — जैसे rollback लेकिन distributed way में।

```
1️⃣ Order Service  → Order create करे।
2️⃣ Payment Service → Payment success हो।
3️⃣ Inventory Service → Stock reduce हो।
```

अगर Payment fail हो जाए तो:

* Order cancel करना होगा।
* Inventory restore करना होगा (अगर reduce हुआ था)।

👉 Saga यही manage करता है।

## ✅ **Saga के 2 तरीके**

| Type                  | कैसे काम करता है                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **1️⃣ Choreography**  | हर Service खुद decide करती है कि आगे किसे notify करना है। Services events publish/subscribe करती हैं। कोई central coordinator नहीं।    |

### अब Step-by-Step देखें: **Choreography vs Orchestration**

---

## 🔹 **1️⃣ Choreography-based Saga**

**कैसे काम करता है?**

* Service A: Order Created → Event Publish करता है (Kafka/RabbitMQ)
* Service B: Payment Service उस Event को Subscribe करता है → Payment Process करता है → फिर Payment Success Event Publish करता है।
* Service C: Inventory Service Payment Success Event सुनकर Stock reduce करता है।

👉 अगर बीच में कोई failure हुआ तो दूसरा event publish होगा — e.g., `PaymentFailed` → Order Service वो सुनकर Order Cancel कर देगा।

---

**Use करता है:**

* Event Bus (Kafka, RabbitMQ, ActiveMQ)
* Spring Cloud Stream

---

## 🔹 **2️⃣ Orchestration-based Saga**

**कैसे काम करता है?**

* एक Orchestrator होता है (जैसे **Saga Service** या **Workflow Engine** — Camunda, Axon, Eventuate Tram)।
* Orchestrator step-by-step:

  * Order Service को call करता है।
  * फिर Payment Service को।
  * फिर Inventory Service को।
* अगर कहीं fail होता है तो Orchestrator compensating action को trigger करता है।

---

**Use करता है:**

* REST calls या Messaging
* Central Saga Orchestrator logic

### ✅ ✅ **👉 Orchestration Example: Custom Orchestrator**

---

1️⃣ एक **Saga Orchestrator Service** बनाओ — बस एक Spring Boot app।
2️⃣ यह REST API calls से सभी steps को call करता है:

* Order Service → Payment Service → Inventory Service
  3️⃣ अगर कोई step fail हो तो Orchestrator compensating REST API को call करता है।

---

**Sample Flow:**

```java
public void startSaga(OrderRequest request) {
  String orderId = orderService.createOrder(request);

  boolean paymentDone = paymentService.processPayment(orderId);
  if (!paymentDone) {
    orderService.cancelOrder(orderId);
    return;
  }

  boolean stockUpdated = inventoryService.reduceStock(orderId);
  if (!stockUpdated) {
    paymentService.refundPayment(orderId);
    orderService.cancelOrder(orderId);
  }
}
```

* Failure आने पर **Compensating Transactions** run करता है — ताकि पूरे process को rollback जैसा effect मिल सके।
