# ⭐ Easy Interview Definition

**Transactional Outbox Pattern** ek design pattern hai jo pehle **Database aur Outbox Table** ko ek hi local transaction me update karta hai. Uske baad ek alag service Outbox Table se messages read karke Kafka me publish karti hai. Isse **Dual Write Problem** aur **Data Inconsistency** avoid hoti hai.

---

# 📝 Interview Questions (Part 1)

### Q1. Why do we need Transactional Outbox Pattern?

**Answer:**
Microservice Architecture me Data Consistency maintain karne aur Dual Write Problem avoid karne ke liye.

---

### Q2. What is Dual Write Problem?

**Answer:**
Jab ek hi transaction me Database aur Kafka (ya kisi aur system) dono me write karna padta hai.

---

### Q3. What is Data Inconsistency?

**Answer:**
Jab ek service ke paas data ho aur dusri service ke paas same data na ho.

---

### Q4. Why can't we rollback Kafka like Database?

**Answer:**
Kyuki Database aur Kafka alag systems hain. Database transaction rollback ho sakta hai, lekin Kafka message ko usi tarah rollback nahi kar sakte.

---

### Q5. Give one real-time example of Dual Write.

**Answer:**
Order Service pehle Order Database me save karti hai aur uske baad Kafka me `OrderCreated` event publish karti hai. Agar in dono me se koi ek fail ho jaye, to Data Inconsistency create ho jati hai.

# ⭐ Easy Interview Definition

**Transactional Outbox Pattern** me hum pehle **Order Table aur Outbox Table** ko ek hi local transaction me update karte hain. Uske baad ek **Order Puller (Message Relay)** Outbox Table se unprocessed records read karke Kafka me publish karta hai aur record ko processed mark kar deta hai. Isse data consistency maintain rehti hai aur Dual Write Problem solve ho jata hai.

---

# 📌 Advantages

### 1. No Dual Write Problem

Database aur Kafka ko ek sath write nahi karna padta.

---

### 2. Reliable Message Delivery

Message lose hone ke chances bahut kam hote hain.

---

### 3. Data Consistency

Sab Microservices ko same data milta hai.

---

### 4. Retry Possible

Agar Kafka down ho

To message Outbox me hi pada rahega.

Later publish ho jayega.

---

### 5. Duplicate Avoid

Processed Flag duplicate publish hone se bachata hai.

---

# 🎯 Interview Questions (Part 2)

### Q1. What is an Outbox Table?

**Answer:**
Outbox Table ek database table hoti hai jisme publish hone wale events temporarily store hote hain.

---

### Q2. Why do we use an Outbox Table?

**Answer:**
Reliable message delivery aur Data Consistency maintain karne ke liye.

---

### Q3. Who reads records from the Outbox Table?

**Answer:**
Order Puller Service ya Message Relay Service.

---

### Q4. What is the purpose of the Processed Flag?

**Answer:**
Ye batata hai ki message Kafka me publish hua hai ya nahi. Isse duplicate processing avoid hoti hai.

---

### Q5. Why is Transactional Outbox called a Local Transaction?

**Answer:**
Kyuki Order Table aur Outbox Table dono same database me hote hain aur ek hi database transaction ke andar update hote hain.

---

### Q6. What happens if Kafka is down?

**Answer:**
Message Outbox Table me safely stored rehta hai. Jab Kafka wapas up ho jata hai, Order Puller us message ko publish kar deta hai.

## 💡 Interview Tip (Most Asked)

Interviewer aksar puchta hai:

**"Agar Kafka down ho jaye to kya hoga?"**

**Answer:**

* Order aur Outbox record already database me save ho chuke hote hain.
