# Part 1 – API Timeout

Sabse pehle tumhare current question wale topic se start karte hain.

## 1. Timeout kya hota hai?

Simple:

**Timeout = system ne response ke liye wait kiya, lekin configured time ke andar response nahi mila.**

Example:

```text
Order Service → Payment Service
```

Payment Service ko response dene mein normally:

```text
200 ms
```

lagta hai.

Lekin production mein kisi reason se:

```text
20 seconds
```

lag rahe hain.

Aur Order Service ka timeout:

```text
5 seconds
```

hai.

To:

```text
0 sec   → Request sent
1 sec   → waiting
2 sec   → waiting
3 sec   → waiting
4 sec   → waiting
5 sec   → TIMEOUT ❌
```

---

# 2. Real Production Example

Suppose hamare paas:

```text
User
 ↓
API Gateway
 ↓
Order Service
 ↓
Payment Service
 ↓
Database
```

User:

```http
POST /order
```

Order Service payment service ko call karti hai:

```text
Order Service
      ↓
Payment Service
```

Ab Payment Service slow ho gayi.

For example:

```text
Payment Service response = 30 sec
Order Service timeout     = 5 sec
```

To Order Service 5 seconds ke baad request ko timeout kar degi.

Result:

```text
User
 ↓
API Gateway
 ↓
Order Service
 ↓
Payment Service
       ⏳
       ⏳
       ❌ timeout
```

User ko generally `5xx` type error mil sakta hai; exact status code architecture par depend karta hai.

---

# 3. Production mein problem dangerous kyun hai?

Yahi **real-world point** interview mein important hai.

Suppose 100 requests aa rahi hain:

```text
100 requests
     ↓
Payment Service slow
     ↓
100 threads waiting
```

Agar threads continuously downstream response ka wait karte rahe:

```text
Thread Pool
----------------
Thread 1 → waiting
Thread 2 → waiting
Thread 3 → waiting
...
Thread 100 → waiting
```

Ab naye requests ke liye threads nahi bachenge.

Result:

```text
Service slow
    ↓
Threads blocked
    ↓
More requests wait
    ↓
Thread pool exhausted
    ↓
Service unavailable
```

PDF ke page 16 mein isi concept ko **cascade failure** ke through dikhaya gaya hai: Service A slow Service B ko call karti hai, threads block hote hain aur eventually Service A bhi unavailable ho sakti hai. 

---

# 4. Timeout ke common causes

Production mein timeout aaya to blindly timeout value increase nahi karni.

Pehle root cause find karna hai.

### Cause 1 – Downstream API slow

```text
Service A
   ↓
Service B
   ↓
slow response
```

### Cause 2 – Database slow

```text
API
 ↓
DB
 ↓
Slow Query
```

### Cause 3 – Network problem

```text
Service A
   ↓
Network
   ↓
Service B
```

Network latency/connection problem ho sakti hai.

### Cause 4 – Thread pool exhausted

```text
Too many requests
       ↓
Threads busy
       ↓
New requests waiting
```

### Cause 5 – External API slow

Example:

```text
Your Application
      ↓
Payment Provider
      ↓
Third-party API
```

Third-party API slow hai to tumhari API bhi wait kar sakti hai.

### Cause 6 – Database connection pool exhausted

```text
API
 ↓
HikariCP
 ↓
All connections busy
 ↓
Request waiting
 ↓
Timeout
```

Tumhari PDF ke page 6 mein HikariCP connection pool exhaustion ka example diya hai, jahan connections busy rehne ya close na hone se requests queue mein wait karti hain.

# 6. Fix kya karenge?

PDF ke page 16 ke according important fixes hain: **timeouts set karna, retries carefully use karna, aur Circuit Breaker lagana**. 

### Fix 1 – Proper timeout

Example concept:

```text

```

> Thread indefinitely wait nahi karega.

# 7. Retry

Suppose temporary network problem hai:

```text
Request
 ↓
Failed
 ↓
Retry
 ↓
Success
```

Lekin **har failure par unlimited retry nahi karna**.

Wrong:

```text
Retry forever ❌
```

Better:

```text
Retry 2-3 times
      ↓
Still failed
      ↓
Fallback / Circuit Breaker
```

PDF bhi retry ko carefully use karne aur bounded retries ka concept batati hai. 

---

# 8. Circuit Breaker

Ye bahut important interview topic hai.

Suppose:

```text
Service A → Service B
```

Service B continuously down hai.

Without Circuit Breaker:

```text
A → B ❌
A → B ❌
A → B ❌
A → B ❌
A → B ❌
```

Service A ke threads waste honge.

Circuit Breaker:

```text
          failures
Service B ─────────→ OPEN
                     ↓
              Don't call B
                     ↓
                  Fallback
```

States:

```text
CLOSED
   ↓
Failures increase
   ↓
OPEN
   ↓
Wait
   ↓
HALF-OPEN
   ↓
Test request
   ↓
Success → CLOSED
Failure → OPEN
```

PDF ke page 16 mein exactly **Closed → Open → Half-Open** flow diya gaya hai. 

---

# 9. Timeout vs Circuit Breaker

Interview mein ye difference yaad rakho:

| Timeout                                 | Circuit Breaker                                  |
| --------------------------------------- | ------------------------------------------------ |
| Kitna wait karna hai                    | Kab downstream ko call karna hi band karna hai   |
| Individual request ko protect karta hai | System ko cascading failure se protect karta hai |
| Example: 5 sec                          | Example: 50% failures → OPEN                     |
| Waiting stop karta hai                  | Calls stop karta hai                             |

Simple line:

> **Timeout says "I won't wait longer." Circuit Breaker says "I won't call this failing service for some time."**

---

# 10. Interview Answer – Ready Format

**Interviewer:**

> Production mein API timeout aaye to kaise debug karoge?

**Answer:**

> "First, I will identify where the timeout is happening by checking application, gateway and infrastructure logs. Then I will check API response time and downstream service latency. I will also check database slow queries, connection pool and thread pool metrics. If a downstream service is slow, I will configure proper connection and read timeouts. For temporary failures I can use limited retries, and for continuous downstream failures I would use a circuit breaker and fallback to prevent cascade failure. Finally, I would add proper monitoring and alerts so that we can detect the issue early."

---

# 11. Ek line mein yaad rakho

```text
TIMEOUT
   ↓
Don't wait forever
   ↓
Find slow dependency
   ↓
DB / API / Network / Pool / Threads
   ↓
Fix root cause
   ↓
Timeout + Limited Retry
   ↓
Circuit Breaker
   ↓
Fallback + Monitoring
```

# Part 2 – OutOfMemoryError / Java Heap Space

Ye tumhari PDF ka **Page 1/20** wala production issue hai. 

Isko hum bilkul real production scenario ki tarah samjhte hain.

---

## 1. OutOfMemoryError kya hai?

Simple language mein:

> **JVM ke paas object create/store karne ke liye enough heap memory nahi bachi, isliye Java `OutOfMemoryError` throw karta hai.**

Example:

```text
Java Application
      ↓
JVM Heap
      ↓
Objects create ho rahe hain
      ↓
Memory continuously increase
      ↓
Heap full ❌
      ↓
OutOfMemoryError
```

Typical error:

```text
java.lang.OutOfMemoryError: Java heap space
```

PDF mein bhi production log ka example `java.lang.OutOfMemoryError: Java heap space` diya hai. 

---

# 2. Real Production Scenario

Suppose tumhari application mein ek API hai:

```http
GET /orders
```

Aur database mein:

```text
10 lakh orders
```

Developer ne accidentally:

```java
List<Order> orders = orderRepository.findAll();
```

kar diya.

Ab kya hoga?

```text
Database
   ↓
10 lakh records
   ↓
Java List
   ↓
Heap memory mein objects
   ↓
Heap continuously increase
   ↓
💥 OutOfMemoryError
```

Production mein API crash ya service instability aa sakti hai.

---

# 3. Heap kya hota hai?

Simple:

**Heap = JVM ka memory area jahan Java objects store hote hain.**

Example:

```java
Customer customer = new Customer();
Order order = new Order();
Payment payment = new Payment();
```

Ye objects heap mein memory consume karte hain.

Conceptually:

```text
JVM Heap
┌─────────────────────────┐
│ Customer Object         │
│ Order Object            │
│ Payment Object          │
│ List Objects            │
│ Cache Objects           │
│ String Objects          │
└─────────────────────────┘
```

---

# 4. Production mein Heap full kyun hota hai?

PDF ke according important root causes:

* **Static collection** objects ko permanently hold kar sakti hai.
* **Memory leak** ki wajah se objects release nahi hote.
* **Large in-memory load**, jaise bahut bada file/data memory mein load karna.
* Objects ka memory se properly release na hona. 

### Example – Static Collection

```java
public class Cache {

    public static Map<String, Object> data = new HashMap<>();

}
```

Agar continuously:

```java
data.put(key, object);
```

hota rahe aur old objects remove na hon:

```text
Object 1
Object 2
Object 3
...
Object 1,000,000
```

Memory grow hoti rahegi.

---

# 5. Memory Leak kya hota hai?

Ye interview mein bahut important hai.

Simple definition:

> **Memory leak means application mein objects ki zarurat khatam ho gayi hai, lekin koi reference unhe hold kar raha hai, isliye Garbage Collector unhe remove nahi kar pa raha.**

Example:

```java
static Map<String, User> cache = new HashMap<>();
```

Requests aati rahi:

```text
User 1 → cache
User 2 → cache
User 3 → cache
...
User 1 lakh → cache
```

Agar cache mein eviction/removal mechanism nahi hai:

```text
Heap
 ↓
Cache
 ↓
Millions of objects
 ↓
GC cannot remove them
 ↓
Heap grows
 ↓
OOM
```

PDF ke page 5 mein **static collection ko memory leak ka common cause** dikhaya gaya hai. 

---

# 6. Garbage Collector object ko kab remove karta hai?

Important interview concept:

GC simply ye nahi dekhta ki:

> "Object use nahi ho raha."

GC mainly reachability/reference relationship dekhta hai.

Example:

```java
User user = new User();
```

Agar baad mein:

```java
user = null;
```

aur object ka koi aur reachable reference nahi hai:

```text
User Object
    ↑
 no reference
    ↓
GC can collect
```

Lekin:

```java
static List<User> users = new ArrayList<>();
users.add(user);
```

To static list reference hold kar rahi hai.

```text
Static List
    ↓
User Object
```

GC us object ko collect nahi kar sakta.

---

# 7. Production mein kaise pata chalega ki OOM hai?

Suppose production alert aaya:

```text
Application Down
```

Logs check kiye:

```text
java.lang.OutOfMemoryError:
Java heap space
```

Ab immediately application restart karna **root-cause analysis nahi hai**.

PDF ke page 1 mein bhi first step ke roop mein immediately restart na karke **heap dump capture** karne ka approach diya gaya hai. 

---

# 8. Heap Dump kya hota hai?

Simple:

> **Heap dump = ek snapshot jisme JVM heap ke andar kaunse objects memory consume kar rahe hain, uski information hoti hai.**

Imagine:

```text
Production JVM
      ↓
Heap
      ↓
Heap Dump
      ↓
Analyze
      ↓
Which object consuming memory?
```

PDF mein heap dump ke liye `jmap` ka example diya gaya hai:

```bash
jmap -dump:format=b,file=heap.hprof <pid>
```



---

# 9. MAT kya hai?

**MAT = Eclipse Memory Analyzer Tool**

Heap dump ko MAT mein open karke dekh sakte hain:

```text
Which object is consuming most memory?
```

PDF ke example mein MAT ke **Dominator Tree** se ek `HashMap` ko large heap consumer ke roop mein identify kiya gaya hai. 

Simple flow:

```text
Production JVM
      ↓
heap.hprof
      ↓
MAT
      ↓
Dominator Tree
      ↓
Large object / collection
      ↓
Root Cause
```

---

# 10. Dominator Tree simple language mein

Interview mein deep theory ki zarurat nahi.

Simple bolo:

> **Dominator Tree helps us identify which objects are retaining a large amount of memory.**

Example:

```text
HashMap
   ↓
User Objects
   ↓
Order Objects
   ↓
Payment Objects
```

Agar HashMap bahut saare objects ko retain kar rahi hai, to MAT mein wo major memory consumer dikhegi.

---

# 11. Production Debugging Flow

Ye flow **interview mein yaad karna hai**:

```text
OOM Alert
   ↓
Check application logs
   ↓
Confirm OutOfMemoryError
   ↓
Capture Heap Dump
   ↓
Open Heap Dump in MAT
   ↓
Check Dominator Tree
   ↓
Find memory-consuming object
   ↓

   ↓

   ↓

   ↓
Monitor Heap / GC
```

---

# 12. Root Cause Example

Suppose MAT mein mila:

```text
HashMap → 2 GB
```

Ab question:

**HashMap itni badi kyun hai?**

Code search kiya:

```java
private static Map<String, User> cache =
        new HashMap<>();
```

Aur kahin bhi eviction nahi.

Root cause:

```text
Static HashMap
      ↓
Objects continuously added
      ↓
Objects retained
      ↓
Heap grows
      ↓
OOM
```

---

# 13. Fix kya karoge?

### Fix 1 – Unlimited collection mat rakho

Wrong:

```java
static Map<String, User> cache = new HashMap<>();
```

Agar unlimited growth possible hai.

Better approach:

```text
Bounded Cache
+
Eviction
+
Expiration
```

---

### Fix 2 – Large data ko ek saath memory mein mat lao

Wrong:

```java
findAll()
```

for millions of records.

Better:

```text
Pagination
```

Example:

```text
Page 1 → 100 records
Page 2 → 100 records
Page 3 → 100 records
```

Instead of:

```text
10 lakh records → JVM Heap ❌
```

---

### Fix 3 – Large file ko memory mein mat load karo

Instead of:

```text
10 GB file
   ↓
Entire file → memory ❌
```

Use:

```text
File
 ↓
Stream / chunks
 ↓
Process small portion
```

---

# 14. `-Xmx` increase karna solution hai?

Ye **interview trap question** ho sakta hai.

Suppose:

```text
-Xmx512m
```

se OOM aa raha hai.

Tum:

```text
-Xmx2g
```

kar dete ho.

Kya problem solve ho gayi?

**Not necessarily.**

Agar memory leak hai:

```text
512 MB → OOM
2 GB   → later OOM
4 GB   → later OOM
```

Root cause still exists.

PDF ke page 1 mein temporary mitigation ke roop mein heap increase karne ke saath **leak fix karna aur large resources/data ko properly manage karna** emphasize kiya gaya hai. 

### Interview mein bolo:

> "Increasing `-Xmx` can be a temporary mitigation, but I would not consider it the root-cause fix. I would analyze the heap dump and identify the objects retaining memory."

---

# 15. OOM vs Memory Leak

Bahut important difference:

| OOM                            | Memory Leak                                       |
| ------------------------------ | ------------------------------------------------- |
| Heap memory available nahi hai | Objects unnecessarily retained hain               |
| Error/result                   | Root cause ho sakta hai                           |
| `Java heap space` aa sakta hai | Eventually OOM cause kar sakta hai                |
| Large load se bhi ho sakta hai | Static collection/cache/reference se ho sakta hai |

Simple:

> **Memory leak OOM ka ek possible cause hai.**

---

# 16. Interview Scenario

### Interviewer:

> Production mein `java.lang.OutOfMemoryError: Java heap space` aa raha hai. What will you do?

### Tum:

> "First, I will check the application logs and confirm whether it is a heap space issue. I would avoid blindly restarting the application and, if possible, capture a heap dump. Then I would analyze the heap dump using tools like MAT and check the Dominator Tree to identify which objects are consuming or retaining most of the heap. I would investigate common causes such as static collections, unbounded caches, large in-memory data or objects that are unnecessarily retained. After identifying the root cause, I would fix the code, for example by adding cache eviction, pagination or streaming. Increasing `-Xmx` can be a temporary mitigation, but it should not replace root-cause analysis."

---

# 17. 30-Second Interview Version

Agar interviewer short answer chahta hai:

> **"For a Java heap-space OOM in production, I first confirm it from logs, capture a heap dump, analyze it using MAT and check the Dominator Tree to find the objects retaining most memory. Then I identify whether the cause is an unbounded cache, static collection, large in-memory data or another retention issue. I fix the root cause and monitor heap and GC. Increasing `-Xmx` can be temporary mitigation but is not the actual fix."**

# 5. Thread ID ko convert kyun karte hain?

Ab Linux se thread ID mila:

```text
12346
```

Java thread dump mein thread ID usually hexadecimal form mein useful hoti hai.

So:

```text
12346 decimal
      ↓
hexadecimal
      ↓
303A
```

Linux command:

```bash
printf '%x\n' 12346
```

Output:

```text
303a
```

Ab hum thread dump mein:

```text
nid=0x303a
```

search kar sakte hain.

---

# 6. Step 3 – Thread Dump lo

Command:

```bash

```

Yahan:

```text
12345 = Java process PID
```

Thread dump mein multiple threads milenge.

Example:

```text

    nid=0x303a
    at com.myapp.service.OrderService.process(OrderService.java:187)
```

Ab important part:

```text
RUNNABLE
nid=0x303a
OrderService.java:187
```

Hume pata chal gaya:

> High CPU thread `OrderService.java` ki line 187 ke around running hai.

# 7. High CPU ke common Root Causes

# Part 4 – Deadlock in Production

Ye tumhari PDF ka **Page 3/20 – Deadlock** wala production issue hai. 

Isko simple real-world example se samajhte hain, phir **production mein detect kaise karna hai**, `jstack` se kaise identify karna hai, aur interview mein kya answer dena hai.

---

## 1. Deadlock kya hota hai?

Simple language mein:

> **Deadlock tab hota hai jab do ya more threads ek-dusre ke lock ko release hone ka wait karte rehte hain, aur koi bhi thread aage nahi badh pata.**

Example:

```text id="c9r5v8"
Thread-1 → Lock A le liya
           ↓
           Lock B ka wait

Thread-2 → Lock B le liya
           ↓
           Lock A ka wait
```

Ab:

```text id="0f1xq8"
Thread-1 → A ✔ → B ❌
                  ↑
                  │
Thread-2 → B ✔ → A ❌
```

Dono ek-dusre ka wait kar rahe hain.

**Result: application ka kuch part hang ho sakta hai.**

---

# 2. Real Production Example

Suppose hamare banking application mein:

```text id="t0t7a4"

```

```text id="b5x1g2"

```

Aur simultaneously doosra transfer:

```text id="q0a2s4"

```

Agar code locks ko different order mein acquire karta hai:

### Thread 1

```text id="a2x6c8"
Lock Account A
       ↓
Lock Account B
```

### Thread 2

```text id="k4t7b1"
Lock Account B
       ↓
Lock Account A
```

Production mein:

```text id="9k8gq1"
Thread-1
   ↓
A locked
   ↓
Waiting for B

Thread-2
   ↓
B locked
   ↓
Waiting for A
```

💥 **Deadlock**

# 3. Simple Java Example

Ye code intentionally deadlock create karega:

```java id="m3g4pk"
public class DeadlockDemo {

    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {

        Thread thread1 = new Thread(() -> {

            synchronized (lockA) {
                System.out.println("Thread 1 locked A");

                try {
                    Thread.sleep(100);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }

                synchronized (lockB) {
                    System.out.println("Thread 1 locked B");
                }
            }

        }, "Thread-1");


        Thread thread2 = new Thread(() -> {

            synchronized (lockB) {
                System.out.println("Thread 2 locked B");

                try {
                    Thread.sleep(100);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }

                synchronized (lockA) {
                    System.out.println("Thread 2 locked A");
                }
            }

        }, "Thread-2");


        thread1.start();
        thread2.start();
    }
}
```

# 8. Deadlock aur Normal Waiting mein Difference

Ye interview mein important hai.

### Normal waiting

```text id="1b2x9z"
Thread-1 → waiting
       ↓
Thread-2 completes
       ↓
Lock released
       ↓
Thread-1 continues
```

Ye normal ho sakta hai.

### Deadlock

```text id="8k4v1q"
Thread-1 → waiting for Thread-2
       ↑                ↓
       │                │
       └────────────────┘
       Thread-2 → waiting for Thread-1
```

**Forever waiting.**

---

# 9. Deadlock ke 4 conditions

Interview ke liye ye important hain.

Deadlock generally tab possible hota hai jab ye conditions exist karein:

### 1. Mutual Exclusion

Ek lock ko ek time par ek thread hold kar raha hai.

```text
Lock A → Thread-1
```

### 2. Hold and Wait

Thread ek lock hold karke doosre lock ka wait kar raha hai.

```text
Thread-1
   ↓
A locked
   ↓
B waiting
```

### 3. No Preemption

Lock ko forcefully doosre thread se nahi cheena ja sakta.

### 4. Circular Wait

Sabse important:

```text
T1 → waits for T2
T2 → waits for T1
```

Circular dependency ban gayi.

---

# 10. Deadlock ko prevent kaise karoge?

Sabse simple aur important technique:

## Same Lock Ordering

Problem:

```text id="9a6v3s"
Thread-1:
A → B

Thread-2:
B → A
```

Fix:

```text id="c4v7m1"
Thread-1:
A → B

Thread-2:
A → B
```

Ab circular wait nahi banega.

---

# 11. Example – Fixed Code

Instead of:

```java id="x5q3n8"
Thread 1:
synchronized (lockA) {
    synchronized (lockB) {
    }
}

Thread 2:
synchronized (lockB) {
    synchronized (lockA) {
    }
}
```

Dono threads mein same order rakho:

```java id="f2m7k9"
synchronized (lockA) {

    synchronized (lockB) {

        // business logic

    }
}
```

Now:

```text id="6z3r2v"
Thread-1 → A → B
Thread-2 → A → B
```

Thread-2 ko A available hone tak wait karna padega, but circular deadlock nahi banega.

---

# 12. `ReentrantLock` + `tryLock()`

Another useful approach:

```java id="8v4q1p"
if (lockA.tryLock()) {

    try {

        if (lockB.tryLock()) {

            try {
                // business logic
            } finally {
                lockB.unlock();
            }

        }

    } finally {
        lockA.unlock();
    }
}
```

Concept:

```text id="v7x2k9"
Try to acquire lock
       ↓
Lock available?
   ↙        ↘
 Yes        No
  ↓          ↓
Continue   Don't wait forever
```

Iska benefit hai ki thread indefinitely lock ka wait nahi karta.

# 18. Interview Question

### Q: What is deadlock?

**Answer:**

> "Deadlock is a situation where two or more threads are waiting indefinitely for locks held by each other, so none of them can proceed."

---

### Q: How do you detect deadlock in production?

**Answer:**

> "I would take a Java thread dump using `jstack` and inspect the BLOCKED threads and lock ownership. The thread dump can indicate a Java-level deadlock and show which thread is waiting for a lock held by another thread."

---

### Q: How do you prevent deadlock?

**Answer:**

> "The main approach is to maintain a consistent lock acquisition order across threads. We can also minimize nested locks and use mechanisms such as `tryLock()` with timeout where appropriate."

> **Ek query parent records ke liye chalti hai, aur har parent ke liye ek additional query chalti hai.**


```text

```

So:

```text

    ↓

```

Conceptually much better.

# 17. Interview Question

### Q: What is N+1 query problem?

**Answer:**

> "N+1 is a performance issue where the application executes one query to fetch the parent records and then executes additional queries for each parent record to fetch its related data. For example, fetching 100 customers with one query and then executing one order query for each customer results in 101 queries."

---

### Q: How do you identify N+1 in production?

**Answer:**

> "I would check the API response time and SQL logs. If I see one parent query followed by many repeated child queries with different IDs, that indicates an N+1 problem. I would also check Hibernate query metrics or tracing if available."

---

### Q: How do you fix N+1?

**Answer:**

> "Depending on the use case, I can use JOIN FETCH, EntityGraph or batch fetching. I would choose the appropriate fetch strategy rather than blindly changing everything to EAGER."

---

# 18. Short Interview Answer ⭐

> **"N+1 occurs when we execute one query for parent data and then one additional query for each parent to fetch related data. For example, one customer query plus 100 order queries means 101 queries. In production I identify it by checking SQL logs and query count. I can fix it using JOIN FETCH, EntityGraph or batch fetching depending on the use case."**

# 15. Connection Leak kaise identify karoge?

Agar connections continuously busy hain:

```text id="n7c2v5"
Active Connections ↑
Idle Connections ↓
```

aur expected time par release nahi ho rahe:

```text id="y4m8q1"
Possible Connection Leak
```

HikariCP mein leak detection configuration bhi available hoti hai.

Example:

```properties id="b6x3p9"
spring.datasource.hikari.leak-detection-threshold=2000
```

Meaning conceptually:

> Agar connection unusually long time tak borrowed raha, Hikari warning generate kar sakta hai.

**Important:** Is setting ko blindly low value par production mein nahi rakhna chahiye, warna normal long-running operations bhi false warnings de sakti hain.

# 21. Interview Question – What is HikariCP?

> **"HikariCP is a JDBC connection pool used by Spring Boot applications to efficiently manage and reuse database connections instead of creating a new database connection for every request."**

---

# 22. Interview Question – What is Connection Pool Exhaustion?

> **"Connection pool exhaustion occurs when all available database connections are busy and new requests cannot obtain a connection within the configured connection timeout. Common causes include connection leaks, slow queries, long transactions and high concurrent database usage."**

---

# 23. Interview Question – How will you debug it?

Ye answer yaad karo:

> **"First, I will check the HikariCP metrics such as active, idle and pending connections. If all connections are busy, I will investigate why they are not being released quickly. I will check for connection leaks, slow SQL queries, long-running transactions and high database traffic. I will also check database health and query performance. I would fix the root cause instead of blindly increasing the pool size."**

---

# 24. Short Interview Answer ⭐

Agar interviewer bole:

**"Production mein HikariCP connection timeout aa raha hai, what will you do?"**

Bolo:

> **"I will first check HikariCP metrics. If active connections are equal to maximum pool size, idle connections are zero and pending requests are increasing, the pool is under pressure. I will then check for connection leaks, slow queries, long transactions and traffic spikes. After finding the root cause, I will fix it and only then tune the pool size if required."**
